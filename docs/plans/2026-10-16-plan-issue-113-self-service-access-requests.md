## 2. Architecture Decisions

### Increment A: self-service request and withdraw

#### A-1 Token classes and the two scopes (Q-113-2)
Three new options on `EntraIdAuthOptions` (`JwtOptions.cs`, next to `ReadOnlyScopes`): `SelfServiceScopes` (nullable list, empty or null = **feature off**, sample value `["data.access.request"]`), `ReviewScopes` (nullable list, sample `["data.access.review"]`). No default values for `SelfServiceScopes` (PRD FR-113-1); `ReviewScopes` null means `["data.access.review"]` **only when the review requirement is active** (below).

`EntraTokenPolicy.Apply` changes in the delegated branch only:
1. `readOnlyOrSelf = ReadOnlyScopes ∪ SelfServiceScopes`; the token is read-only when `scopes.All(in readOnlyOrSelf)` and the union is non-empty (today: `ReadOnlyScopes` only). A token that has **any scope outside the union** keeps today's behaviour (full token, **not** read-only, no self-service marker needed).
2. When the token is read-only, `scopes.Any(in SelfServiceScopes)`, `scopes.Count > 0` (delegated) **and** the subject is a person (A-2), the policy adds the self-service marker (`TokenAccessScope.MarkSelfService`, fixed issuer, same pattern as `MarkReadOnly`, new constant `autheris:access_self_service`). The marker is **additive to** `autheris:access_mode=read`: the token stays read-only.
3. The review requirement (`ReviewScopeRequired`) is active when `SelfServiceScopes` is non-empty **or** `ReviewScopes` is explicitly non-empty. Off by default so existing deployments are unchanged (owner flag O-1).

Startup validation (`GatewayEmptyListConfigurationValidator` pattern plus a new `SelfServiceScopeConfigurationValidator`; fails the start): scope names trimmed and non-empty; **no scope appears in both `SelfServiceScopes` and `ReviewScopes`**; **no review scope appears in `ReadOnlyScopes`** (a read-only review token is a contradiction); if `SelfServiceScopes` is non-empty, the effective review scopes are non-empty. An explicit empty `SelfServiceScopes: []` is logged like `ReadOnlyScopes` (Warning, feature off). **Rev. 2 (SEC-113-03, O-1):** scope names carry no resource prefix that differs from the configured API audience (or both sides are normalised by the same function); one scope reader `TokenScopes.Read(principal)` (`scp`, mapped scope URI, `scope`) is used by `EntraTokenPolicy`, the classifier, `ConsentActorPolicy` and the middlewares, and `IsSameScope` uses the same normaliser; as soon as `SelfServiceScopes` is non-empty the review requirement cannot be switched off; tokens without `scp` stay exempt only from the missing-review-scope condition of A-4.

#### A-2 Person-subject gate (Q-113-1)
New `PersonSubject.TryResolve(ClaimsPrincipal, IIdentitySubjectResolver)` in Application returning the requester `Sid` or failure: requires `Identity.IsAuthenticated`, `ResolveSubject(...).Type == SubjectType.User`, **and** at least one claim of `Sid.cs`'s immutable user list (`ImmutableUserSidClaimTypes`, `:41-52`). The requester `Sid` is the first immutable claim in the same order as `GetUserSid()` **excluding** `appid`/`client_id`/`azp` (new `ClaimsPrincipalExtensions.GetPersonSid()` next to `GetUserSid`; `GetUserSid()` itself is **not** changed, it has many callers; the #129 plan introduces its own `CallerSubjectFactory`, the two must agree on the claim order, test 9). Failure (app-only, service principal, certificate subject, no immutable claim) means **no self-service** and `FORBIDDEN` with the neutral text `Access requests require a signed-in person.`; delegated tokens that carry no human claim (no upn/mail/preferred_username/unique_name, so the resolver classifies them as service principal) are rejected too (fail closed, documented in Phase 6). The gate applies to: a **read-only** principal on `requestTableAccess`, `withdrawMyAccessRequest` and the MCP tools. For full tokens the existing behaviour (`GetUserSid()`) is kept for `requestTableAccess` (no regression for existing clients) but the gate result is **also** required to be present when the token is app-only (`AppOnlyTokens=ReadWrite`): an app-only full token filing requests is out of scope and rejected as `FORBIDDEN` (hardening, owner flag O-2). **Rev. 2 (SEC-113-04..06):** `GetPersonSid()` accepts only `oid` and on-prem SID claims (`primarysid`/`objectSid`-class) for the self-service path; `sub` and `NameIdentifier` alone (pairwise per application, unmatchable against an approver key) do not qualify and fail closed. The stored `RequesterIdentifiers` always contain that canonical key, so identity-set self-approval matches across token classes. The rejection of app-only and service-principal tokens, for requesting and deciding, is **unconditional** (it is no longer tied to an owner flag; O-2 is a confirmation only); the decision side ships first in WP-0.

#### A-3 Closed allowlist in the GraphQL pipeline (FR-113-2, PRD veto 1)
`ReadOnlyOperationMiddleware` keeps its place and contract; before returning `READ_ONLY_TOKEN` it asks the new `MutationRootFieldClassifier` (Application-free, `Autheris.GraphQL`):
- Selected operation: by `OperationName`; if the name is null and the document has more than one operation, **all** operations are considered (as today); an operation name that matches no definition counts as "unknown" and the request is rejected.
- Root selections are collected by walking the selection set of each mutation operation: plain `FieldNode` (use **`Name`, never the alias**), `InlineFragmentNode` (a type condition other than `Mutation` or absent is rejected), `FragmentSpreadNode` resolved against the document's fragment definitions with a visited set and depth limit 8 (cycle, missing fragment, or depth overflow rejects). `__typename` is ignored. Directives `@skip`/`@include` do not change classification (a conditionally skipped field is still counted).
- The document is **self-service-only** iff every collected root field name is in the **code constant** `{ requestTableAccess, withdrawMyAccessRequest }` (case-sensitive ordinal) **and** at least one exists. A single other field makes the whole document `READ_ONLY_TOKEN`.
- The exception requires `principal.IsReadOnly()` **and** `TokenAccessScope.IsSelfServiceRequester(principal)` **and** the person gate (A-2). Without the marker, behaviour is exactly as today.
- Adding a name to the constant is a code change with a security review (FR-113-2); a source-level test pins the set.
Subscriptions are untouched (the classifier only looks at mutation operations). GraphQL batching: each batch item is its own `RequestContext` through the same middleware; there is no shared state. **Rev. 2 (SEC-113-02):** the classifier exception is the **last** commit of WP-A3 (after the resolver guard and `ConsentDecisionMiddleware`) and is inert unless `SelfServiceScopes` is non-empty; the reflection test T-S6 (every mutation field is outside the allowlist and unreachable for read-only principals, or explicitly allowlisted) runs in CI.

#### A-4 Decision guard (G-3, review scope)
New `ConsentActorPolicy` (Application, pure, injectable; options snapshot of `EntraIdAuthOptions` plus `IIdentitySubjectResolver`):
`Evaluate(ClaimsPrincipal, ConsentAction { Request, Withdraw, Decide })`. For `Decide` (approve, reject; in B also configuration confirmation) it denies (`FORBIDDEN`, code `DECISION_NOT_PERMITTED`) when **any** holds:
1. the principal is read-only (`IsReadOnly()`), whatever its scopes;
2. the subject is not a person (A-2) (a service principal never decides: owner flag O-2);
3. `ReviewScopeRequired` and the token is scope-bearing (`scp` present, `TokenAccessScope.GetScopes(principal).Count > 0`) and carries **no** scope of the effective review list; tokens without `scp` (Basic, Kerberos, ForwardAuth, ADFS: they cannot carry the scope) are not subject to 3 but still to 1 and 2;
4. the token carries **any scope of `ReadOnlyScopes` or `SelfServiceScopes`** (agent class), with or without the marker and with or without a review scope: requesting and deciding never share a token and an agent-class token never decides (owner flag O-5; **rev. 2, SEC-113-01**: `{Agent.Read, data.access.review}` is a full token but cannot decide). A Warning is logged when a decision is denied for this reason.
It is evaluated at two points: (a) in the new `ConsentDecisionMiddleware` registered **next to** the read-only middleware (it uses the same root-field walk: a mutation operation containing `approveConsentRequest` or `rejectConsentRequest`, plus the B fields, runs the policy before any resolver); (b) inside the resolvers `ApproveConsentRequestAsync` and `RejectConsentRequestAsync` at the top, by resolving `IConsentActorPolicy` from `HttpContext.RequestServices` (precedent: `MutationTypes.cs:313-320` resolves `IGrantPolicy` this way). (b) is defence in depth for callers that bypass the pipeline (tests, future in-process callers); a missing service in (b) is a composition error caught by a DI composition test, not a silent allow. The policy **adds to**, never replaces, the existing checks (ownership/admin authorization, self-approval by identity set, repository re-checks, four-eyes). **Rev. 2 (SEC-113-02):** WP-0 has already placed `IConsentDecisionGuard` in both resolvers (read-only and non-person denial). In A the resolver call is switched to `IConsentActorPolicy`, which composes that guard, in the first commit of WP-A3; resolution is `GetRequiredService` (throw) and **no `GetService ... ?? new` fallback** exists anywhere (the `:316-318` pattern is forbidden for guards). Denials are aggregated per principal and minute: the first writes the Tier-A `CONSENT_DENIED`, the others only increment the metric (SEC-113-13). The approve/reject messages no longer contain the table identifier or foreign-tenant wording and answer the same `NOT_FOUND` for unknown and foreign ids (SEC-113-10).
Self-approval stays as today (`MutationTypes.cs:273`, repository `:1056-1088`); the policy adds nothing there but test 6 pins it for the new token classes. Requesting and deciding are therefore separated twice: by scope (token level) and by person (identity level).

#### A-5 Request record: `context`, token class, withdrawal
`CONSENT_REQUESTS` (baseline in place) gets `context` (nullable, max 500 stored, option cap 200), `withdrawn_at` (nullable), `submitted_via` (`full` or `self-service`, fixed vocabulary). `ConsentRequest` (`GovernanceModels.cs:33`) gets `Context`, `WithdrawnAt`, `SubmittedVia` (init). Repositories write them in `CreateConsentRequestAsync` and read them in `GetConsentRequestAsync`, `GetRequestsByRequesterSidAsync`, `GetPendingRequestsForApproverAsync` (three engines). `ConsentRequestDto` gets `Context`, `WithdrawnAt`. `context` is plain text: control characters rejected, trimmed, length-capped (`MaxContextLength`, default 200), **never** used for routing, authorization, approver selection or SQL; output through GraphQL is JSON-escaped; the audit stores only its length (SI-113-6). It is part of the idempotency fingerprint (`ConsentRequestService.cs:86-88`, append `context`; a key reuse with another context is a different request, not a replay). **Rev. 2 (SEC-113-08):** `context` **and** `justification` go through one `UntrustedText.Normalize` (NFC; control characters rejected, except LF in `justification`; bidi overrides U+202A-202E and U+2066-2069, zero-width characters and NUL rejected; per-field length cap). `ConsentRequestDto` and the MCP results additionally carry `submittedVia` and the caller-application label so an approver sees that an agent filed the request; both text fields are documented as untrusted user data, never logged, never used for routing, approver selection or tool arguments.

#### A-6 `withdrawMyAccessRequest` (FR-113-3)
New `IConsentWithdrawalService.WithdrawAsync(requestId, principal, tenant)` (Application). Rules, in this order, all tenant-scoped: person gate (read-only principals need the self-service marker, A-3); load the request; unknown id, foreign tenant, or a request whose `RequesterSid` is **not** in `principal.GetAllUserSids()` all answer the **identical** `NOT_FOUND` (same message, no oracle); status must be `PENDING` or `PENDING_SECOND_APPROVAL`, else `ACCESS_REQUEST_NOT_PENDING` (this includes `PENDING_EXTERNAL_APPROVAL`: the ticket belongs to the change board, G-7, and `APPROVED`, `REJECTED`, `WITHDRAWN`). The repository applies **one conditional statement**: `UPDATE CONSENT_REQUESTS SET status = 'WITHDRAWN', withdrawn_at = @now WHERE id = @id AND tenant_id = @t AND requester_sid = @sid AND status IN ('PENDING','PENDING_SECOND_APPROVAL')` and an audit entry in the same transaction; zero rows means the state changed concurrently and answers `ACCESS_REQUEST_NOT_PENDING`. The approve and reject UPDATEs in the three repositories get the matching `AND status = @expected` guard so an approval and a withdrawal that race end in exactly one terminal state (test 22). No consent exists for a withdrawn request (the `WHERE status = 'APPROVED'` activation conditions already exclude it). Available to every authenticated person (full and self-service tokens), not to app-only tokens (A-2). **Rev. 2 (SEC-113-11):** the guarded approve/reject `UPDATE` and the policy-before-step order are delivered by WP-0; A adds `WITHDRAWN` to the non-approvable set of `ConsentApprovalPolicy.EnsureApprovableStatus`, and until B the consent creation after the step re-reads the status and creates nothing for a request that is not `APPROVED` (a withdrawn or no-longer-pending request never produces a consent).

#### A-7 Limits (FR-113-5)
`ConsentRequests:MaxPendingPerPerson` (25), `ConsentRequests:MaxSubmissionsPerHour` (30), both counted in the store by **immutable requester sid and tenant** (`CountOpenRequestsAsync`, `CountSubmissionsSinceAsync` on `IConsentApprovalRepository`, default interface members throwing `NotSupportedException`, the precedent `GetRowFilterAsync`): pending = status in `PENDING`, `PENDING_SECOND_APPROVAL`, `PENDING_EXTERNAL_APPROVAL`. A repository failure **denies** the submission (`ACCESS_REQUEST_LIMIT_INDETERMINATE`, fail closed, nothing created). The count-then-insert is not atomic across engines; a burst can exceed the cap by at most the number of concurrent submissions, which is acceptable for an anti-spam limit and documented (R-4); the limit is not a security boundary. Exceeding returns `ACCESS_REQUEST_LIMIT_EXCEEDED`. The limits apply to **all** submissions (self-service and full) so the agent path cannot flood approvers while a person path stays open. **Rev. 2 (SEC-113-09):** additional **self-service sub-caps** `SelfServiceMaxPending` (default 5) and `SelfServiceMaxSubmissionsPerHour` (default 10) apply to requests with `submitted_via = self-service`. **At most one open request per (person, table):** a partial unique index over (tenant, requester, table) for the open statuses (C-4) makes this rule race-free; a second identical open request returns the existing request id, writes no row and dispatches no ticket (a duplicate for another table is a normal request). ITSM dispatch happens only after every limit check. A denial by a limit is a metric only (no Tier-A event per attempt). The remaining count-then-insert race applies only to the caps (R-4).

#### A-8 Hidden datasets and neutral answers (FR-113-6)
After the metadata lookup `SubmitAsync` applies the visibility predicate delivered by #111 (`CatalogVisibility` with the `Discovery` surface; PLAN-GOV-111): a table that is `Hidden` for the caller (caller neither admin, nor owner/delegate, nor holder of a grant) answers the **same** `FORBIDDEN` as an unknown table (`ConsentRequestService.cs:96-101`, same code, same text). The check runs **before** the grant policy and before any write. A visibility lookup failure denies. This depends on I-7 (#111): without persisted tiers every table is `Hidden` for non-owners, so A must not ship before I-7 (the tracker already orders it so). The same predicate guards the MCP request tool. Behaviour change for full tokens documented as owner flag O-6. **Rev. 2 (SEC-113-10):** fixed order **input validation, visibility, limits, grant policy**; hidden and unknown tables share one code path (same code, same text, no timing-relevant extra work), the idempotency replay precedes only for the caller's own stored result.

#### A-9 MCP tools for agents
Two built-in tools, registered in `McpToolRegistry` and listed in `McpToolGroups` group `Access` (PLAN-SEC-115; the pinning test fails CI for an unmapped new tool): `request_dataset_access` (`dataset`, `justification`, `durationDays`, optional `context`; calls `IConsentRequestService.SubmitAsync`) and `withdraw_access_request` (`requestId`; calls `IConsentWithdrawalService`). Tool visibility: not listed for sessions that are read-only without the marker or not person-bound (precedent `McpAdminTools.CanUseAdminTools`, `McpAdminTools.cs:45-51`). Over MCP there is **no** approve or reject tool and none is added (an agent must never decide). Owner flag O-7 (the PRD names only GraphQL). **Rev. 2 (A conditions 10, 11):** the marker is dropped when sent as a claim or `AdditionalClaims`; tools are listed only for person-bound sessions that carry the marker; the tool descriptions state that a request is filed only on the explicit instruction of the user; results return request id, status and the neutral error text only, never other people's data; sessions inherit the per-person and self-service limits; no notification is introduced (any later one sends ids and counts only, never `justification` or `context`, and never an approval deep link).

#### A-10 Audit, metrics
New Tier-A event types `ACCESS_REQUEST_SUBMITTED` and `ACCESS_REQUEST_WITHDRAWN` (`AuditEventTypes.cs`, `FailClosed` in `AuditPolicyTable.cs`). Written through `IAuditWriter.RecordRequiredAsync` (abort on failure): for submission **after** the request row exists and compensated by deleting it when the audit write fails (precedent `DeleteConsentRequestAsync`, `ConsentRequestService.cs:172-191`); for withdrawal inside the repository transaction. Details: requester sid, table, token class (`read-only+self-service` or `full`), request id, requested valid-to, context **length** (never text), caller application header value as `CallerContext` already carries it (normalisation per REQ-OBS-114 is applied once #114 lands; until then the existing field). Also `DECISION_NOT_PERMITTED` denials by `ConsentActorPolicy` write a Tier-A `CONSENT_DENIED` entry (`AuditEventTypes.cs:70`) with the reason class (read-only, not person, missing review scope, mixed token). Metrics: `autheris_access_requests_total{outcome,token_class}` (outcome from a fixed set), `autheris_access_request_denied_total{reason}`; labels are fixed vocabularies, never ids. **Rev. 2 (SEC-113-13) supersedes the compensation described above:** the submission row and its audit entry are written in **one repository transaction** (`CreateConsentRequestWithAuditAsync`, as the withdrawal does); an audit failure rolls the request back and there is no window with an unaudited, approvable request and no compensating delete. ### Increment B: approver-chosen configuration on approval

#### A-12 Scope of B and what it reuses
B adds an **approval configuration** (column levels plus typed row filters) chosen by the approver or proposed from a template, validated at write time, frozen per request, and activated atomically with the consent. It reuses `ConsentRowFilter` (`SimpleColumnPredicate` only, `LITERAL` only; correlated and cross-source filters and `USER_ATTRIBUTE` are **not** offered on approval: #129 comes later in the delivery order and the correlated forms carry the #107 strategy surface that has its own admin API), `ConsentColumnRule` and `TypedRowFilterBuilder` for enforcement. It does not invent a filter dialect and does not duplicate F-GOV-11 access profiles (templates are an approver convenience, not a second policy store: they are consulted only while a request is being decided and never grant anything by themselves). **Rev. 2:** B offers a **dataset-default template** per table and free-form admin configuration; **group templates are not part of B** (SEC-113-15, R2.4).

#### A-13 Atomic approve-and-activate (SI-113-4, G-6)
New `IConsentApprovalRepository.ApproveConsentRequestWithConfigurationAsync(requestId, approverSid, ApprovalConfiguration config, ConsentActivationPlan activation, ct)` (default member throwing `NotSupportedException`; implemented on the three engines by factoring the existing step logic into an internal core that accepts an optional activation): in **one transaction** it re-checks status, authorization, self-approval and four-eyes (as the existing step), inserts the step with the config hash, writes or checks the frozen configuration row, updates the status, and **when the new status is `APPROVED`** inserts the consent through the existing `InsertConsentCoreAsync` (consent row, column rules, row filters, `CONSENT_GRANTED` audit), bumps the table epoch (`IncrementTableEpochInternalAsync`, same transaction), and commits; only after the commit `InvalidateEpochAsync` (exactly as `CreateConsentAsync`, `:1282-1297`). Any failure rolls the step back: the request stays pending. `IGrantPolicy.Evaluate` runs in the application service **before** the call, at activation time with `Now` (as `MutationTypes.cs:313-337`), and a denied decision aborts before any write; the repository additionally refuses an activation plan whose individual-grant `ValidTo` is null or beyond a re-derived class maximum (second line, test 33). The existing two-call path in `MutationTypes.cs:293-356` is replaced by this call for **all** approvals (with and without explicit configuration), which also fixes the A-phase gap for existing clients; the legacy overload without configuration keeps working through the built-in default configuration. **Rev. 2 (SEC-113-12 B, -22):** the repository second line **re-derives the grantee class and the class maximum from table metadata through `GrantClassifier`** (never from caller-supplied plan data) and refuses a null or oversized `ValidTo` for User/ServicePrincipal grantees; the ITSM overload and the (guarded, A-20) auto path evaluate `IGrantPolicy` at activation with `Now`; the approval configuration offers no duration. The legacy overload without configuration is exactly "approve with `confirmProposed` against the current proposal" and runs through the same guards, including `CONFIGURATION_BLOCKED`; it is not a bypass of the blocked state.

#### A-14 Approval configuration model and validation (FR-113-8, FR-113-10, SI-113-5)
`ApprovalConfiguration` = column levels (`Deny`, `Mask`, `Clear` per column; the GraphQL names `DENY`, `MASKED`, `FULL` map to the existing `ColumnAccessLevel`) plus up to `MaxRowFilters` (default 8) typed filters. `ApprovalConfigurationValidator` (Application, pure plus the table metadata) rejects the **whole** approval (`INVALID_ROW_FILTER`, `INVALID_COLUMN_LEVEL`; nothing is written, the request stays pending) unless:
- every column named exists in the catalog metadata of the table (case-insensitive exact, canonicalised to the catalog spelling), appears once, and every catalog column gets a level (missing columns default to the built-in snapshot level, never to `Clear`);
- no non-admin approver raises any column above the built-in snapshot level (`Mask` to `Clear` for a sensitive or masked column is **governance admin only**; `Deny` is always allowed); a four-eyes table keeps its two steps, and the second approver must submit the **same** configuration hash (A-16);
- every filter: `FilterType = SimpleColumnPredicate`, `ValueSource = LITERAL`, operator in the allowlist of `TypedRowFilterBuilder` (`EQ NEQ LT GT LTE GTE LIKE IN`, exposed as one shared internal constant so the validator cannot drift from the enforcer), column identifier matches the same regex, value JSON parses and its element types match `ValueType` and the catalog type of the column (`int`, `decimal`, `date`, `string`), `IN` has 1..`MaxInValues` (default 100) elements, `LIKE` patterns at most 128 characters, string values at most 256 characters, no NUL or control characters, `USER_ATTRIBUTE`, subquery and cross-source properties **must be null**;
- a **dry compile** with `TypedRowFilterBuilder.Build(filters, table)` succeeds (the validator calls the enforcing compiler, so a filter that would fail at read time, which would deny the table to the grantee, is rejected at write time);
- the filter references **no sensitive column in a way that discloses it**: a filter on a column whose level is `Deny` is rejected (a hidden column must not steer visible rows); a filter on a `Mask` column is allowed (the filter applies to the stored value, as for every consent filter).
Values are persisted as `ValueJson` and bound as parameters by the existing builder; nothing is concatenated. The validator never logs values. **Rev. 2 (SEC-113-16, -17):** the validator persists the **canonical** operator (upper case) and the catalog spelling of the column; a configuration that declares N filters must still hold N compilable filters after canonicalisation, and an effectively empty filter list (which means "no restriction") is rejected when filters were declared; `LIKE` patterns made only of `%` and `_` are rejected as `FILTER_NOT_RESTRICTIVE`; fixed value typing: `int` = Int64 invariant, `decimal` = invariant without exponent, `date` = strict `yyyy-MM-dd`, `string`; error messages and logs carry a reason code and the filter index, **never input text** (the message of `TypedRowFilterBuilder` that echoes the column text is changed accordingly). Free-form configuration and any `Mask` to `Clear` raise of a sensitive or masked column require the admin class (claims) **and a second distinct approver, forced regardless of `requires_four_eyes`**; in `Multi` tenancy mode a tenant-scoped admin may do this only for tables of their own tenant (PLAN-GOV-111 rev. 3 `CallerScopeResolver` rule), else `FORBIDDEN`.

#### A-15 Templates (FR-113-9, Q-113-3, Q-113-4, Q-113-5)
Storage `TABLE_ACCESS_TEMPLATES` (separate from `TABLES`: ingestion upserts rewrite `TABLES`, the reason F-GOV-21 and #107 used separate tables), tenant-scoped, **one dataset-default template per (tenant, table)** (Rev. 2: no `group_key`). A template = column levels + typed filters in the same shape as A-14 (validated at write time by the **same** validator against the current catalog metadata). Maintained through the governance admin REST API and the declarative manifest (F-GOV-15, `DeclarativeConsentApplyService`); a row has `source` (`admin` or `manifest`); **the manifest wins** only with an audit entry: applying a manifest replaces the row for the same (tenant, table) and marks it `manifest`; an admin `PUT` on a `manifest` row answers `409 TEMPLATE_MANAGED_BY_MANIFEST`. Template revisions increment; the approval stores template id and revision.

**Rev. 2 (SEC-113-14, -15, -19): proposal states, no fallback.** The proposal service (evaluated at approval time, never at request time) returns one of three states: `TEMPLATE` (the dataset-default template exists and **validates on every read**), `BUILTIN` (the dataset has **no template at all**, is not a four-eyes table and its sensitivity rank is at most `ConsentRequests:BuiltInDefaultMaxSensitivity`, default `Internal`; the built-in default is the metadata column snapshot without row filter), or `BLOCKED` (a template exists but fails validation, its JSON is malformed or tampered with, or it cannot be applied; **or** there is no template and the sensitivity is above the ceiling or the table is four-eyes). There is **no** fallback from `BLOCKED` to `BUILTIN` on any error path; the Error log carries ids and a reason class, never values. Group templates and any requester-group resolution are not part of B (R2.4); the approver's and the requester's groups are never consulted.
Who may choose what (Q-113-3, rev. 2): a **non-admin** approver (owner, delegate) may approve only a proposal in state `TEMPLATE` unchanged (`templateId` plus `proposalHash`) or `BUILTIN` unchanged; a free-form column level or filter by a non-admin is `FORBIDDEN_FREE_FORM_CONFIGURATION`, and a `BLOCKED` proposal answers `CONFIGURATION_BLOCKED` with nothing written. A **governance admin** (claims `GovernanceAdmin` or canonical ClusterAdmin, `MutationTypes.cs:259`) may submit a validated free-form typed configuration, also to override a `BLOCKED` proposal; such an approval is audited as an override with a reason class (`TEMPLATE_INVALID`, `ABOVE_CEILING`, `FOUR_EYES_NO_TEMPLATE`, `FREE_FORM`) and always needs a second distinct approver (A-14). Template authoring (admin API, manifest) is governance-admin-only.

#### A-16 Confirmation, proposal hash, frozen configuration (FR-113-8, FR-113-13)
`proposalHash` = SHA-256 over the canonical JSON of (proposal state, template id, template revision, column levels, filters, table id, **request id, tenant id, requester canonical key, requested `ValidTo`, and a hash of the live table metadata (column names, types, sensitivity)**) (Rev. 2, SEC-113-18: a hash computed for one request never confirms another). Approving **without** a configuration argument is accepted only when the resolved proposal is `BUILTIN` (which already implies no four-eyes and sensitivity at or below the ceiling); in state `TEMPLATE` it answers `CONFIGURATION_CONFIRMATION_REQUIRED` carrying the current hash, in state `BLOCKED` `CONFIGURATION_BLOCKED`, and nothing is written in either case. `confirmProposed: true` plus `proposalHash` is accepted only if the backend recomputes the **same** hash now (a template or table metadata edited between preview and approve answers `PROPOSAL_CHANGED`). The first approval step stores the configuration (table `CONSENT_REQUEST_APPROVAL_CONFIGS`, one row per request: `config_json`, `config_hash`, template id and revision, state, proposer sid, `metadata_hash`, `four_eyes_forced`, `override_reason_class`, resolution record); `APPROVAL_STEPS` gets a `config_hash` column. A second step must present the **same** hash (or `confirmProposed` against the stored frozen configuration) **and** the stored configuration is re-validated against live metadata at step-2 time (drift answers `PROPOSAL_CHANGED`), else `CONFIGURATION_MISMATCH`; the same person cannot give both steps under any claim spelling. A later step cannot change what an earlier step approved; changing means reject and re-request. The frozen row is what the activation reads.

#### A-17 Auto-approve, ITSM, bundled requests (FR-113-12)
`IsAutoApproveEnabled` (insecure getting-started flag, `GatewayOptions.cs:109`): never for self-service or agent-class requests (A-20); for other requests the path applies **only** the dataset-default template (never free-form) through the same atomic activation and only if a valid default exists, or the dataset has no template and its sensitivity is at most `BuiltInDefaultMaxSensitivity` (`Table.SensitivityRank`, `TableModels.cs:60`); otherwise the request stays `PENDING` (a dataset with any template but no valid default, or above the ceiling without template; fail closed, Error log and metric). **ITSM (SEC-113-20, Rev. 2):** at submission, after the limit checks, the service resolves the dataset-default proposal and **freezes** it in `CONSENT_REQUEST_APPROVAL_CONFIGS` (state `ITSM_DEFAULT`) before dispatch; the ticket text carries the configuration summary (hash, filter column names and column levels, no values; for the built-in snapshot the text states "no row filter"). If the dataset has any template and no valid default, the submission is refused `ACCESS_REQUEST_CONFIGURATION_BLOCKED` with nothing created and an alert. The signed webhook activation (`ActivateConsentCoreAsync`, new overload) applies the frozen configuration only if the recomputed hash equals the frozen hash (else it stays `PENDING_EXTERNAL_APPROVAL`, retryable failure, alert) and evaluates `IGrantPolicy` at activation with `Now` (SEC-113-12). Without any template the built-in snapshot applies unchanged, regardless of the ceiling, because the change board approves a ticket that says so (owner flag O-4). `BundledConsentRequestService` requests are decided by the same GraphQL approval and therefore get B automatically; their creation is **not** opened to read-only tokens (REST path, closed by `ReadOnlyTokenMiddleware`).

#### A-18 GraphQL surface for B
Additive: `approveConsentRequest(requestId, idempotencyKey, configuration: ApprovalConfigurationInput)` with `ApprovalConfigurationInput { templateId, proposalHash, confirmProposed, columnLevels: [{column, level}], rowFilters: [{column, operator, valueType, values: [String!]!}] }` (a legacy call without the argument keeps compiling); query `proposedAccessConfiguration(requestId)` returning `{ source, templateId, templateRevision, proposalHash, columnLevels, rowFilters, candidates, requiresConfirmation, preview }`; `preview` is the **effective access** the requester would get, computed with the existing `EffectiveAccessExplanationService` over a **hypothetical consent** (no write, FR-113-14). Both are guarded by `ConsentActorPolicy` `Decide` and the approver authorization of the request (non-approvers get `FORBIDDEN`, unknown or foreign-tenant ids `NOT_FOUND`). `pendingApprovalsForMe` and `myAccessRequests` additionally return `context`, `withdrawnAt` and (to approvers) the proposal source. Idempotency fingerprint of approve includes the configuration hash. **Rev. 2 (SEC-113-21, -22):** `proposedAccessConfiguration` returns `{ state, templateId, templateRevision, proposalHash, columnLevels, rowFilters, blockedReasonClass, requiresConfirmation, preview }` (`candidates` is removed with group templates); unknown and foreign-tenant ids answer the same `NOT_FOUND`; the preview names columns and levels of the request's own table and the filters of this request's proposal only and is never cached across callers.

#### A-19 Admin REST and manifest for templates (Q-113-4)
`GET|PUT|DELETE /api/v1/governance/access-templates/{datasetId}` (`GatewayPolicies.GovernanceAdmin`, `WithAudit(AuditLevel.Full, AccessTemplateChanged/Deleted)`, new `FailClosed` event types; Rev. 2: before/after **hashes** in the audit, no filter values anywhere in log lines; tenant predicate on every read; dataset resolution reuses the catalog resolution of #111; the `/groups/{groupKey}` routes are removed). The manifest gains an `accessTemplates` section (F-GOV-15 shape) applied by `DeclarativeConsentApplyService` with the same validator and an audit entry per replaced row; a validation error rejects the whole manifest (the existing all-or-nothing behaviour). Template changes do **not** bump the table epoch (a template grants nothing); they are visible to the next proposal only, and a changed template invalidates a previewed hash (`PROPOSAL_CHANGED`).

## 7. Fail-Closed Behaviour

| Situation | Behaviour |
|---|---|
| `SelfServiceScopes` empty or null | feature off; read-only tokens behave exactly as today |
| Token with a scope outside `ReadOnlyScopes` union `SelfServiceScopes` | full token, not read-only (as today); never gains the marker |
| Self-service marker absent, forged claim, or token without person subject | `READ_ONLY_TOKEN` / `FORBIDDEN`; marker claim from outside is dropped (fixed issuer) |
| Document with any non-allowlisted mutation field, unresolvable fragment, unknown operation name, indeterminate root fields | `READ_ONLY_TOKEN` for the whole document |
| Read-only token, service principal, mixed request/review token, missing review scope (when required) on approve or reject | `DECISION_NOT_PERMITTED`, no repository access, Tier-A denial entry |
| Policy service missing in a resolver | composition test fails; at runtime the resolver throws (never allows) |
| Unknown, foreign, other-person, or hidden request or dataset | identical neutral answer (`NOT_FOUND` for withdraw, `FORBIDDEN` for submit) |
| Limit lookup fails | submission denied (`ACCESS_REQUEST_LIMIT_INDETERMINATE`), nothing created |
| Visibility lookup fails | submission denied |
| Audit write fails | withdrawal rolled back; submission compensated (request deleted); decision denial still returned |
| Withdraw races with approve | exactly one terminal state (guarded `UPDATE`) |
| Invalid filter, column, level, ambiguous or stale proposal, hash mismatch | whole approval rejected, nothing activated, request pending |
| Any repository error during approve-and-activate | transaction rolled back, request unchanged |
| Template stored JSON malformed, tampered or failing the validator on read; or a dataset with templates that cannot be applied | proposal `BLOCKED`: non-admin approval `CONFIGURATION_BLOCKED`, nothing written; governance admin may approve a validated free-form configuration (audited override, forced four-eyes); never a fallback to the built-in default |
| Auto-approve: agent-class or self-service request, template without valid default, or no template above the ceiling | request stays `PENDING`; ITSM with templates but no valid default: submission refused, nothing created |
| No template and sensitivity above `BuiltInDefaultMaxSensitivity`, or four-eyes table without template | proposal `BLOCKED` (as above) |
| `IGrantPolicy` indeterminate or denies | no activation (as everywhere else) |

### R2.1 Decision on the optional WP-0: a standalone first PR

Owner rule: security bugs first. Question: is the app-only approval path a live bypass of person-based four-eyes today?

**Yes, behind one non-default setting.** With `AppOnlyTokens=ReadWrite` (`JwtOptions.cs:198`, default `ReadOnly`) an application token whose app registration carries the `GovernanceAdmin` role claim is not read-only and passes the claim test at `MutationTypes.cs:259`. `ApproveConsentRequestAsync` and `RejectConsentRequestAsync` then decide under the application id (`GetUserSid()` falls back to `appid`/`client_id`/`azp`, `Sid.cs:32-34`; P-4 of the review). Two consequences contradict the person-based control:

1. Four-eyes (`ConsentApprovalPolicy.cs:119-132`) only requires two **different approver keys**. A person approver plus one application id satisfies it, so one human who holds a client secret of an app registration with the role completes both steps alone.
2. Self-approval is matched against the requester's identity set (`MutationTypes.cs:273`, repository `:1056-1088`). An application id is never in a person's identity set, so a person cannot be stopped from approving their own request through an application they control.

The setting is opt-in and the review rated P-4 Low/Medium, but the effect is a real bypass of separation of duties that exists in the shipped code, and WP-0 fixes it without any of the A-increment machinery. Together with P-3 (approval step committed before `IGrantPolicy`, no status guard) it forms one small change in the same two resolvers and the same three repository files. **Decision: WP-0 is created and is a standalone first PR, merged before increment A, with no dependency on #111 or #107.** It is not folded into A, so the fix does not wait for the A branch and its dependency on I-7.

### P3.2 Verification of the pre-existing issues

**P-1 Read-only scope trap (`EntraTokenPolicy.cs:82-87`): VERIFIED, design weakness, NOT a live exploit today.** `scopes.Count > 0 && readOnlyScopes.Count > 0 && scopes.All(in readOnlyScopes)` marks a token read-only only when **every** `scp` entry is listed; any other scope makes it a full token (`:82-87`; defaults `Agent.Read`, `App.Read`, `JwtOptions.cs:190-195`). The classification is "read-only unless proven otherwise" in the wrong direction: it is an inclusion test, so an unlisted scope silently removes the restriction. Why it is not live today: `scp` of a v2 token contains only the scopes of **this** API's app registration, and the gateway lists exactly the two agent scopes; a token holds an unlisted scope only if the operator granted the agent application another scope of this API (a conscious grant of a write-capable scope) or exposes a new scope and consents it to the agent app. No code path adds a scope on its own. It becomes a **real bug the moment `data.access.request` is issued** to the agent application (architect G-1 is correct) unless A-1 lands in the same change. Also noted: `TokenAccessScope.GetScopes` reads only `scp` and the mapped scope URI (`TokenAccessScope.cs:25-29,39-44`), while `GetScopeSet(IEnumerable<Claim>)` also reads `scope`; a token with only a `scope` claim has zero scopes and is never read-only (`EntraTokenPolicy.cs:28,36`); Entra v2 uses `scp`, so this is theoretical, but the two readers must agree (SEC-113-03). **Severity:** Medium, latent (configuration-dependent), becomes High if A-1 is not shipped with the first issuance of the new scope. **WP-0 recommendation: NO standalone WP-0.** The fix is A-1 itself and must be the first commit of A with test T-S1; shipping it alone would change nothing observable today. Interim operational rule for the release note: never consent an agent application to any scope other than the listed ones.

**P-2 Approve/reject GraphQL mutations without scope or read-only check (`MutationTypes.cs:222-370`, `:385-465`): VERIFIED, defence-in-depth gap, NOT a live bug today.** `ApproveConsentRequestAsync` evaluates tenant (`:263-270`), self-approval (`:273`), approver authorization (`:277-291`, claims `GovernanceAdmin`/canonical ClusterAdmin at `:259`, else ownership/delegation) and nothing about scopes or the read-only marker; `RejectConsentRequestAsync` (`:385-465`) the same minus self-approval. The only protection against a read-only token is `ReadOnlyOperationMiddleware` (`ReadOnlyOperationMiddleware.cs:27-47`, registered at `GatewayServiceCollectionExtensions.cs:581`), which rejects every document containing a mutation operation for a read-only principal, and `ReadOnlyTokenMiddleware` (`:56-97`) at HTTP level. I found **no other route** to these resolvers: the MCP `query_graphql` path rejects mutations (`GatewayMcpQueryExecutor.cs:175`), the ITSM webhook calls the repository directly (`ItsmWebhookHandler.cs:373,389`), no other caller of the resolver methods exists. All other mutations (`RevokeConsentAsync` `:481`, `ReloadSchemaAsync`, the syncs) rely on the same blanket gate, so approve/reject are not special today. The gap becomes **critical exactly when A-3 opens the pipeline** for the self-service allowlist: from then on the blanket gate is no longer total, and a classifier defect would reach resolvers that have no second line. **Severity:** Low today, High after A-3 without A-4(b). **WP-0 recommendation: NO standalone WP-0 for the scope part**; the resolver-level guard (A-4 b) is mandatory in A and must be in place before A-3 is merged (SEC-113-02).

**P-3 Non-atomic approval (`MutationTypes.cs:293` then `:356`): VERIFIED, an integrity/availability defect, not a confidentiality or privilege bug.** The step (`ApproveConsentRequestStepAsync`, own transaction, status `APPROVED`) commits at `:293`; `IGrantPolicy` is evaluated **after** it (`:313-337`) and the consent is created in a second transaction at `:356`. Consequences: (a) if the grant policy denies at activation (class maximum changed, table sensitivity raised between submission and approval) or `CreateConsentAsync` fails, the request is `APPROVED` with no consent and cannot be approved again (`ConsentApprovalPolicy.EnsureApprovableStatus` rejects non-pending status), the idempotency record is not stored (`:361`), so the requester waits forever and the approver sees an error for an already-final request; (b) the failure direction is **safe** (no access is granted), and no path creates a consent for such a request without the policy: `ActivateConsentAsync` is called only from the ITSM handler after its own step (`ItsmWebhookHandler.cs:398`). **Severity:** Medium (integrity/availability, no escalation); the new self-service volume and the withdrawal race (SEC-113-11) raise its operational weight. **WP-0 recommendation: OPTIONAL narrow WP-0 (S), not blocking A:** (1) evaluate `IGrantPolicy` **before** the final step (the request already carries `RequestedValidTo`, so the decision can be made on the pending request; a denial then leaves the request pending and rejectable); (2) a status guard in the approve/reject `UPDATE` (`SqliteGovernanceRepository.Consent.cs:1192,1267`: no `AND status = ...`). The full atomic fix stays in B (A-13). If the owner prefers not to touch this before #113, A must carry (1) and (2) itself (SEC-113-11).

**P-4 (found during review, not in the architect list): app-only decider.** `GetAuthenticatedUserSid` uses `GetUserSid()` (`MutationTypes.cs:49-69`, `Sid.cs:21-36`) with fallback to `appid`/`client_id`/`azp`. With `AppOnlyTokens=ReadWrite` (non-default, `JwtOptions.cs:198`) an application token carrying a `GovernanceAdmin` role claim can approve and reject today under its application id (`MutationTypes.cs:259,281`). Severity Low/Medium, operator-opt-in; it contradicts the owner rule only if automation is not intended to decide (owner flag O-2). Covered by SEC-113-06; the minimal decision-guard (read-only + service-principal denial) belongs in the optional WP-0 if the owner wants this closed before A.

**Summary:** no finding is a live, unauthenticated or privilege-escalating bug today. The recommended **standalone WP-0 is limited to P-3 (1)+(2) and, optionally, the P-4 guard**; P-1 and P-2 are closed by the planned A-1/A-4 provided the conditions below on ordering hold.

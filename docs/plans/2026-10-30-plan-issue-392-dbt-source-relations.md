# Plan: dbt source relations, source keys and relation columns in describe_dataset (issue #392)

Phase 2 (csharp-architect), 2026-10-30. Branch `fix/issue-392-dbt-source-relations` (base `0e5b62cf`). Triage: `2026-10-29-triage-issues-388-393.md` section #392. Size: L in three work packages (392a M, 392b S-M, 392c S-M); about 450 production LOC, 700 test LOC.

## Problem (verified on the branch)

- `DbtArtifactStreamingParser.ExtractModelName` (`:679-704`) turns `source('src','t')` into `src.t`; the `relationships` test path (`:63-101`) compares that with bare `depends_on` names, so with `attached_node: null` the first source in `depends_on` (possibly the parent) becomes the child. Relations carry names only (`DbtRelationshipDefinition`, `DbtMetadataModels.cs:68`).
- `ImportRelationsAsync` (`DbtMetadataIngestionService.cs:901-926`) keys `modelByName` by `Name` and `UniqueId` with last-wins, so `src.t` gives `UNKNOWN_MODEL` and a name shared by two nodes silently picks one.
- `CollectUniqueTest` (`:621-671`) falls back to `model.` dependencies only; source key tests are lost. The final key loop (`:408-414`) already covers sources.
- `McpGraphQlRelation(Field, Dataset, IsList)` (`McpDatasetModels.cs:96`) drops the join keys that `CatalogRelationField.ParentColumns/ChildColumns` (`CatalogSchemaModel.cs:37-38`, own side first in both directions, `:405-406`, `:469-470`) already carry; `CatalogGraphQlMap.cs:49` discards them.
- Size ceilings (`Baselines/source-size-ceilings.txt`, may only fall): `McpDatasetCatalog.cs` 1319/1319, `DbtMetadataIngestionService.cs` 2160/2173. New logic goes into new classes.

## Decisions

1. **Node index and reference resolver (392a).** New `src/Autheris.Extensions/Dbt/DbtManifestReferenceResolver.cs` (internal sealed). The parser registers every `model.`/`seed.`/`snapshot.` node (unique id, `name`, `package_name`, `version`) and every `sources` entry (unique id, `source_name`, `name`, `package_name`). `Resolve(string to, IReadOnlyList<string> dependsOn, string? ownerPackage)` parses `ref('m')`, `ref('pkg','m')`, `ref('m', v=N)` and `source('s','t')` (also inside `{{ }}`) and returns `Resolved(uniqueId)`, `Unknown` or `Ambiguous`. Order: candidates among the test's `depends_on` first; if none, the global index; still more than one, narrow to `ownerPackage`; still more than one = `Ambiguous`. Matching is OrdinalIgnoreCase on the logical names; the unique id is then exact. `ExtractModelName` stays for display names only.
2. **Deferred relation resolution.** Test nodes precede `sources` in the manifest, so the parser collects `PendingRelation` (kind, `to`, `attached_node`, `depends_on`, ordered parent and child columns, optional relation name) during the node pass and resolves them after the sources pass, in manifest order. `RelationCollector` counts an attempt when a pending entry is collected (memory stays bounded by `MaxRelations`, SEC-REL151-02 unchanged); `TryAdd`/`Skip` at resolution no longer count.
3. **Child resolution.** `attached_node` non-empty: child = that unique id (must be in the index, else `UNKNOWN_MODEL`). Otherwise the eligible `depends_on` nodes minus the resolved parent: exactly one = child; none while the parent is in `depends_on` = self relation (child = parent); more than one = `AMBIGUOUS_REFERENCE`. Model and column `foreign_key` constraints resolve `to` with the same resolver (child = the owning node), so a model FK to `source(...)` now works.
4. **Relation definition carries unique ids.** `DbtRelationshipDefinition` gains `string? ParentUniqueId = null, string? ChildUniqueId = null` (additive). `ParentModelOrTable`/`ChildModelOrTable` become the resolved node `name` (never `src.t`). Relation name rule unchanged (`name` of the parent, `stg_` stripped), so existing model relations keep their natural key and re-sync is idempotent (`CreateRelationAsync` upserts by parent, child, name).
5. **Ingestion lookup, fail closed.** New `src/Autheris.Extensions/Dbt/DbtRelationModelLookup.cs` replaces the dictionary in `ImportRelationsAsync`: with a unique id, exact `UniqueId` match only (missing = `UNKNOWN_MODEL`, no name fallback); without one (legacy callers), name match where more than one model has the name = `AMBIGUOUS_MODEL`, never a pick. Table identity stays `DbtModelDefinition.ToTableIdentifier()` (database, schema, name), the same mapping as table registration, so quoting and case follow the existing model path. The tenant filter (`:751`) also checks `ParentUniqueId`/`ChildUniqueId` against `rejectedSet`.
6. **Reason codes.** New: parser `AMBIGUOUS_REFERENCE` (a `ref`/`source` or child matches more than one node), ingestion `AMBIGUOUS_MODEL` (legacy name lookup). Parser `UNKNOWN_MODEL` when the resolver finds no node (same code as ingestion). Warnings keep the sanitized `Relation '..' (child -> parent) skipped: CODE` form with node names, no manifest free text.
7. **Source key tests (392a).** `CollectUniqueTest` falls back, when `attached_node` is empty, to the single `depends_on` node with prefix `model.`, `seed.`, `snapshot.` or `source.`; zero or more than one such node = no key plus warning `Key test '<test id>' skipped: AMBIGUOUS_ATTACHMENT`. `unique` and `unique_combination_of_columns` then land on the source via the existing key loop. Source `constraints` stay unsupported (dbt does not define them on sources).
8. **Multi-column relations (392b).** Accept a table-level generic test `relationships_combination` (default taken: the issue's first option) with kwargs `columns` (child, ordered), `to`, `fields` (parent, ordered) and optional `relation_name`. Arrays via `ReadKeyArray` (bounded at `MaxKeyColumns + 1`); validation through `RelationCollector.TryAdd` (`COUNT_MISMATCH`, `DUPLICATE_COLUMN`, `TOO_WIDE`, `MISSING_COLUMNS`, `INVALID_IDENTIFIER`); a non-array `columns`/`fields` or non-string `to` = `UNSUPPORTED_FORM`. Without `relation_name` the default name applies, so a combination test and a single-column test on the same pair collide and the existing grouping skips both with `DUPLICATE_RELATION` (fail closed, documented in the warning). `dbt_constraints.foreign_key` is a follow-up candidate, not in scope.
9. **Relation columns in describe_dataset (392c).** `GraphQlRelationMapping` gains `IReadOnlyList<string> Columns, IReadOnlyList<string> TargetColumns` (from `ParentColumns`/`ChildColumns`); `McpGraphQlRelation` gains `IReadOnlyList<McpRelationColumnPair>? Columns = null` with `McpRelationColumnPair(string Column, string TargetColumn)` (catalog column names, ordered). New `src/Autheris.Application/Mcp/Services/McpRelationColumnProjector.cs` decides per relation: pairs only when every own column is in the caller's listed columns of the described table and every target column is in the target's visible row columns (`ICatalogVisibilityService.FindVisibleAsync`, Full shape only; bypass: metadata repository), OrdinalIgnoreCase. Otherwise `Columns = null`: the pairs are dropped as a whole (never a subset, same rule as `TableKeyVisibility`), the relation entry itself stays as today (target-visibility gate unchanged). One lookup per distinct visible target. `McpDatasetCatalog.GraphQlAccessAsync` delegates; net line count of `McpDatasetCatalog.cs` must not grow.
10. **Schema impact: none.** `TABLE_RELATIONS` and its key-pair rows already hold ordered multi-column keys (#151); no governance table, column or index changes, so no migration step under the #388 migration framework. Contract changes are additive in-memory records and one additive JSON field (`columns`) in the `describe_dataset` output.
11. **Known limitation (not changed).** Source tables are registered under `name`, not the dbt `identifier`; changing that alters table identity and belongs to a separate issue.

## Phase 3 binding conditions (csharp-security-expert, 2026-10-30)

Verdict: APPROVED WITH CONDITIONS. Principles: ambiguity fails closed (wrong parent/child = wrong join exposure); describe_dataset reveals no column or relation the caller cannot see (all-or-nothing, like `TableKeyVisibility`); tenant filter on unique ids; bounded manifest work.

Rulings: Q1 keep the relation entry with `Columns = null` (existing target-visibility gate unchanged, no regression; null = "not disclosed", never an empty or partial list). Q2 no `ownerPackage` narrowing (see SC-02). Q3 self relation allowed only under the evidence rule in SC-04. Q4 pairs only if every target column passes the same column filter (including `Deny`) that `describe_dataset` applies to the target's own column list; otherwise drop all pairs. Q5 require namespace null or the project's own package, else `UNSUPPORTED_FORM`.

Binding conditions:
- I392-SC-01: The resolver returns `Resolved` only for exactly one candidate. Zero = `Unknown`, more than one = `Ambiguous`; both skip the relation with the sanitized warning. No first-wins, last-wins or name fallback anywhere (parser, lookup, ingestion).
- I392-SC-02: Order is `depends_on` candidates, then the global index, with no package narrowing. An explicit package argument in `ref('pkg','m')` is a filter, not a tiebreaker. Any residual multiplicity across packages = `AMBIGUOUS_REFERENCE`. Decision 1 is amended accordingly.
- I392-SC-03: With `attached_node` set, child must be that unique id and in the index; a `depends_on` mismatch (attached node missing from `depends_on`) = skip `UNKNOWN_MODEL`. Parent and child unique ids must both be set for the unique-id path; a null id never falls through to name matching except via the explicit legacy path of Decision 5.
- I392-SC-04: Self-relation inference only when the deduplicated `depends_on` holds exactly one eligible node equal to the resolved parent and `attached_node` is empty; any other shape with no single distinct child = `AMBIGUOUS_REFERENCE`. Source key fallback (Decision 7) uses the same exactly-one rule.
- I392-SC-05: `McpRelationColumnProjector` emits pairs only if all own columns are in the caller's listed columns of the described table and all target columns pass the target's column visibility incl. `Deny` and the row-shape requirement; otherwise `Columns = null` for the whole relation. Lookup failure, exception or missing target = null (fail closed). Pairs are catalog names only, never values, and not written to logs or audit.
- I392-SC-06: The relation entry gate (target visibility) must be evaluated before and independently of column projection; the projector must not widen what the gate hides. Bypass path (metadata repository) must be limited to the same authorization the existing bypass uses.
- I392-SC-07: Tenant filter checks `ParentUniqueId` and `ChildUniqueId` against `rejectedSet` in addition to names; a relation touching a rejected tenant node is dropped, and the drop reason must not name the other tenant's node.
- I392-SC-08: `relationships_combination` accepts namespace null or the project's package only; other namespaces = `UNSUPPORTED_FORM`. Array reads bounded by `MaxKeyColumns + 1`; `depends_on` iteration capped (reuse existing manifest list bound); resolver index capacity bounded by the existing node limit; `PendingRelation` counted at collection (Decision 2) and memory-bounded by `MaxRelations`.
- I392-SC-09: Warnings and reason codes use node names and codes only; no raw `to` expression, test kwargs or manifest free text. `describe_dataset` JSON gains only `columns`; nothing else changes.

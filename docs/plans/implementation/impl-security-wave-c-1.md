## 2. Work packages

### WP-SEC1-01: Stop unauthenticated request noise from entering the audit chain (SR-L-01)

- **Goal:** Requests that match no endpoint (`endpoint == null`) or that fail with non-auth 4xx must never produce a `TABLE_QUERY`/`ALLOW` row with a client-chosen target.
- **Design:**
  - In `AccessAuditMiddleware.FinalizeAuditAsync` (`src/Autheris.Api/Middleware/AccessAuditMiddleware.cs`), add an early branch after the exemption check: when `endpoint == null && statusCode < 500 && statusCode is not (401 or 403 or 429)` (typically 404/405/400 from the router), do not call `RecordAuditEventAsync`. Instead increment a new counter `GatewayDiagnostics.UnroutedRequestCounter` (`Autheris.Domain.Diagnostics`, tagged with status code and channel, no path tag to avoid cardinality blowup), emit a sampled `LogInformation` with the truncated path, and call `auditContext.MarkHandled()`.
  - Important constraint found in code: `PostgreSqlGovernanceRepository.RecordAuditEventAsync` (`...Audit.cs:24-36`) treats every event type other than `TABLE_QUERY`/`WEBSQL_QUERY` as Tier-A (synchronous, lock-serialized). A new event type for unrouted requests would therefore make flooding worse. Hence "do not persist" rather than "persist under a new type".
  - 401/429 keep the existing `IAuthFailureAggregator` path (aggregated, not persisted individually). 403 stays a DENY row (authenticated and routed).
  - For all remaining persisted rows cap `TargetTable` at 256 characters (`Truncate(target, 256)`), including `endpoint != null` rows with attacker-influenced path parameters.
  - Authenticated requests to unrouted paths follow the same rule (no per-request chain row); the counter plus log is sufficient and avoids authenticated flooding as well.
- **Affected files:** `src/Autheris.Api/Middleware/AccessAuditMiddleware.cs`, `src/Autheris.Domain/Diagnostics/GatewayDiagnostics.cs` (new counter), `tests/Autheris.Tests.Unit/Audit/AccessAuditMiddlewareTests.cs`, `tests/Autheris.Tests.Integration/AuditEndpointCoverageTests.cs` (verify it does not assume a row for unrouted paths).
- **Migration/compat:** Behavioural change: audit trail no longer contains rows for 404/405 on unrouted paths. No schema or config change. Documented in `docs/features` audit page by Phase 6. Dashboards/alerts that counted these rows should switch to the new counter.
- **Security (fail-closed):** Applies only to responses the router itself produced with no endpoint; any exception path (`exceptionOccurred`) and any 5xx keep the existing audit behaviour; failure of the audit write for non-DENY still rethrows (unchanged).
- **TDD:** `AccessAuditMiddlewareTests` (unit). Red test first: `InvokeAsync_UnroutedAnonymous404_DoesNotRecordTableQueryAllow` (endpoint null, status 404, repository mock must receive no call). Then `InvokeAsync_RoutedEndpoint404_StillRecorded`, `InvokeAsync_LongPath_TargetCappedTo256`, `InvokeAsync_Unrouted401_UsesAggregatorOnly`, `InvokeAsync_UnroutedException_StillRecordsError`.
- **Acceptance:** Scanner traffic to random paths produces zero audit chain rows and increments `UnroutedRequestCounter`; no persisted row has `TargetTable` longer than 256; existing audit tests stay green.
- **Effort:** S. **Risk:** Low (hot file `AccessAuditMiddleware.cs`, but isolated).

### WP-SEC1-02: Host filtering and CSRF origin check against an allow-list (SR-L-02)

- **Goal:** Close DNS-rebinding against Development anonymous modes, MCP developer CORS and intranet deployments by validating `Host` and not treating `Origin == Host` as proof of same-origin.
- **Design:**
  - Add `List<string> AllowedHosts { get; init; } = []` to `HostingLimitsOptions` (`src/Autheris.Domain/Options/GatewayOptions.cs:376`), bound as `Gateway:Hosting:AllowedHosts`. Entries: exact host (`gateway.corp.example`), `host:port`, or `*.suffix` wildcard (the ASP.NET `HostFilteringOptions` syntax).
  - In `GatewayServiceCollectionExtensions` (`src/Autheris.Api/Extensions/GatewayServiceCollectionExtensions.cs`) configure `HostFilteringOptions` from the list: `AllowedHosts` = configured list; if empty and `IsDevelopment()` use the loopback set (`localhost`, `127.0.0.1`, `[::1]`, `*.localhost`); `AllowEmptyHosts = false`; `IncludeFailureMessage = false`.
  - In `UseGatewayPipeline` (`GatewayApplicationBuilderExtensions.cs`) call `app.UseHostFiltering()` directly after `UseForwardedHeaders()` (so that, with `ReverseProxy.Enabled`, the forwarded host is what is validated) and before the CORS/CSRF middleware. If the generic host already inserted its own host filter from the `AllowedHosts` config key, ensure the two are consistent (do not set the `AllowedHosts` configuration key; use only `HostFilteringOptions`, and add a pipeline test to guard against double registration).
  - CSRF origin check (`GatewayApplicationBuilderExtensions.cs`, `isOriginTrusted` block ~line 220): replace `originUri.Authority == Request.Host.Value` with a check of `originUri.Authority` against the same allow-list (via a small `HostAllowList.IsAllowed(string authority)` helper shared with the host filter options, so both use one matcher), retaining `GraphQL.TrustedOrigins`. Since `Request.Host` is already validated by host filtering, an attacker's rebound domain no longer matches.
  - `GatewayStartupValidator` (`src/Autheris.Api/Extensions/DependencyInjection/GatewayStartupValidator.cs`): outside Development, empty `AllowedHosts` fails startup with an actionable message (fail-closed).
  - Health probes: Kubernetes/compose probes send the pod IP as `Host`. Either exempt `/health*` paths from host filtering (preferred: small pre-filter branch) or require operators to list probe hosts; document in Helm values (`deploy/helm`).
- **Affected files:** `src/Autheris.Domain/Options/GatewayOptions.cs`, `src/Autheris.Api/Extensions/GatewayServiceCollectionExtensions.cs`, `src/Autheris.Api/Extensions/GatewayApplicationBuilderExtensions.cs`, `src/Autheris.Api/Extensions/DependencyInjection/GatewayStartupValidator.cs`, `deploy/helm/**/values.yaml` and `deploy/compose/**` (add hosts), `src/Autheris.Api/appsettings.Development.json` if present.
- **Migration/compat (BREAKING):** Production deployments must set `Gateway:Hosting:AllowedHosts` or the gateway refuses to start. Development accepts only loopback host names by default; docker-compose/WSL setups using other host names (for example `gateway:8080`) must add them. Wire into Helm values and quickstart docs.
- **Security:** Empty list outside Development is a startup failure, not "allow all". Wildcard-only entry `*` is rejected outside Development by the validator.
- **TDD:** `tests/Autheris.Tests.Unit/Security/HostFilteringTests.cs` (WebApplicationFactory-free: build a `TestServer` host with `UseGatewayPipeline`; check existing `GatewayApplicationBuilderExtensions` tests for a reusable harness). Red test first: `Request_WithUnlistedHost_Returns400`. Then `Csrf_OriginEqualsHostButHostNotAllowed_Rejected`, `Csrf_OriginInAllowList_Accepted`, `Development_EmptyList_AllowsLoopbackOnly`, `StartupValidator_NonDevelopmentEmptyAllowedHosts_Fails`, `HealthEndpoint_UnlistedHost_StillServed`.
- **Acceptance:** Rebinding simulation (Host and Origin both `evil.example`) is rejected with 400; production start without list fails; OData `@odata.context` links can only contain allow-listed hosts.
- **Effort:** M. **Risk:** Medium (deployment breaking; shared hot file `GatewayApplicationBuilderExtensions.cs`).

### WP-SEC1-05: Access-plan confirmer binding, bounded and shared plan state (SR-L-06)

- **Goal:** Apply is bound to the confirming administrator, plan state is bounded and TTL-limited, and (when a cluster state provider is configured) shared across nodes with a shared signing key. Remove the demo directory outside Development.
- **Design:**
  - **Part A (no dependency, do first):** In `AccessPlanningService.ApplyAccessAsync` compare `stored.AdminSid` with `adminSid` (same `SecurityException` as confirm) and compare `stored.TenantId` with the caller `tenantId` when both are set (SR-H-02 consistency). Bind the token to the admin by parsing `adminSid` out of the signed payload (`{planId}:{adminSid}:{unix}` already contains it; `ValidateConfirmationToken` currently ignores it) and requiring equality with the caller. Replace the string-concatenated payload with a length-prefixed or `|`-free encoding to avoid ambiguity when the SID contains `:`.
  - **Part B (bounded state):** Introduce `AccessPlanOptions` under `Gateway:Governance:AccessPlanning` (`MaxPendingPlansPerAdmin` default 20, `PlanTtlMinutes` default 10, `ConfirmationTokenTtlMinutes` default 10, `SweepIntervalSeconds` default 60) in `src/Autheris.Domain/Options/`. Prune expired `_plans` entries opportunistically on `PlanAccessAsync` and on a periodic sweep; evict consumed-token entries when their plan expires; reject with `SecurityException` above the per-admin cap.
  - **Part C (shared state):** Extract `IAccessPlanStore` (`Autheris.Application/Governance/Interfaces`) with `SaveAsync(planId, StoredPlan, ttl)`, `TryGetAsync`, `TryMarkTokenConsumedAsync(token, ttl)` (atomic `SET NX`), `CountByAdminAsync`. Implementations: `InMemoryAccessPlanStore` (current behaviour, bounded) and `ClusterAccessPlanStore` built on `IDistributedClusterStateProvider` (the same abstraction as `ClusterTotpSecretStore`). Derive the confirmation HMAC key from `IKeyVaultSecretProvider` via HKDF (reuse the audit/HitL derivation pattern from SR-M-03) with a per-process random fallback only when no secret provider is configured and the deployment is single-node (in-memory store); a clustered store without a resolvable signing key fails startup. TTL and absent-vs-unavailable semantics of the cluster provider are owned by Architecture R0+R2 (ARC T5 / "access plan/token TTLs"); this WP must consume that contract and must not invent its own, so Part C is scheduled after that contract lands and is the only part with that dependency.
  - **Part D:** `ResolvePrincipalAsync`: gate `DefaultDirectory` behind `IHostEnvironment.IsDevelopment()` (inject `IHostEnvironment` or an options flag `AllowDemoDirectory`), and replace the hard-coded `sales.public.orders` owner lookup by an empty list outside the demo path (or a real directory port, out of scope; decision D3).
- **Affected files:** `src/Autheris.Application/Governance/Services/AccessPlanningService.cs`, new `IAccessPlanStore.cs` and two implementations, `src/Autheris.Application/Governance/AccessPlanningServiceCollectionExtensions.cs`, `src/Autheris.Domain/Options/GatewayOptions.cs` (or a new options file), `src/Autheris.Api/Endpoints/GovernancePlanEndpoints.cs` and `AdminMcp` callers (check `Mcp/Services` for `admin_plan_access`).
- **Migration/compat:** Part A/B/D: in-flight plans do not survive restarts (already true). Part C: multi-node deployments gain cross-node confirm/apply; tokens issued before an upgrade are invalid after it (10-minute lifetime, acceptable). Production clustered mode requires a resolvable signing secret (new startup validation). No schema change.
- **Security:** Apply fails closed on any mismatch (admin, tenant, token, TTL); atomic token consumption in the cluster store; unavailable cluster store means deny (not allow) per the R0+R2 contract.
- **TDD:** `tests/Autheris.Tests.Unit/Mcp/AdminMcpTwoPhaseTests.cs` (extend) and new `Governance/AccessPlanStoreTests.cs`. Red test first: `ApplyAccess_TokenFromDifferentAdmin_Throws` (plan by admin A, confirm by A, apply with B and the leaked token). ### WP-SEC1-06: Optional fail-closed token revocation lookup (SR-L-10)

- **Goal:** Operators can choose to deny rather than accept requests when revocation status cannot be determined because Redis is unreachable.
- **Design:**
  - Add `bool FailClosedOnRevocationLookupError { get; init; }` and `[Range(0,3600)] int RevocationLookupGraceSeconds` to `RedisOptions` (`GatewayOptions.cs:732`), bound as `Caching:Redis:FailClosedOnRevocationLookupError`. Default: `true` outside Development (resolved in `GatewayStartupValidator`/options post-configure from the environment), `false` in Development/Test. Review whether to default to `true` everywhere (decision D2).
  - Add `TokenRevocationUnavailableException : Exception` in `src/Autheris.Application/Interfaces/ITokenRevocationService.cs` (documented on the interface). `RedisTokenRevocationService.IsRevokedAsync` (`:131-189`): when fail-closed is on and (`!_multiplexer.IsConnected` or any per-key lookup faults or the outer catch fires), throw `TokenRevocationUnavailableException`; if the token's `iat` is within the grace window and the local layer has no hit, allow (token younger than grace cannot have been revoked on another node before the outage began, an approximation controlled by the option). ### WP-SEC1-07: Audit chain integrity latch, anchor monotonicity residuals, legacy HMAC removal (SR-L-07 residual, SR-L-08, SR-L-09)

- **Goal:** (a) A detected chain violation permanently latches the repository (until restart/explicit operator action) and blocks both tiers according to a configurable policy; (b) anchor stores can never go backwards on any backend; (c) the public legacy HMAC key is removed.
- **Design:**
  - **SR-L-08 latch.** In the three `*GovernanceRepository.Audit.cs` files separate the two states: `_isAuditPipelineFaulted` (write failure, recoverable) and `_auditChainViolation` (integrity, latched). Never clear the latter. The recovery code (`:132-135` PostgreSQL, `:126-129` SQL Server, `:151-155` SQLite) is unchanged but must only reset the write-failure flag; remove `_isAuditPipelineFaulted = true` from `FlagAuditChainViolation` in PostgreSQL/SQL Server (the violation field alone represents the state) so recovery cannot mask it. Admission in `RecordAuditEventAsync` checks the property `IsAuditPipelineFaulted` for Tier-B (line 44/38/45) and, for Tier-A, checks `_auditChainViolation` according to policy.
  - New option `AuditOptions.OnChainViolation` enum `{ DenyDataAccess, DenyAll, AlertOnly }` (`src/Autheris.Domain/Options`), default `DenyDataAccess` outside Development and `AlertOnly` in Development/Test. `DenyDataAccess`: Tier-B (query) events throw `InvalidOperationException("... integrity violation (fail-closed)")` which already fails the data request closed; Tier-A security and admin events keep being written (so the incident and the operators' actions are recorded) but each carries a `chainViolation=true` detail. `DenyAll` rejects both. Emit one `AUDIT_PIPELINE_FAULT` event per latch. Operator recovery is by restart after forensic review (documented), not by an endpoint, to avoid a new privileged attack surface.
  - SQLite: `FlagAuditChainViolation` (`:1037-1043`) must also be observed by admission (covered by checking the property).
  - **SR-L-07 residual.** In `SqliteGovernanceRepository.Audit.cs:276-280` and `:442-446` apply the same guard as PostgreSQL (`TryLoadVerifiedAnchor` then save only if `current == null || current.Sequence < anchor.Sequence`). In `FileAuditChainAnchorStore.Save` (`AuditChainAnchorStores.cs:57-85`) read the current file under the existing `_ioLock` and refuse (no-op, return) a lower sequence; for cross-process replicas on a shared path take an OS-level advisory lock (`FileStream` with `FileShare.None` on a sibling `.lock` file) around read-compare-write, since the in-process `lock` does not cover other replicas. `InMemoryAuditChainAnchorStore` gets the same monotonic check. `WormDirectoryAuditChainAnchorStore` is append-only by name and already picks the maximum on read (lines 161-190), no change.
  - **SR-L-09.** Delete the constant fallback in `SqliteGovernanceRepository.Audit.cs:~705`. Provide a one-time migration step instead: at startup, when NULL-`seq` rows exist and `Audit:AllowLegacyUnsequencedRows` is true (default false), re-seal them under the real key (HKDF-derived audit key) assigning sequence numbers in rowid order, record the boundary in the signed anchor, then verification requires `seq` on every row. If the flag is false and unsequenced rows exist, flag a chain violation (fail-closed) and log the operator instructions. Do this inside the existing `_lock` and in a single transaction, with a backup copy of the table (`AUDIT_LOG_ENTRIES_legacy_backup`) so the change is reversible.
- **Affected files:** `src/Autheris.Infrastructure/Persistence/PostgreSqlGovernanceRepository.Audit.cs`, `SqlServerGovernanceRepository.Audit.cs`, `SqliteGovernanceRepository.Audit.cs`, `AuditChainAnchorStores.cs`, `src/Autheris.Domain/Options/GatewayOptions.cs` (AuditOptions), `src/Autheris.Domain/Audit/AuditCanonicalizer.cs` (no change expected), `src/Autheris.Infrastructure/Health/GatewayHealthCheckService.cs` (include the policy in the readiness message). The Architecture R0+R2 "audit contract T2" scope also touches these repositories (batch/outbox contracts); sequence this WP after, or coordinate file ownership with, that work (see section 4).
- **Migration/compat (BREAKING):** (1) Existing SQLite files with legacy unsequenced rows now require the one-time migration flag or the gateway reports a chain violation at startup. (2) Default `DenyDataAccess` outside Development changes runtime behaviour on a detected violation: previously the gateway kept serving, now sensitive queries fail until investigation and restart. Provide `AlertOnly` as an explicit opt-out. PostgreSQL/SQL Server need no schema change; the SQLite migration adds a backup table only.
- **Security:** Violation state is monotonic for the process lifetime; anchors never regress; no compile-time key remains in the repository.
- **TDD:** `tests/Autheris.Tests.Unit/Audit/` (existing audit chain/anchor tests live here and in `ConcurrencyAndAuditReplicationTests.cs`, `AuditWormExportTests.cs`). New: `AuditChainViolationLatchTests.cs`, `AnchorStoreMonotonicityTests.cs`, `SqliteLegacyAuditMigrationTests.cs`. Red tests first: `TierB_AfterViolationFlagged_AndSuccessfulBatch_StillRejected` (theory over SQLite, PostgreSQL-fake, SQL Server-fake where unit-testable; else integration with containers in `Autheris.Tests.Integration`), `FileAnchorStore_Save_LowerSequence_IsIgnored`, `Sqlite_OnTransactionCommitted_DoesNotRegressAnchor`, `Sqlite_Verify_NullSeqRowSealedWithPublicConstant_Fails`, `Sqlite_LegacyMigration_ResealsAndRecordsBoundary`, `OnChainViolation_AlertOnly_AllowsQueries`, `OnChainViolation_DenyAll_RejectsTierA`.
- **Acceptance:** After a detected tamper, a subsequent successful batch does not re-enable query admission; the constant `"AutherisAuditLogHmacTamperEvidenceSecret2026!"` no longer exists in the source tree (grep gate in an architecture test); anchor sequence is monotonic across stores and replicas in tests.

### WP-SEC1-08: Tenant binding for SQL-channel virtual filters (SR-L-11)

- **Goal:** The predicate injected into WebSQL/REST/OData by structured and SQL-defined virtual filters restricts every tenanted source table to the caller's tenant, matching the federation key query.
- **Design:**
  - Share the tenant-column resolution used by `SqlVirtualFilterKeySetProvider.cs:218` (`TableMetadata.RequireTenantColumnOrThrow(metadata, dataSources.RequireTenantColumn, dataSources.TenantColumnExemptTables)`) through a new `VirtualFilterTenantColumns.Resolve(definition, catalog, options)` returning `IReadOnlyDictionary<string,string>` (alias to column), reused by the key query builder to remove duplicated logic.
  - `StructuredFilterSqlBuilder.Build` and `BuildTyped` take the tenant columns by alias and the caller tenant (through `FilterBinding` or the existing builder context; inspect `IVirtualFilterPredicateBuilder` and `MandatoryRowFilterResolver` for the cleanest carrier). Emit `alias.tenantcol = <tenant>` per tenanted alias: textual path uses a bound parameter name `@vf_tenant` (consistent with `StructuredFilterKeyQueryBuilder.TenantParameter`) registered with the existing parameter list; typed path uses a `PolicyPredicate` parameter named `{parameterPrefix}tenant`. If a tenanted table has no resolvable tenant column and `RequireTenantColumn` is on, throw (fail closed), same as the key query path.
  - `SqlFilterCompiler.Validate` (`SqlFilterCompiler.cs:124-139`): replace "column referenced" with "column compared for equality with the gateway-bound tenant parameter". Concretely require the filter SQL to contain a predicate `alias.<tenantcol> = :tenant` (a reserved parameter name accepted by the parser) in a conjunctive position; at compile time the gateway binds it to the caller's tenant. Resolve the column via `RequireTenantColumnOrThrow`, not the literal `tenant_id`/`tenantid`. Filters that already compare a literal or another column fail validation with a message explaining the reserved parameter.
  - Existing stored SQL-defined filters that do not meet the new rule are reported by a validation endpoint/lint (reuse the filter lint path in `SqliteGovernanceLintSource`) and fail at compile (deny, not skip).
- **Affected files:** `src/Autheris.Application/VirtualFilters/StructuredFilterSqlBuilder.cs`, `SqlFilterCompiler.cs`, `Federation/StructuredFilterKeyQueryBuilder.cs`, `Federation/SqlVirtualFilterKeySetProvider.cs`, `IVirtualFilterPredicateBuilder`, `src/Autheris.Application/Sql/Policy/GovernancePolicyFactory.cs` (where `BuildTyped` is consumed), `tests/Autheris.Tests.Unit/VirtualFilters/*`.
- **Migration/compat (BREAKING for stored filters):** SQL-defined virtual filters whose source tables carry a tenant column must reference the reserved tenant parameter; otherwise they are rejected at validation/compile time. Structured filters need no change in definition (the predicate is added automatically). Needs release note and a lint pass over catalogs before rollout.
- **Security:** Parameterized only; tenant from the resolved `SecurityPrincipalContext`, never from the filter text; fail-closed on unresolved tenant column when required.
- **TDD:** `tests/Autheris.Tests.Unit/VirtualFilters/StructuredFilterSqlTests.cs` (extend), `SqlFilterDefinitionTests.cs`, `TypedVirtualFilterTests.cs`. - **Effort:** M. **Risk:** Medium (typed AST path and parameter plumbing; affects every virtual-filtered query).

### WP-SEC1-09: Catalog-driven masking of federated subgraph results (SR-L-12)

- **Goal:** Subgraph result masking follows catalog classification instead of only a field-name denylist; the heuristic remains as a secondary layer.
- **Design:**

Subgraphs do not expose catalog tables directly, so matching is by normalized field name (`taxNumber` ~ `tax_number`); an explicit config map `Federation:FieldClassifications` (`subgraph.type.field` to rule type) covers non-matching names and takes precedence.

Add `Federation.DefaultMaskUnknownSensitiveScalars` (default false for compatibility; true recommended) which masks scalar fields whose type name is in a configured sensitive-type list.

## 5. Open decisions requiring stakeholder input

- **D1: Host allow-list behaviour (WP-SEC1-02).** Fail startup in production when `AllowedHosts` is empty (recommended) versus warn only. Also whether `/health*` is exempt from host filtering (recommended: yes). Development default: loopback names only (recommended).
- **D2: Revocation fail-closed default (WP-SEC1-06).** Recommend default `true` outside Development with a 60-second grace window, accepting 503s during Redis outages; alternative is `false` by default with a documented warning (availability over security).
- **D3: Principal resolution outside Development (WP-SEC1-05 Part D).** Return an empty directory (recommended, minimal) versus implementing a real directory port backed by IdP/Graph (out of scope, would need a feature item).
- **D4: Response to a detected audit chain violation (WP-SEC1-07).** Recommend `DenyDataAccess` by default outside Development (Tier-B refused, Tier-A still written with a violation marker), recovery by restart after review. Alternatives: `DenyAll` (strictest, can lock out admins) or `AlertOnly` (current behaviour). Also whether to auto-migrate legacy SQLite rows (recommended: only with explicit `Audit:AllowLegacyUnsequencedRows=true`, default off).
- **D5: Federated masking strategy (WP-SEC1-09).** Name-based catalog mapping with explicit config overrides (recommended), versus requiring subgraph schemas to carry `@sensitive`-style directives, which is more precise but needs a federation contract change. Also whether to enable `DefaultMaskUnknownSensitiveScalars` by default (recommend yes for new installations, off for upgrades).
- **D6: SQL-defined filter migration (WP-SEC1-08).** Hard reject of existing filters that lack the reserved tenant parameter (recommended, fail-closed) versus a one-release deprecation window with a warning; the latter keeps a known cross-tenant gap open for a release.
- **D7: Unrouted-request telemetry (WP-SEC1-01).** Counter plus sampled log (recommended) versus a rate-limited single aggregated audit row per source IP per interval via `IAuthFailureAggregator`; the latter adds forensic value but needs a new aggregator method and a new event type.

### Wave R1 - unified governed query pipeline

#### WP-ARC-B-01 - Shared governed table-read planner (extract from `GovernedDataQueryService`)

- **Covers:** ARC-C-01 (foundation), ARC-G-07 (data side).
- **Goal:** one reusable component that turns a table-read intent (table, columns, filter, order, limit/offset) plus a `TableAccessDecision` into Trino-dialect SQL text with client parameters and runs it through `IGovernedSqlExecutionService` (Compile + binder). `GovernedDataQueryService.ExecuteQueryAsync` (`Application/Data/Services/GovernedDataQueryService.cs:65-260`) is already the working reference (REST datasets); extract its steps 3-5 (column authorization, oracle-inference guard on filter/order columns, SQL formulation) into a service the other adapters call.
- **Design:**
  - New `Autheris.Application/Data/Services/GovernedTableReadPlanner.cs` with `IGovernedTableReadPlanner.Plan(TableReadIntent, TableMetadata, TableAccessDecision) -> PlannedTableRead(Sql, Parameters, ColumnsToSelect)`. `TableReadIntent` carries: `SelectColumns`, a neutral `TableFilterExpression` (see below), `OrderBy`, `Limit`, `Offset`, `Transport`.
  - Neutral filter: add `TableFilterClause.GetTrinoPredicate()` (Trino syntax, named client parameters `:name`) next to the dialect-specific `GetSqlPredicate(dialect)`; `ODataFilterParser` (`Extensions/OData/ODataFilterParser.cs:21-50`, already builds a `SqlGenerationContext` per dialect) gets a Trino `SqlGenerationContext`. `DataApiFilterTranslator.TranslateFilterToTrino` already exists for REST. Values never enter the text; they travel as `GovernedSqlQueryRequest.Parameters`.
  - Pagination: emit the Trino `OFFSET n LIMIT m` form that the AST compiler translates per dialect (capability `PaginationStyle`), and delete the in-memory skip described in the (now stale, pre-X1) comment at `GovernedDataQueryService.cs:~190-200`. Keep the window cap until the per-dialect integration tests in `tests/Autheris.Tests.Integration/AstCompiler*ExecutionTests.cs` cover OFFSET (feature hand-off, section 3.3).
  - `GovernedDataQueryService` is refactored to call the planner (behavior-preserving, existing tests stay green).
- **Affected files:** `Application/Data/Services/GovernedDataQueryService.cs`, new planner, `Application/Data/DataApiFilterTranslator*` (locate by name), `Application/Interfaces` (TableFilterClause home), `Extensions/OData/ODataFilterParser.cs`, DI in `Api/Extensions/DependencyInjection/GatewayExecutionServiceExtensions.cs`.
- **Compatibility/config:** none externally visible; no new options. The planner is internal infrastructure for WP-02.
- **Security (fail-closed):** column allow-list from the catalog (never from input), quoted catalog spellings, deny/mask columns rejected in filter and order (existing H-10/SEC-01 behavior preserved), every value a client parameter, unknown column or unsupported operator throws (no best-effort text).
- **TDD:** `GovernedTableReadPlannerTests` (Unit). Red test first: `Plan_FilterOnMaskedColumn_Throws` (moved from `GovernedDataQueryService` tests) and `Plan_ODataFilter_EmitsNamedParametersOnly` (assert no literal value in `PlannedTableRead.Sql`). Add parity theory: for each dialect in {SqlServer, PostgreSql, Sqlite, Oracle}, compile the planned SQL through `FastSqlEngine.Compile` and assert `CompiledSql.Parameters` contains every client value. Architecture guard: planner output is never passed to `DbCommand.CommandText` (extend `CutoverArchitectureTests`).
- **Acceptance:** `GovernedDataQueryService` has no SQL-formulation code; planner covered per dialect; no behavior change in REST dataset tests.
- **Effort:** M. **Risk:** low-medium (OData filter semantic parity: case-insensitive `contains`, `datetime` literals, `in`; mitigate with the existing OData filter test corpus run against both outputs).

#### WP-ARC-B-02 - Migrate GraphQL flat reads, OData, MCP query executor, connector SPI onto the governed pipeline; retire `SqlDataSourceExecutor`

- **Covers:** ARC-C-01 (main part), ARC-C-02 (SqlDataSourceExecutor), ARC-I-13 (`SqlConnector`), ARC-G-07 (partial, flat reads).
- **Goal:** SQL-source table reads no longer build SQL with `CombinedRowFilterSql`; they use WP-01's planner and `IGovernedSqlExecutionService`, so tenant, row policy, masks, limits and audit digest come from the single compiler path. Non-SQL sources (`DeclarativeHttpDataSourceExecutor`, `PluginHttpDataSourceExecutor`, Lakehouse) keep `IDataSourceExecutor` and the in-memory `InMemoryRowFilterEvaluator` (WP-04 hardens that).
- **Design:**
  - `GatewayExecutionService` (`Services/GatewayExecutionService.cs`, 693 LOC) routes by `metadata.DataSourceType`: SQL types -> new `ISqlTableReadExecutor` (Application, implemented over WP-01 + `IGovernedSqlExecutionService.ExecuteQueryBufferedAsync`); others -> existing executors. Result masking for the SQL branch is already applied inside the compiled SQL (`MaskSpec`); the post-hoc `IColumnMaskingProvider` call must be skipped for that branch to avoid double masking (assert with a test).
  - `SqlConnector` (`Infrastructure/Connectors/SqlConnector.cs:126`) and `BatchRelationLoader` stop instantiating/using `SqlDataSourceExecutor`; they receive `ISqlTableReadExecutor`. `IColumnMaskingProvider? maskingProvider = null` becomes required (ARC-I-13: a missing provider currently degrades HMAC pseudonymization to redaction).
  - Delete `SqlDataSourceExecutor{,.Projection,.Synthetic}.cs` SQL path; keep synthetic-data handling only if still referenced (decide during implementation; `Synthetic.cs` is 112 LOC). Remove `OracleBindByName.RewriteMarkers` (marker rewriting is now the compiler's job) and keep `Enable` for the binder (it moves with WP-09).
  - Remove `Autheris.Application.Services.SqlDataSourceExecutor` from `AllowedExceptionsOutsideCompile`; add `GatewayExecutionService.ExecuteQueryAsync` (SQL branch), `ODataHandler` entry method and `GatewayMcpQueryExecutor` to `GovernedEntryPoints` (`CutoverArchitectureTests.cs:493`).
  - GraphQL schema (ARC-G-07): `CatalogSchemaModel.cs:104-111` stops hard-coding three dialects for *flat* reads; tables on any admitted dialect (`SqlDialectMapper.IsExecutable`) are exposed. Tree (nested relation) support stays gated by WP-03/WP-09 capability `SupportsTreeCompile`, and excluded tables are logged once at schema build with the reason.
- **Affected files:** `Services/GatewayExecutionService.cs`, `Services/SqlDataSourceExecutor*.cs` (delete), `Services/BatchRelationLoader.cs`, `Infrastructure/Connectors/SqlConnector.cs`, `Extensions/OData/ODataHandler.cs`, `GraphQL/Types/QueryTypes.cs`, `GraphQL/Mcp/GatewayMcpQueryExecutor.cs`, `GraphQL/Catalog/CatalogSchemaModel.cs`, `Api/Extensions/DependencyInjection/GatewaySqlEngineServiceExtensions.cs:56-58` and `GatewayExecutionServiceExtensions.cs`, architecture tests. Test blast radius: 24 test files reference `SqlDataSourceExecutor`, 33 reference `GatewayExecutionService`.
- **Compatibility/config:** behavior changes to document in `docs/features/f-dialect-02-ast-sql-compiler.md` section 2.1 (exception list shrinks) and the release notes: (1) OData/GraphQL SQL reads now count against WebSQL-style compile limits (`CompileTimeout`, bind budget, function allowlist is not relevant since no user functions) and are subject to `SqlDialectMapper.IsExecutable` admission - a Databricks (Experimental) table that previously worked through `SqlDataSourceExecutor` returns the stable `SQL_DIALECT_NOT_SUPPORTED` error; (2) Oracle tables appear in GraphQL; (3) error shapes of the SQL branch use `SqlCompilerErrorMapper` codes. No option removals. Provide a one-release escape hatch? No: a second path is the defect being removed (see open decision D2).

Tenant column absence follows `RequireTenantColumnOrThrow` inside the compiler.
- **TDD:** Unit: `GatewayExecutionServiceSqlBranchTests`, `ODataHandlerGovernedPathTests`, `SqlConnectorRequiresMaskingProviderTests`. Red test first: `ExecuteQuery_SqlTable_DoesNotUseCombinedRowFilterSql` (architecture-level: Mono.Cecil call-graph assertion that `GatewayExecutionService` reaches `ISqlEngine.Compile` and the binder for SQL tables, using the existing scanner in `CutoverArchitectureTests`). Integration (existing `AstCompiler*ExecutionTests`/`EndToEndSqliteTests`): GraphQL and OData reads under tenant + row filter + mask on SQLite, PostgreSQL, SQL Server, Oracle containers; one differential test proving the migrated result set equals the pre-migration result for a frozen fixture (snapshot captured before deleting `SqlDataSourceExecutor`).
- **Acceptance:** no production class other than `GovernedSqlExecutor` assigns `DbCommand.CommandText` for governed reads (extend the existing guard); `AllowedExceptionsOutsideCompile` lacks `SqlDataSourceExecutor`; Oracle table queryable through GraphQL; all tests green.

  - **Audit failure semantics are NOT decided here.** The stage takes the audit contract from the R0+R2 T2 work (Tier-A fail-closed vs Tier-B channel). #### WP-ARC-B-04 - Single mask and row-filter semantics (ARC-C-12)

- **Covers:** ARC-C-12; closes the text-consumer exception list (OQ-4) semantically.
- **Goal:** one definition of mask kinds, null handling and canonicalization for SQL and in-memory sources, and in-memory row filters evaluated from the typed predicate, not from re-parsed SQL text.
- **Design:**
  - Golden corpus `tests/Autheris.Tests.Unit/Masking/MaskSemanticsCorpus.cs`: for every `MaskSpec` kind (`Nullify`, `Redact`, `PartialMask`, `Hmac`, `GeoJitter`, `Constant`) x value kinds (null, empty, unicode, numeric, date) the expected output, executed against `SqlDataMaskingProvider` (via compile + SQLite) and `ColumnMaskingProvider` (in-memory). Divergences found become bugs fixed in `ColumnMaskingProvider`, which is reduced to a thin evaluator of `MaskSpec` (no private mask semantics; `Services/MaskingInputCanonicalizer.cs` stays the single canonicalizer).
  - `InMemoryRowFilterEvaluator` (`Services/InMemoryRowFilterEvaluator.cs:48-63`, `ParseTuples` text parsing `:320`) evaluates `PolicyPredicate`/`IRowPolicy` (the typed tree, `Policy/PolicyPredicateRowPolicy.cs`, `Governance/CasbinEnforcementService.cs:~1037`) directly. Text path `CombinedRowFilterSql` remains only for the listed text consumers and is evaluated nowhere in memory.
  - Reject predicates containing nodes the evaluator does not implement (fail closed: deny all rows, log once), instead of the current text-normalization best effort (`NormalizeRowFilterForInMemoryEvaluation`).
- **Affected files:** `Services/ColumnMaskingProvider.cs`, `Services/InMemoryRowFilterEvaluator.cs`, `Sql/Masking/*`, `Policy/*RowPolicy*.cs`, consumers `GovernedConnectorReader.cs:115-187`, `GatewayExecutionService.cs:350-381`.

#### WP-ARC-B-14 - Governance stores per aggregate with shared dialect layer (ARC-I-01, ARC-L-03)

- **Covers:** ARC-I-01, ARC-L-03.
- **Goal:** stop the "one class, 13 interfaces, three dialect copies" shape; make consent and audit semantics a single implementation with thin per-dialect SQL.
- **Design (phased, each phase one PR, behavior-preserving):**
  1. Registration: `AddAutherisGovernance` (`GatewayGovernanceServiceExtensions.cs:37-83`) is replaced by a per-aggregate registration table; the façade class remains temporarily but each interface resolves through the per-aggregate store where it exists.
  2. Audit store first: `AuditStore` (chain hashing, anchor handling, channel writer, tail verification, `IAuditLogRepository`, `IAuditChainExportSource`, 3,162 lines across the three `Audit.cs` partials) extracted as Infrastructure-neutral logic `AuditChainEngine` (hash chain, anchor sequencing, key handling) plus `IAuditStoreDialect` (SQL text, parameter style, upsert/locking: PG `pg_advisory_xact_lock`, SQL Server `sp_getapplock`, SQLite writer lock). Chain semantics move once, tested once; **coordinate with Security Wave C SR-L-07/08/09, which modify these exact files** (section 3.2: land those first or fold them into phase 2).
  3. Consent store (`IConsentRepository`, `IConsentApprovalRepository`, state transitions in the three `Consent.cs`, 4,871 lines): consent state machine in a dialect-neutral class; `IConsentStoreDialect` for SQL.
  4. Catalog, outbox, tenant registry, virtual filters (smaller): split only when touched; same pattern.
  A shared `IGovernanceSqlDialect` supplies upsert, paging and boolean/timestamp fragments. A contract test suite (`GovernanceStoreContractTests<TFixture>`) runs the identical assertions against SQLite, PostgreSQL and SQL Server containers; this is the guarantee that three dialect implementations behave identically. Converging on Dapper/EF Core for the internal store is an option (open decision D5), not part of the plan baseline.
- **Compatibility:** no schema change (migrations from WP-12 unchanged), no config change; DI interfaces stay.
- **Security:** audit chain bytes and HMAC input format must remain identical (golden chain fixture produced by the old code and verified by the new engine); fail-closed behavior on chain violation (`_auditChainViolation`, `IsAuditPipelineFaulted`) preserved.
- **TDD:** `AuditChainEngineGoldenTests` (red test: verify a chain written by the pre-refactor code), `GovernanceStoreContractTests` x3 providers, `ConsentStateMachineTests`.
- **Effort:** XL (4 phases, 1 developer each phase is realistic). **Risk:** high; defer behind the others, and do not start before WP-12/13 are merged.

## 4. Recommended sequence

Phase 0 (parallel, no hot-file overlap, can start immediately):
- WP-ARC-B-05 (consent service, `MutationTypes.cs` only), WP-ARC-B-06 (MCP resources, `GatewayMcpServer.cs` + Mcp services), WP-ARC-B-08 (engine marker cleanup, `TrinoSqlEngine`), WP-ARC-B-12 (migrations; persistence-only files), WP-ARC-B-04 (mask and in-memory filter semantics; masking/connector files). Rationale: independent file sets, each unblocks later phases, and WP-12 has the highest value (compliance) and no code dependency.

Phase 1 (R1 core, serialized on `GatewayExecutionService`/DI files):
- WP-ARC-B-01 -> WP-ARC-B-03 -> WP-ARC-B-02 (02a, 02b, 02c sequentially). WP-03's stage helper is introduced before WP-02 so migrated adapters adopt it immediately. WP-ARC-B-07 can run in parallel with WP-02 after WP-01 and WP-03 (Api endpoint files only) but shares `GatewayExecutionServiceExtensions.cs` DI with WP-02 (small merge risk).

Phase 2 (R3 structure):
- WP-ARC-B-09 (after WP-02 and WP-08), in parallel WP-ARC-B-13 (after WP-12; SQLite persistence files only, no overlap with WP-09).
- WP-ARC-B-10 after WP-02 (DI files) and independent of WP-09 except `Autheris.Application.csproj`/DI; serialize with WP-09 if the same developer is not used (csproj and `GatewayExecutionServiceExtensions.cs`).

Phase 3:
- WP-ARC-B-14 (phases 1 to 4 sequentially; phase 2 only after Security Wave C audit fixes).
- WP-ARC-B-11 (folder moves) last, after a freeze of other PRs.

Parallelizable by independent developers: {05, 06, 08, 12, 04} at phase 0; {07, 13} alongside 02/09. Must be serialized: {01, 03, 02}, {09, 10, 11} (shared csproj/DI/namespace surface), {12, 13, 14} (same persistence files). Per team practice, parallel implementers do not build; the lead compiles and tests once per phase (Release, warnings as errors).

Wave exit criteria: R1 done when `AllowedExceptionsOutsideCompile` contains only `GovernedTreeQueryService` (documented), `FederatedStagingService`, `DuckDbOlapEndpoints`, `SqlConnector` (if still text-based) and each is covered by a parity test; R3 done when the package-boundary and constructor-I/O architecture tests pass with empty allow-lists and `autheris_schema_migrations` exists on all backends.

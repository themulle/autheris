## 1. Owner decisions (binding)

- OD-1 One documented behaviour per capability across WebSQL, GraphQL and REST.
- OD-2 SQL three-valued logic wherever it applies: `= NULL`, GraphQL `eq: null`, REST `eq null` give zero rows on every channel.
- OD-3 A client error is a stable 4xx with a catalogue code (`ApiErrorCodes`, `GovernedSqlErrorCodes`, GraphQL sanitizer whitelist), never a 5xx.
- OD-4 Advertised but unsupported items are rejected with a catalogue code or removed from the allowlist.
- OD-5 No internal parameter names, exception type names or engine messages in any error message (all environments, Development included).
- OD-6 Fail-closed security is never weakened: SQLA-06 tree rules, tenant/row policy, the bind-everything rule, SQ-01/SQ-02 lexer hardening, SEC-X1-05 anti-oracle, SEC-PAR-01..07.
- OD-7 Breaking changes are fine; no upgrade migrations.

1. **#304 GAP-013 portable date-part grouping (P1).** Behaviour: `EXTRACT(f FROM x)`, `year|quarter|month|day|hour|minute|second(x)`, `date_part('f', x)` and `date_trunc('unit', x)` work on every dialect, SQLite included. Root cause: WebSQL compiles in bound mode; `SqliteDialectGenerator.FormatExtract`/`FormatDateTrunc` throw `NoBoundForm` (422 `SQL_CONSTRUCT_NOT_SUPPORTED`); `year`/`date_part` are not in `SqlFunctionAllowlists.Sqlite`, and `date_trunc` is removed by `SqlFunctionAllowlists.WithoutDateTranslation` because `CompileRequestFactory` never sets `TranslateTrinoDateFunctions` (403 `SQL_POLICY_VIOLATION`). Change: (a) SQLite bound forms: the strftime format and the `datetime` modifier come from the generator's closed switch and are bound with `context.BindValue(value, SqlParameterType.String, ParameterOrigin.QueryLiteral)` (precedent: `AppendZoneArgument`), so no literal is emitted and the bind-everything rule holds; (b) `SqlAstBuilder` turns `year(x)`..`second(x)` and `date_part('<field literal>', x)` into `ExtractExpression` (field through `SqlSafeTokens.EnsureExtractField`; a non-literal field is `Unsupported`); (c) `CompileRequestFactory` sets `TranslateTrinoDateFunctions = true` for governed WebSQL (date_trunc/date_add/now become `DateFunctionExpression`; SQLite `FormatDateAdd` gets the same bound-modifier form). GraphQL `timeBuckets` (`GovernedTableReadPlanner`, string SQL) is not reused: the AST generators already own the per-dialect rendering. Red: `SqliteDialectTests.Extract_Bound_BindsFormatAndEmitsNoLiteral`, `.DateTrunc_Bound_Year_BindsModifier`, `.DateAdd_Bound_BindsModifier`; `SqlAstBuilderDatePartTests.YearFunction_BuildsExtract`, `.DatePart_NonLiteralField_IsUnsupported`; parity `Robin_Proactive_GroupByYearWebSql` (3 variants). Entries: `RobinKnownGaps` 5 x GAP-013; `MatrixKnownGaps["group_date_part_standard_sql|WebSql"]`; `DialectStructureTests` line 57 assertion. Default taken: the PostgreSQL pairwise WebSQL date-part cells are rendered with `EXTRACT` on every dialect and stop being Pending (WP-Z), so the dialect job checks portability.

### Binding conditions

- SEC-PG-01 (WP-A, #304) Every strftime format, `datetime` modifier and unit comes from a closed generator switch keyed by a validated enum (`SqlSafeTokens.EnsureExtractField`, fixed unit set), never from client text. They are bound via `BindValue(.., ParameterOrigin.QueryLiteral)`. A `date_add`/`date_trunc` amount is a bound numeric (integer-validated), combined with the unit by a generator-owned expression; a non-literal or non-numeric amount or unit is `Unsupported` (422), never concatenated.
- SEC-PG-02 (WP-A) The emitted SQL for every date-part, date_trunc, date_add and typed-literal form contains no string literal; the bound parameter count stays inside the existing parameter cap (a long chain of date functions cannot exceed it).
- SEC-PG-03 (WP-A) `TranslateTrinoDateFunctions = true` only for governed WebSQL and only restores the dialect's existing date allowlist entries (`date_trunc`, `date_add`, `now`); no other function is added. The allowlist stays deny-by-default per dialect; the non-governed/admin paths are unchanged (a test pins the allowlist set before/after).
- SEC-PG-04 (WP-A, #297) Typed DATE/TIMESTAMP literals bind the regex-validated, canonicalised value as a string parameter (`QueryLiteral`); an invalid value stays rejected with the existing code, with no echo of the submitted text in the message.
- SEC-PG-05 (WP-A, #309) Empty `IN ()`/`NOT IN ()` folds only after the left operand has been visited: the operand stays in the AST (or is visited by the security visitor) so denied, masked, unknown-column and required-filter checks still fire on it; the constant never replaces a row-policy or tenant predicate and is AND-ed like any predicate. The empty list is a literal AST token only; client list parameters (`IN (@ids)`) are unchanged and still count toward the existing IN-size bound.
- SEC-PG-06 (WP-B, #300) The null comparison is a typed bound NULL parameter (no `= NULL` text, no FALSE constant), so `not`/`or` stay 3VL. The comparison still goes through the tree column authorization, mask and required-filter paths; a required-filter column satisfied by `eq: null` returns zero rows and never skips the tenant/row predicate. `in: [null]` yields the empty-list result; `isNull: null` and `col: null` stay `INVALID_QUERY` with a fixed message.
- SEC-PG-07 (WP-B, #302/#301) `first: 0`/`limit: 0` costs as a minimum-priced bounded query, never as zero cost or skipped analysis. Authorization, masking, row policy and audit still run (or the plan is built and rejected exactly as for any N). ## WP-C implementation notes (2026-10-23)

Plan facts verified on `fix/parity-gaps-wp-c`; drift and deviations from the section 2 / section 3 design:

- 2026-10-23 #296 (SEC-PG-08): `LiteralTokenRejectedException` is not a `ParseCanceledException` subclass. It is the inner cause of the same `ParseCanceledException` the check sites threw before (`LiteralTokenRejectedException.Reject`). Reason: many existing security tests assert `Assert.Throws<ParseCanceledException>` (exact type) and match the old messages; a subclass would have broken them. The mapper matches the inner type only (rule before the syntax row), every other `ParseCanceledException` stays `SQL_SYNTAX_ERROR`. The `[`/`]` token rejection and the E'', UESCAPE, comment and `$$` rejections stay plain syntax errors (only literal/backslash check sites are typed).
- 2026-10-23 #310 (SEC-PG-09): the visitor had no column types, so `AstSecurityVisitorOptions.ColumnDataType` (optional lookup, table + column -> catalog `DataType`) is new; `GovernedSqlCompiler.BuildOptions` sets it (file outside the WP-C list, change is 12 lines). The guard is `AggregateTypeInvalidException` (code `AGGREGATION_INVALID_FUNCTION_FOR_TYPE`, 400 via the mapper), runs after the mask guards, only for a direct column argument listed in the catalog of a FROM table. A column absent from the catalog (unknown or denied), a derived-table column and a computed expression pass: the executor answers unknown/denied as before (SEC-X1-05) and no type is disclosed. A listed column with an unrecognised or missing type fails closed. The engine classifier `AggregateTypeClasses` mirrors `ColumnValueKinds` (pinned by `AggregateTypeClassConsistencyTests`) and additionally knows dialect numeric spellings that the catalog kinds treat as String (Oracle `NUMBER`, `BINARY_DOUBLE`, DuckDB `HUGEINT`, ...): without them the guard would reject valid Oracle sums (existing Oracle compile tests use `NUMBER(10)`). The GraphQL matrix still maps those to String (pre-existing gap, not changed here).
- 2026-10-23 #312 (SEC-PG-10): `DmlErrorSanitizer.Map` classifies unknown identifiers (SQL Server 207, Oracle 904, PostgreSQL 42703, SQLite code 1 + "no such column", DuckDB binder "not found" message, Databricks `UNRESOLVED_COLUMN`) as `GovernedSqlException(PolicyDenied)`; `SqlCompilerErrorMapper.MapGoverned` maps it to 403. DuckDB and Databricks have no numeric code, so their classification reads the provider message text (a client can only move a 502 to the equally harmless 403 by naming a column that way).
- 2026-10-23 #293 (SEC-PG-11): `WebSqlEndpoints.Execution.cs` writes `{ error: "BadRequest", code, message, traceId }` with `INVALID_JSON` / `MISSING_REQUIRED_FIELD`; the Trino header and the 2 MB size 400 bodies are unchanged (not in scope).

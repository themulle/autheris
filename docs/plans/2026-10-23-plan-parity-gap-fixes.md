## 1. Owner decisions (binding)

- OD-1 One documented behaviour per capability across WebSQL, GraphQL and REST.
- OD-2 SQL three-valued logic wherever it applies: `= NULL`, GraphQL `eq: null`, REST `eq null` give zero rows on every channel.
- OD-3 A client error is a stable 4xx with a catalogue code (`ApiErrorCodes`, `GovernedSqlErrorCodes`, GraphQL sanitizer whitelist), never a 5xx.
- OD-4 Advertised but unsupported items are rejected with a catalogue code or removed from the allowlist.
- OD-5 No internal parameter names, exception type names or engine messages in any error message (all environments, Development included).
- OD-6 Fail-closed security is never weakened: SQLA-06 tree rules, tenant/row policy, the bind-everything rule, SQ-01/SQ-02 lexer hardening, SEC-X1-05 anti-oracle, SEC-PAR-01..07.
- OD-7 Breaking changes are fine; no upgrade migrations.

## 2. Per-issue decisions (behaviour; root cause; change; red tests; parity entries)

Unit tests go to `tests/TrinoSqlEngine.Tests` (engine) or `tests/Autheris.Tests.Unit` (application, API, GraphQL); parity cells run with `AUTHERIS_PARITY_RUN=1` on the in-process SQLite host. A fixed gap shows as "PARITY-GAP-NNN is fixed: remove the KnownGap"; a fixed observed server error as "observed server error fixed, move the case back"; this is the expected green signal of a WP before WP-Z removes the entries.

1. **#304 GAP-013 portable date-part grouping (P1).** Behaviour: `EXTRACT(f FROM x)`, `year|quarter|month|day|hour|minute|second(x)`, `date_part('f', x)` and `date_trunc('unit', x)` work on every dialect, SQLite included. Root cause: WebSQL compiles in bound mode; `SqliteDialectGenerator.FormatExtract`/`FormatDateTrunc` throw `NoBoundForm` (422 `SQL_CONSTRUCT_NOT_SUPPORTED`); `year`/`date_part` are not in `SqlFunctionAllowlists.Sqlite`, and `date_trunc` is removed by `SqlFunctionAllowlists.WithoutDateTranslation` because `CompileRequestFactory` never sets `TranslateTrinoDateFunctions` (403 `SQL_POLICY_VIOLATION`). Change: (a) SQLite bound forms: the strftime format and the `datetime` modifier come from the generator's closed switch and are bound with `context.BindValue(value, SqlParameterType.String, ParameterOrigin.QueryLiteral)` (precedent: `AppendZoneArgument`), so no literal is emitted and the bind-everything rule holds; (b) `SqlAstBuilder` turns `year(x)`..`second(x)` and `date_part('<field literal>', x)` into `ExtractExpression` (field through `SqlSafeTokens.EnsureExtractField`; a non-literal field is `Unsupported`); (c) `CompileRequestFactory` sets `TranslateTrinoDateFunctions = true` for governed WebSQL (date_trunc/date_add/now become `DateFunctionExpression`; SQLite `FormatDateAdd` gets the same bound-modifier form). GraphQL `timeBuckets` (`GovernedTableReadPlanner`, string SQL) is not reused: the AST generators already own the per-dialect rendering. Red: `SqliteDialectTests.Extract_Bound_BindsFormatAndEmitsNoLiteral`, `.DateTrunc_Bound_Year_BindsModifier`, `.DateAdd_Bound_BindsModifier`; `SqlAstBuilderDatePartTests.YearFunction_BuildsExtract`, `.DatePart_NonLiteralField_IsUnsupported`; parity `Robin_Proactive_GroupByYearWebSql` (3 variants). Entries: `RobinKnownGaps` 5 x GAP-013; `MatrixKnownGaps["group_date_part_standard_sql|WebSql"]`; `DialectStructureTests` line 57 assertion. Default taken: the PostgreSQL pairwise WebSQL date-part cells are rendered with `EXTRACT` on every dialect and stop being Pending (WP-Z), so the dialect job checks portability.

### WP-B implementation notes (2026-10-23)

Deviations from section 2, items 7-9:
- The null operand is an untyped NULL parameter (`TreeComparison.BindNullOperand`); the compared column types it. `nin` drops null items like `in`; list operators with a bare `null` (`in: null`) are rejected with a fixed INVALID_QUERY message.
- A zero page is planned as `WHERE [(pred) AND] 1 = 0 ... LIMIT 1`, never `LIMIT 0`, so no dialect emits `FETCH NEXT 0 ROWS`; the tree compiler does the same for a zero root page on SQL Server. Authorization, masking and required-filter checks run as for any N.
- `GovernedDataQueryService` plans `limit + 1` (zero stays zero in the envelope, `HasMore` reflects the look-ahead row); `SqlTableReadExecutor` no longer rounds 0 up to 1.
- Caller audit (`GovernedTableReadPlanner.Plan`): `GovernedDataQueryService` (REST, MCP; callers default to 50 explicitly) and `SqlTableReadExecutor` (ExecuteAsync, StreamAsync). Out of #301 scope and unchanged: `GovernedTableReadPlanner.Keyset.cs` (rejects limit <= 0), `TableStreamEndpoints.cs` slice limit (0 means 5000), `LakehouseDataSourceExecutor.cs` (0 means default). Tests: `GovernedDataQueryServiceTests.PlannerCallerAudit_ZeroNeverBecomesDefault`, `SqlTableReadExecutorZeroLimitTests`.

### WP-D implementation notes (2026-10-23)

- `ErrorSanitizingFilter.OnError` is now one path for all environments: classification by exception/error type (`InvalidGraphQLRequestException` -> `INVALID_JSON`/`MISSING_REQUIRED_FIELD`; `FormatException`, `OverflowException`, `InvalidFormatException`, `SerializationException` -> `GRAPHQL_VARIABLE_INVALID`; `DbException` "LIKE or GLOB" -> `INVALID_QUERY`; exception-less errors with no code or an `HCnnnn` code -> `GRAPHQL_PARSE_FAILED`/`GRAPHQL_VARIABLE_INVALID`/`GRAPHQL_VALIDATION_FAILED` by message shape). Classified errors are rebuilt (fixed message, code, path, locations; engine extensions dropped). Anything else fails closed to `INTERNAL_SERVER_ERROR`. `TableNotFoundException` is masked as FORBIDDEN/"Access denied." in Development too.

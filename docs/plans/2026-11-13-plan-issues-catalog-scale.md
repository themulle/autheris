## Cross-cutting invariants (binding for every WP below)

- **INV-1 Epoch per changed table:** every write that changes authorization-relevant metadata of a table (columns, masking rules, classifications, keys, row-filter strategy, visibility, hidden flag, `IsActive`, owners, relations) increments that table's `POLICY_EPOCHS` row inside the write transaction and calls `InvalidateTableEpochAsync` (`GovernanceRepository.cs:428`) after commit. Batching defers only the catalog version bump and the `catalog:changed` event, never the per-table epoch (decision and compiled-plan caches key on it; OD-40 catalog epoch in the decision cache key).
- **INV-2 No lost change:** a deferred version bump and event are always flushed for every committed write, also on exception and cancellation (flush with `CancellationToken.None` in `finally`); the 30 s poll (`CatalogSnapshotBackgroundService.cs:22`) remains the safety net.
- **INV-3 Fail-closed batches:** a chunk is one transaction; any failure rolls back the whole chunk (no partial table, no epoch bump without its data) and the writer reports the chunk as failed.
- **INV-4 Deltas never drop restrictive changes:** an incremental snapshot or index update that cannot prove completeness (gap, read error, unknown table) falls back to a full reload; a removed or hidden table is removed from snapshot and search before the update is published.

## #672 Catalog writes: one version bump and change event per multi-table write

- **Verdict:** NEW PLAN (WP-OI-SCALE-1).
- **Problem:** every single-table write bumps epoch and catalog version and publishes `catalog:changed`; multi-table writers emit n events, each triggering full snapshot, search and schema rebuilds (O(n^2 * columns)).
- **Verified state on main:** `GovernanceRepository.Catalog.cs:354` `UpsertTableMetadataAsync` opens its own transaction (:366), increments the epoch (:448), bumps the version (:451) and publishes (:453); the same pattern in `ReplaceTableKeyDefinitionAsync` (:474-498), `SetRowFilterEvaluationAsync` (:511-531), dataset catalog settings (:584-603), `CreateRelationAsync` (:664-702), `DelegateDataOwnershipAsync` (:728-747), `SetRelationCrossDataSourceOptInAsync` (:757-768). Multi-table callers: `DbtMetadataIngestionService.cs:736, :896, :1003, :1630, :1793`, `DbtSemanticManifestIngestionService.cs:480`, `OpenMetadataSyncService.cs:156, :851`, `DataCatalogSyncService.cs:273`, `OpenApiIngestionService.cs:398`, `VirtualSystemTables.cs:186`. No unit of work exists.
- **Root cause:** the version bump and event are fused into each per-table transaction.
- **Design:** `ICatalogWriteScope` (Application, `Catalog/ICatalogWriteScope.cs`) opened by `ICatalogWriteScopeFactory.Begin(string writer)`; ambient via `AsyncLocal` like `TransactionScope`, so the existing per-table repository methods need no new parameter. Inside a scope the repository still commits the per-table data and epoch (INV-1) but accumulates `structureDelta`/`contentDelta` and the changed-table count in the scope. `DisposeAsync` (and every `CatalogWriteChunkSize` = 500 changed tables, a constant, Q-SCALE-2) runs one `BumpCatalogVersionInternalAsync` with the summed deltas clamped to 1 each in its own short transaction and publishes once (INV-2). Without a scope the behaviour is unchanged (admin single-table endpoints stay immediate). Nested scopes join the outer scope.
- **Work packages / PRs:** PR 1 scope type, factory, repository deferral, unit tests (~+180 src). PR 2 adopt the scope in all multi-table writers listed above and in the dbt relation loop (~+60 src). Freeze: performance refactor, no new endpoint or option; no exception needed.
- **Tests (TDD):** `CatalogWriteScopeTests.Upserts_InScope_PublishOneCatalogChangedOnDispose`, `..._BumpVersionOncePerChunk`, `..._StillIncrementEpochPerChangedTable` (INV-1), `..._FlushOnException_PublishesForCommittedTables` (INV-2), `..._FlushOnCancellation_UsesNoneToken`, `..._NestedScopes_JoinOuter`, `..._NoScope_PublishesPerWrite` (regression); per writer `DbtSyncCatalogEventCountTests.Sync1000Tables_ProducesOneVersionBumpPerChunk`, `OpenMetadataSyncCatalogEventCountTests`, `OpenApiIngestionCatalogEventCountTests`, `SemanticManifestCatalogEventCountTests`; architecture test `MultiTableCatalogWritersUseWriteScopeTests` (every type calling an upsert inside a loop opens a scope; baseline list). Security (`[Trait("Category","Security")]`): `CatalogWriteScopeSecurityTests.HiddenFlagChangeInScope_InvalidatesDecisionCacheBeforeScopeEnds`.
- **Dependencies:** SCALE-0; before WP-SIMPL-28 extraction.
- **Risks:** snapshot and search lag up to one chunk during a sync (acceptable; per-table epochs keep enforcement fresh). An `AsyncLocal` leaking across `Task.Run` in a writer would defer events of unrelated writes: the scope captures the tenant and writer and the repository ignores a scope from another tenant.
- **Size:** M (~240 src, ~350 test, 2 PRs).

## #673 Repository batch upsert for table metadata

- **Verdict:** NEW PLAN (WP-OI-SCALE-2).

- **Work packages / PRs:** PR 1 repository batch API and SQL for both engines (~+350 src). PR 2 dbt chunked pipeline (~+250 / -150 src). PR 3 OpenMetadata, OpenAPI and semantic manifest writers (~+120 src). Freeze: performance refactor, allowed.

## #674 dbt sync: skip unchanged tables

- **Verdict:** NEW PLAN (WP-OI-SCALE-3).
- **Problem:** an unchanged manifest re-writes every table and bumps all epochs and versions.
- **Verified state on main:** `UpsertTableMetadataAsync` bumps unconditionally (`GovernanceRepository.Catalog.cs:448-453`); it already computes `HasMaskingRulesChanged` (:432) and a column change flag (:437) but uses them only to choose structure vs content delta (:449-450). Only dataset catalog settings skip the bump when unchanged (:584-603). dbt has no change detection (`grep Unchanged|Fingerprint` in `Dbt/` finds nothing).
- **Root cause:** no no-op detection at the repository; writers cannot know whether a write changed anything.
- **Design:** generic, in the repository (covers every writer): one `CatalogTablePersistedProjection` record per table (exactly the fields written: table row, columns, masking rules, classifications, key definitions, row-filter strategy) used both to bind write parameters and to compare with the loaded state. Equal projection: no write, no epoch, no version, no event; the call returns the stored metadata and reports `Unchanged`. Comparison after the writer's merge (documentation precedence, governance fields preserved), ordinal and culture-invariant. No schema change (no stored hash). Relations: `CreateRelationAsync` returns the existing relation unchanged without a bump when an identical active relation exists.
- **Work packages / PRs:** PR 1 projection, comparer, repository short-circuit (~+200 src). Freeze: bug fix / performance, allowed.
- **Tests (TDD):** `CatalogTableProjectionTests.EqualMetadata_IsUnchanged`, `..._ColumnTypeChange_IsChanged`, `..._DescriptionChange_IsChanged`, `..._OrderOfColumnsIrrelevantForComparison`; `CatalogTableProjectionCoverageTests.EveryPersistedPropertyIsProjected` (reflection over `TableMetadata`, `TableColumn`, `MaskingRule`; fails when a new persisted property, e.g. a WP-SIMPL-52 classification, is not part of the projection); repository `UpsertUnchangedTable_NoEpochNoVersionNoEvent`; scale `DbtResyncTests.SecondRunSameManifest_ZeroWritesZeroBumps` and `..._3000UnchangedTablesUnderOneMinute`. Security (`[Trait("Category","Security")]`): `CatalogNoOpSecurityTests.MaskingRuleChangeOnly_IsNeverTreatedAsUnchanged`, `..._ClassificationChangeOnly_BumpsEpoch`, `..._HiddenFlagChangeOnly_BumpsEpoch`, `..._IsActiveChangeOnly_BumpsEpoch`.
- **Dependencies:** SCALE-0; before SCALE-1/2 (they reuse the projection).
- **Risks:** a false "unchanged" silently drops a restrictive change; mitigated by the single projection used for write and compare plus the coverage test (Phase 3 focus).
- **Size:** M (~200 src, ~300 test, 1 PR).

## #675 Catalog snapshot: coalesce change events and apply deltas

- **Verdict:** NEW PLAN (WP-OI-SCALE-4).
- **Problem:** each event triggers a full reload; waiters queue on a semaphore; allocation O(tables * columns) per change.
- **Verified state on main:** `CatalogSnapshotProvider.cs:39` subscribes, every event calls `RefreshAsync` which waits on `_refreshLock` (:16, :67) and, when the version moved, loads `GetAllTablesAsync` (:97) and `GetAllRelationsAsync` (:108) and builds `CatalogSnapshot.Create` (:116). A 30 s poll runs additionally (`CatalogSnapshotBackgroundService.cs:22`). `InProcessChannelEventBus.cs:146-152` starts one `Task.Run` per subscriber and only waits 2 s for it.
- **Root cause:** no coalescing; no way to ask which tables changed.
- **Design:** (a) coalescing: replace the event-to-`RefreshAsync` call with a capacity-1 `DropOldest` signal channel and a single refresh loop with a 1 s minimum interval (constant), like `CatalogSearchWarmupService.cs:29-30`. (b) deltas: new migration step (next free number, both engines) adds `change_version BIGINT` to `POLICY_EPOCHS` (index on it), set to the new catalog content/structure version sum in the same transaction as the epoch increment; relation writes increment the epochs of parent and child tables. `GetTablesChangedSinceAsync(long sinceVersion)` returns changed tables incl. inactive ones; the snapshot applies add/replace/remove (`CatalogSnapshot.WithDelta`) when the delta is consistent (no version gap, delta < 20 % of the catalog), otherwise a full reload (INV-4). Inactive or hidden tables are removed in the same delta.
- **Work packages / PRs:** PR 1 coalescing (~+80 src). PR 2 migration step, repository delta read, snapshot delta apply (~+320 src). Freeze: performance refactor plus a DDL step (allowed; migration policy applies).
- **Tests (TDD):** `CatalogSnapshotProviderCoalescingTests.Burst1000Events_AtMostOneRefreshPerInterval`, `..._RefreshAfterBurst_SeesFinalVersion`; `CatalogSnapshotDeltaTests.OneChangedTable_ReplacesOnlyThatEntry`, `..._DeactivatedTable_IsRemoved`, `..._VersionGap_FallsBackToFullReload`, `..._DeltaReadFails_FallsBackToFullReload`; migration `GovernanceMigrationStepParityTests` entry for the new step; scale `CatalogSnapshotScaleTests.OneTableChangeIn50k_UnderHundredMs_AllocatesProportionalToDelta`. Security: `CatalogSnapshotDeltaSecurityTests.HiddenFlagSet_RemovesTableFromSnapshotInSameUpdate`, `..._RelationWrite_PropagatesToBothTables`.
- **Dependencies:** SCALE-1 (fewer events), SCALE-3; serial with other DDL steps.
- **Risks:** snapshot consumers that rely on a full copy per version (5 consumers outside `Application/Catalog`) must accept shared immutable entries; verify each in PR 2.
- **Size:** M-L (~400 src, ~450 test, 2 PRs, 1 migration step).

## #676 Catalog search index: incremental per-table updates

- **Verdict:** NEW PLAN (WP-OI-SCALE-5). #501 (race, staleness, rate limit) stays in the catalog search cluster and merges first.
- **Problem:** every coalesced change rebuilds all documents, the BM25 index and all embeddings.
- **Verified state on main:** `CatalogSearchWarmupService.cs:29-30` (capacity-1 `DropOldest`), 50 ms delay (:91), full `GetAllTablesAsync` plus `RebuildIndexAsync` (:126-127); `CatalogSearchEngine.cs:57` rebuilds, :177 embeds every table document via `GenerateNormalizedEmbeddingsAsync`; only query embeddings are cached (:33-36).
- **Root cause:** index structures (`Bm25SearchIndex`, `VectorSearchIndex`, `CatalogSearchSnapshot`) are build-once.
- **Design:** segment model: an immutable base segment plus a small delta segment and a tombstone set; a table update writes its new document into the delta segment and tombstones the old one; BM25 statistics (document count, average length, document frequencies) are maintained as base plus delta counters; a background merge folds the delta into a new base when it exceeds 10 % (constant). Document embeddings are cached by a SHA-256 of the scrubbed document text, so only new or changed documents are embedded, also during a full rebuild. Changed tables come from the SCALE-4 delta read; a full rebuild only on demand (admin action already present or on delta inconsistency, INV-4). Removed, inactive or hidden tables are tombstoned before the new snapshot is published.
- **Work packages / PRs:** PR 1 document-hash embedding cache (~+120 src). PR 2 BM25 and vector delta segments with tombstones (~+350 src). PR 3 warmup service switches to delta updates (~+100 src). Freeze: performance refactor, allowed.
- **Tests (TDD):** `CatalogSearchEmbeddingCacheTests.UnchangedDocument_NotReEmbedded`, `..._ChangedDescription_ReEmbedded`; `Bm25DeltaSegmentTests.AddReplaceRemove_ScoresEqualFullRebuild` (property test: random update sequences, ranking equal to a full rebuild within tolerance), `VectorDeltaSegmentTests.ReplaceDocument_OldVectorNeverReturned`; `CatalogSearchWarmupDeltaTests.OneTableChange_UpdatesIndependentOfCatalogSize`; scale `CatalogSearchScaleTests.EmbeddingCallsPerSyncEqualChangedTables`. Security: `CatalogSearchDeltaSecurityTests.HiddenTable_NotReturnedAfterDelta`, `..._DeactivatedTable_NotReturnedAfterDelta`, `..._MaskedColumnTextChange_OldTextNotSearchable`.
- **Dependencies:** SCALE-4 (delta read); #501; coordinate with #625/#626 (field weights, tokenizer) in the search cluster, which change postings: whichever merges second rebases; the #624 relevance set must stay green.
- **Risks:** ranking drift between delta and merged state (property test); memory of tombstoned postings until merge (bounded by the merge threshold).
- **Size:** L (~570 src, ~550 test, 3 PRs).

## #678 Bounded memory independent of catalog size

- **Verdict:** NEW PLAN (WP-OI-SCALE-7); new options need an owner `freeze-exception` (Q-SCALE-1).
- **Problem:** metadata cache, snapshot, search index, GraphQL schema and per-tenant lookups hold O(tables * columns); limits are hard-coded; each cache hit still reads the epoch.
- **Verified state on main:** `GovernanceRepository.cs:25,28` (TTL 30 s, `BoundedCache` 20,000 entries, already bounded but not configurable); `GovernedCatalogProvider.cs:34` and `TenantCatalogLookup.cs:31` are unbounded `ConcurrentDictionary`; the per-hit epoch read happens in `GetTableMetadataAsync` (`GovernanceRepository.Catalog.cs:23-45`).
- **Root cause:** caches sized for small catalogs; full in-memory structures by design.
- **Design:** options under `Gateway:Catalog:Cache` (`DataCatalogOptions`): `MetadataMaxEntries` (default 20,000), `MetadataTtlSeconds` (30), `ProviderMaxEntries` (10,000), validated (`[Range]`), in the generated configuration reference. `GovernedCatalogProvider` and `TenantCatalogLookup` switch to `BoundedCache` (miss = recompute from the authoritative source). Search index stores postings and vectors with table ids only, no references to full `TableMetadata`. The per-hit epoch read stays (Q-SCALE-3) but becomes one batched epoch read per request for all tables of a query. Startup: snapshot, search index and GraphQL schema load in the background; readiness depends on the GraphQL warm-up only (SCALE-8 makes that bounded).
- **Work packages / PRs:** PR 1 options and bounded provider/lookup caches (~+150 src). PR 2 batched epoch read per request and compact search payload (~+150 src). Freeze: PR 1 grows the options ratchet: owner exception (Q-SCALE-1).
- **Tests (TDD):** `CatalogCacheOptionsValidatorTests.RejectsZeroOrNegativeLimits`; `GovernedCatalogProviderCacheTests.ExceedingLimit_EvictsAndRecomputes`; `TenantCatalogLookupCacheTests.BoundedAcrossTenants`; `TableEpochBatchReadTests.QueryOverFiveTables_OneEpochRoundTrip`; security `CatalogCacheEvictionSecurityTests.EvictedEntry_NeverServedWithStaleEpoch`, `..._StaleEpochAfterRemoteWrite_IsReloaded`; scale `CatalogMemoryScaleTests.RssUnderTargetAt50kTables` (gcdump, `Category=Scale`, target Q-SCALE-5).
- **Dependencies:** SCALE-4, SCALE-5, SCALE-6 (only then can full structures shrink); WP-SIMPL-06/32 configuration reference.
- **Risks:** too-small limits thrash the governance DB; defaults keep current behaviour.
- **Size:** M (~300 src, ~300 test, 2 PRs).

## #679 GraphQL catalog schema at 10k-50k tables

- **Verdict:** NEW PLAN, measure then decide (WP-OI-SCALE-8).
- **Problem:** a structure version change rebuilds `CatalogSchemaModel` over all tables and the Hot Chocolate schema; build time and memory at scale are unknown; readiness took 5-6 minutes at 2,981 tables.
- **Verified state on main:** `CatalogGraphQlTypeModule.cs:192-232`: on a new structure version it builds a full `CatalogSchemaModel` only to compute a fingerprint (:217), then builds it again for the types (:277), so every structural change costs two full builds; `CatalogSchemaModel.BuildAsync` calls `GetAllTablesAsync` (`CatalogSchemaModel.cs:172`). Refresh interval `GraphQlOptions.CatalogSchemaRefreshSeconds` = 60 (`src/Autheris.Domain/Options/Protocols/GraphQlOptions.cs:34`). Partitioning `ByConsentScope`/`ByPermissionTier` (:148-177).

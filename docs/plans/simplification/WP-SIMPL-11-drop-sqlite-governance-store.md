# WP-SIMPL-11 Drop SQLite as governance store
Status: Ready for implementation
Parent: [plan](../2026-11-05-plan-project-simplification.md#wp-simpl-11-drop-sqlite-as-governance-store-od-1-req-simpl-12---persistence-lane-serial) | Issues: #515 (stage 1), #520 (hard dependency) | Owner decisions: OD-1 (binding), OD-2 (default taken), OD-12 | Security conditions: SEC-SIMPL-05, SEC-SIMPL-10..18

## 1. Goal and outcome
SQLite is no longer a governance/metadata store. After this WP: 0 `SqliteGovernanceRepository*` files (today 26), governance migration dialects 3 -> 2, `GovernanceDb:Provider=Sqlite` (or a SQLite-shaped connection string) fails host start before any repository is resolved, every shipped config defaults to PostgreSQL, and all governance tests that used in-memory SQLite run on one shared PostgreSQL Testcontainer per test assembly with a per-test-class database cloned from a migrated template.

## 2. Preconditions and dependencies
- Merged first: WP-SIMPL-10 (baselines), **#520 test-host reuse** (rule 6, R9): 70 of 72 host-starting integration files use in-memory SQLite governance; without host reuse a PostgreSQL migration per host start is unaffordable.
- Must complete before WP-SIMPL-12, WP-SIMPL-19, WP-SIMPL-20 (SEC-SIMPL-05). Persistence lane order: WP-SIMPL-11 -> WP-SIMPL-12 -> WP-SIMPL-19 -> WP-SIMPL-20 (this spec and WP-SIMPL-19 win over any other ordering). Persistence lane is serial; nothing else in `Infrastructure/Persistence` may merge in parallel.
- May run in parallel: Stage 0 docs/WF WPs, WP-SIMPL-36 security lane (no Persistence files).

## 3. Scope
### In scope
- Delete SQLite governance family, runner, baseline, steps, shape reader/shape JSON, connection provider, lint source, execution guards, SQLite anchor store branch.
- New `GovernanceProviderGuard`; TLS validator hardening (SEC-SIMPL-14); PostgreSQL default in all shipped configs/deploy files with no literal passwords.
- `GovernancePostgresFixture` + template-database cloning; migration of SQLite-backed governance tests.
- CHANGELOG entry + new `docs/operations/migration-simplification.md` (section "Governance store").
### Out of scope
- SQLite as data source: `Persistence/Catalog/SqliteColumnMetadataReader.cs`, `Persistence/Catalog/SqliteTypeAffinity.cs`, `SqliteDialectGenerator`, `Ast/Security` SQLite type map, `SqliteZoneOffsetTable`, `Microsoft.Data.Sqlite` package, `AstCompilerSqlite*ExecutionTests`, `DatabaseDialect.Sqlite` (all removed by WP-SIMPL-31; SQLite is removed entirely by the program, governance store here, the rest in WP-SIMPL-31).
- Repository unification (WP-SIMPL-20), SQL Server contract suite (WP-SIMPL-19), data-migration tool from SQLite (none; REQ-SIMPL-12.6 default).

### 12.1 Security conditions for PR-C/PR-D

Phase 3 verdict: APPROVED WITH CONDITIONS (verified against `3bee9818`). Binding on C1 unless noted; tests carry `[Trait("Category","Security")]`.

1. **SEC-SIMPL-10 guard placement.** The guard runs after `DevConfiguration.Apply` and before any `builder.Services` registration that reads `GovernanceDb`; the host-level default builder has already merged env/CLI/appsettings, so the effective config is seen. No config source may be added after the call; `DevConfiguration` must not be exempted from it. Test: `ProgramGuardOrderTests.Governance_guard_runs_before_service_registration`, `.Governance_guard_sees_env_override` (`GovernanceDb__Provider=Sqlite` over appsettings PostgreSql).
2. **Dev persistence must go, not be exempted.** `DevConfiguration` (`Dev:Persist:Enabled`, `Data Source=<dir>/dev.db` written into `GovernanceDb:ConnectionString`, `DevConfiguration.cs:~143-160`) is deleted in C1 together with `scripts/dev-reset.sh` references. Without that the guard (correctly) rejects the dev host. Test: `DevConfigurationTests.Persist_enabled_never_writes_sqlite_governance_connection`.
3. **Runtime default must not be SQLite.** `GovernanceDbOptions.Provider` defaults to `"Sqlite"` today; the guard accepts "no provider + non-empty connection string" as PostgreSQL, so the options default and `AuditChainAnchorStores` (`:861`, null provider falls to the SQLite store) must change to PostgreSql in the same commit. Test: `GovernanceProviderGuardTests.Absent_provider_with_connection_string_resolves_postgresql_family`.
4. **SEC-SIMPL-11 with the shipped `"PostgreSql"` + empty connection string (C1 appsettings).** The guard passes that combination; startup must still fail before serving in every environment (no localhost/trust-auth default, no value in the message). Test: `GovernanceProviderGuardTests.Provider_set_with_empty_connection_string_fails_startup`.
5. **Alias parity.** Guard accepts only `PostgreSql`/`SqlServer`; runtime `DataSourceProvider.Is` also accepts `Postgres`/`PgSql`/`MsSql`. Keep the guard strict (fail-closed) and make the error name the accepted values; never widen the guard to aliases silently. Test: `Provider_alias_is_rejected_or_normalized_consistently`.
6. **SEC-SIMPL-12 anchor store.** No default store for any provider other than PostgreSql/SqlServer (`InvalidOperationException`, also for null/empty/whitespace); no file/in-memory anchor fallback; anchor persistence and chain verification tests for PG/SQL Server stay. Tests as in decision 1 plus `AuditChainSecurityTests.Null_provider_has_no_default_anchor_store`.
7. **Data-source SQLite guards stay.** `SqliteExecutionGuard`/`SqliteProviderExecutionGuard` and data-source `IsInMemorySqlite`-style checks must not be removed with the governance startup checks; only the governance-specific `GatewayStartupValidator.IsInMemorySqlite` and `/app` governance-path checks go. The narrowed arch pattern must not match them and must still fail on any `Sqlite*Governance*` type. Test: `ArchitectureTests.No_Sqlite_governance_types_or_steps_folder` (mutation-checked once with a dummy type).

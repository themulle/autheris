# WP-SIMPL-38 Trino client protocol `/v1/statement`, clean core design
Status: Ready for implementation
Parent: [plan](../2026-11-05-plan-project-simplification.md#wp-simpl-18-borderline-triage-execution-d2) (borderline row "Trino client protocol route", issue rows #470 and #484) | Issues: #470, #484 | Owner decisions: OD-18 (binding, 2026-11-05: the Trino protocol route is kept in core), OD-17 (overridden for this item by OD-18) | Security conditions: none of SEC-SIMPL-30/31 apply (nothing is removed); this spec proposes SEC-TRINO-01..08 (section 6) for Phase 3 confirmation

## 1. Goal and outcome
The Trino client protocol (`POST /v1/statement`, follow-up `GET`/`DELETE` on `nextUri`) stays in core as a thin protocol adapter over the same governed execution path as WebSQL. Measurable outcome:
- One execution path: both transports call `IWebSqlStatementManager` / `IGovernedSqlExecutionService`; `WebSqlEndpoints.Execution.cs` contains no `/v1/statement` or `X-Trino-*` logic (grep count 0).
- Transport attribution, row-limit channel and federation gate are derived from the endpoint's ingress metadata only (#470 fixed); read-only tokens can run queries over the protocol and cancel their own statements (#484 fixed).
- Official Trino clients work: the Trino JDBC driver and trino-python-client run queries, page through results, cancel, and read metadata (`DatabaseMetaData`, SQLAlchemy inspector) against a live gateway in a container interop test (nightly and on demand).

## 3. Scope
### In scope
- Split the Trino adapter out of `WebSqlEndpoints` into `TrinoProtocolEndpoints` (routes, header parsing, response shapes only).
- Transport, row-limit channel and audit attribution from ingress metadata (`SqlTransports.ForIngress`), for submit, poll and cancel (#470).
- WebSQL statement polling returns WebSQL `nextUri`s (`/api/v1/sql/statements/{id}`), never `/v1/statement/...`.
- One failure classifier shared by WebSQL (HTTP problem details) and Trino (QueryResults `error`), replacing message-string parsing.
- Trino protocol conformance: absolute `nextUri`, token paging, `DELETE` on `nextUri`, Trino query states only, standard error codes, full `stats`, `warnings` for row-limit truncation, `maxWait`/`X-Trino-Wait-Timeout` semantics.
- Read-only tokens: `POST /v1/statement`, `DELETE` on own statement URIs (#484).
- Trino metadata emulation extended with `system.jdbc.{catalogs,schemas,tables,table_types,columns}`; emulation only on Trino ingress.
- Interop tests with Trino JDBC and trino-python-client in containers, plus a nightly workflow.
### Out of scope
- Prepared statements (`PREPARE`/`EXECUTE`, `X-Trino-Prepared-Statement`), session properties (`X-Trino-Session`, `SET SESSION`), `X-Trino-Schema` default schema resolution, `X-Trino-Set-*`/`X-Trino-Clear-*` response headers, spooled/segmented results, the Trino web UI (`infoUri` target).
- Trino ODBC drivers (Power BI, Tableau ODBC) beyond what the JDBC test proves; they use the same REST protocol (stated as residual risk).
- Changing the WebSQL JSON response shape (only its `nextUri` changes).
- Statement state persistence across gateway instances (sessions stay in-process; sticky routing is an operator concern, unchanged).

## 10. Risks, rollback, and things the developer must NOT do
- Risk: clients need absolute `nextUri`; behind a proxy the scheme/host depend on `UseForwardedHeaders` with `KnownProxies`. Do not add a configurable public base URL unless the interop test proves it is needed.
- Risk: ODBC-based BI tools (Power BI, Tableau ODBC) are not tested directly; they use the same REST protocol. Residual risk recorded; add a client only with an owner request.
- Risk: in-process sessions mean multi-instance deployments need sticky routing for polling (unchanged behaviour).
- Rollback: each PR reverts independently; PR 1 and PR 2 are security fixes and must not be reverted without a replacement.
- Do NOT: trust `X-Trino-User` for anything; build a second execution or authorization path for Trino; forward unsupported `system.jdbc` or `information_schema` shapes to a backend; put SQL, table names or exception text into `error.message`; add a `pull_request_target` or secret to the interop workflow; parse error message strings to choose codes; add new configuration keys; run more than one `dotnet build` at a time.

## Decisions taken in this spec
1. **WP-SIMPL-18 PR C is removed.** OD-18 keeps the Trino route in core; WP-SIMPL-18 must not delete the `trino` group, `DataSourceTransportFlags.Trino`, `SqlTransports.Trino`, `RowLimits.Trino`, `TransportFlagNames`/reporter entries or `WebSqlTrinoProtocolTests` coverage, and must not add Trino keys to `UnknownGatewayKeyGuard`. Its estimate loses about -250 src lines and its "closes #470 and #484 by removal" is void: both issues are fixed by this WP (PR 1, PR 2). The lead updates the WP-SIMPL-18 override banner and the plan row ("Trino client protocol route: KEEP (OD-18), WP-SIMPL-38").
2. Transport, row-limit channel and federation name are derived from endpoint ingress metadata (`SqlTransports.ForIngress`), not from paths or headers (consistent with #447 SEC-ATR-02).
3. WebSQL keeps its JSON shape; only its `nextUri` becomes the WebSQL route. `X-Trino-*` headers have no effect on WebSQL routes.
4. `DELETE /v1/statement/{id}` is removed in favour of `DELETE nextUri` (the protocol form used by JDBC and python clients); no production deployment exists.
5. No new switch to disable the protocol: `WebSql:Enabled=false` still disables it (`DataSourceTransportConfigurationReporter.cs:76`), and operators restrict it per source with `AllowedTransports` (omit `Trino`).
6. Transport-denial errors keep `errorName = TransportNotAllowedException.Code` (REQ-ATR-04 contract) but use the standard code 4 (PERMISSION_DENIED); the former code 3 collides with USER_CANCELED.
7. Paging uses a fixed 4,096-row page and the existing row limit bounds memory; no new option.
8. Interop runs nightly and on `workflow_dispatch`, not on every PR (container cost); PR 5 requires one green dispatch run on its branch before merge.

## Decisions (default taken)
1. D-PI-1 Boundary: the domain model, `IAccessProfileRepository`, `InMemoryAccessProfileRepository`, the profile cache and the profile API stay unchanged. Only `AccessProfileStore` maps `MaskingMode`/`TargetTables` to the new tables. Rationale: smallest change with identical runtime semantics.
2. D-PI-2 Minimal schema (deviates from section 6, which listed per-item `object_kind`, `data_source`, `operation`, `column_set_mode`, `_columns`, `_row_scopes`, item-level `_classification_access`; none has a writer today):
   - `access_profile_items(tenant_id, profile_id, item_no INT, object_ref VARCHAR(512))`, PK `(tenant_id, profile_id, item_no)`, UNIQUE `(tenant_id, profile_id, object_ref)`, FK `(tenant_id, profile_id)` -> `access_profiles` ON DELETE CASCADE. Pattern vs object stays derived from the text (`AccessProfile.MatchesPattern` rules), so there is one source of truth.
   - `access_profile_classification_access(tenant_id, profile_id, code VARCHAR(64), access_level SMALLINT)`, PK `(tenant_id, profile_id, code)`, CHECK `access_level IN (0,1,2)`, same FK. Profile level, because the masking mode is profile-wide today.
   - Per-item columns, operations, row scopes (stay in `access_profiles.row_scope_json`) and `ACCESS_PROFILE_WRITE_RULES.item_no` are deferred to the WP that first writes them (additive step then).
3. D-PI-3 PII mapping, a bijection over the defined values: `Unmasked` <-> `CLEAR` (2), `Default` <-> `MASK` (1), `Strict` <-> `DENY` (0); code `PII`. Read back fail-closed: missing PII row, a level outside 0..2, or any non-`PII` row -> `Strict` (same as today's undefined-mode rule). Never widening: no read path yields a less restrictive mode than the stored one.
4. D-PI-4 API: `POST/GET` profile contract unchanged (`maskingMode`, `tables`). New validation: a `tables` entry longer than 512 characters -> 400 `BadRequest` (today it would only fail later in the DB).
5. D-PI-5 Step `0030_access_profile_items` (PostgreSQL + SQL Server, paired `.sql` + `.shape.json`, header `-- phase3: MIG-0030`), after `0028_data_products` (merged, #850) and the planned `0029_drop_role_grantee`; if 0030 is taken at merge, use the next free number. DDL PRs merge one at a time. One step creates, backfills and drops (no production yet; no dual write).
6. D-PI-6 Backfill (fail closed, the whole step aborts with `RAISE EXCEPTION` / `THROW 51030`, message names the first profile id only):
   - `masking_mode` not exactly one of `Default`, `Unmasked`, `Strict` (case-insensitive) -> abort.
   - `target_tables` not a JSON array of strings (PG `jsonb_typeof <> 'array'` or cast error; SQL Server `ISJSON = 0` or non-string `OPENJSON` type), an element NULL, blank or longer than 512 -> abort.
   - Items: element text verbatim (no trim, no rewrite), `item_no` = ordinal of first occurrence (1-based), duplicates collapsed (set semantics as in `MatchesPattern`); `[]` -> no items.
   - Then `DROP COLUMN masking_mode`, `target_tables` (PG `IF EXISTS`; SQL Server drops the default constraints first, as in step 0024).
7. D-PI-7 Follow-up (c), keep `consent_row_filters.key_set_strategy`, `key_set_duration_seconds`, `key_set_max_keys`: they are a live per-rule override read and written by `RowFilterEvaluationStore`, exposed by the admin API and used by the planner; `virtual_filters.evaluation_mode`/`key_set_max_age_seconds` cover the virtual filter, not the per-rule override. Dropping them would remove an admin-tuned bound (fail open on key-set size). Remove from the section 5.10/PR 6b drop list; revisit only if a WP removes the per-rule override API.

## Binding fail-closed notes for Phase 3 (to confirm as SEC-PI-*)

## Phase 3 security review (2026-11-18)

Verdict: APPROVED WITH CONDITIONS. SEC-PI-01..04 above are confirmed as written; the conditions below are binding and add to them. Verified: `UpsertProfileAsync` already runs one transaction and re-reads assignments with `tx` (`AccessProfileStore.cs` l.213, l.237); `DeleteProfileAsync` deletes assignments then the profile in one tenant-filtered transaction (l.246-255); the endpoints call `InvalidateTenantAsync` and bump `profile_epoch:{tenant}` after write and delete (`GovernanceEndpoints.Access.cs` l.361/388, l.660/692).

- SEC-PI-05 Tenant isolation: both new tables carry `tenant_id` in the PK and in the composite FK `(tenant_id, profile_id)`; every new SELECT, INSERT and DELETE binds `@tenantId` and `@profileId`; the batched load uses `tenant_id = @tenantId AND profile_id IN (...)` with bound parameters only. A profile id that exists in another tenant never yields items or a level.
- SEC-PI-06 Cascade: `DeleteProfileAsync` keeps its transaction and explicitly deletes item and classification rows (tenant-filtered) before the profile row, so it does not depend on `ON DELETE CASCADE` alone; the FK cascade stays as defence in depth. No orphan rows after delete on either engine.
- SEC-PI-07 Atomic upsert: the profile MERGE/upsert, the delete of the old item and classification rows, and the inserts of the new rows share the one existing transaction; the in-transaction re-read (`LoadProfilesAsync(..., tx)`) must include the new tables on the same `tx`. Concurrent upserts of the same profile serialize on the profile row (SQL Server keeps `HOLDLOCK`; PostgreSQL takes the row lock via `ON CONFLICT DO UPDATE` before the child delete); the result is always one writer's complete state, never a mix of item sets. Duplicates in `tables` are collapsed in memory before insert (UNIQUE `object_ref`); a unique violation is not swallowed.
- SEC-PI-08 Cache and epoch: no change to invalidation points; the cache loads through `AccessProfileStore`, so a changed item or level is visible only after the existing `InvalidateTenantAsync` plus `profile_epoch` bump. Profile writes through the repository must not bypass the endpoint paths (no new writer outside `AccessProfileStore`). An unavailable epoch store stays a 503 (fail closed), unchanged.
- SEC-PI-09 Audit and logs: the existing Tier-A profile events stay; no new audit event type. The backfill abort message, the 400 for a >512 entry and any store exception name the profile id only, never `object_ref` or `target_tables` content.
- SEC-PI-10 Rolling upgrade: the step header must state that the step runs only after every node runs the new build (old nodes read and write the dropped `masking_mode`/`target_tables` and would fail closed by error, but must not be left running). The new build must not read the dropped columns, and the step must not run while an old node is live; a fresh install (v1.5.0 base plus steps) must pass the same shape check. No dual write and no read fallback to the old columns.
- SEC-PI-11 Fail closed on read: if the classification query or item query fails, the load throws (no partial profile cached, no empty-items profile with a looser mode); a profile with no PII row resolves `Strict` (SEC-PI-02); an item list is never read from a profile of another `profile_id` in the same batch (group by the `(tenant_id, profile_id)` key).
- SEC-PI-12 Input bounds: `tables` entries over 512 characters, null or blank entries, and a list over the existing profile-entry count cap (or 1000 if none exists) -> 400 before any write; the DB column is `VARCHAR(512)` on both engines.

- 2026-11-19 (Phase 4, `feat/simpl-52-profile-items`): G-PLAN-REBASE on `e3e32b401`. (b) `StepSqlLint` forbids `DO`, so PostgreSQL cannot use `RAISE EXCEPTION`; the abort is the established cast-error pattern of step 0029 (`CAST('MIG-0031 aborted - ...: ' || <profile id> AS INTEGER)` over a one-row subselect), SQL Server uses `THROW 51030`. The PostgreSQL JSON checks use `IS JSON ARRAY` (PostgreSQL 16 or later) so a malformed value never raises a cast error that echoes its text. (c) The hot read `GetProfilesForSubjectsAsync` builds profiles from a join, so it now reads the profile rows and assignments first, then loads items and levels for the matched profile ids in one batched, tenant-filtered query per table. (d) The SQL Server `object_ref` column uses `Latin1_General_100_BIN2` (verbatim, case-sensitive uniqueness); trailing blanks are ignored by SQL Server comparisons, so the in-memory collapse key and the backfill first-occurrence window ignore them too. (e) Entry-count cap: no cap existed, so the bulk-consent endpoint caps `tables` at 1000. (f) The integration migration test runs on PostgreSQL only (compile-checked locally); the SQL Server variant of the step is covered by the unit step tests. `Load_UnknownLevelRowInDb_ResolvesStrict` is covered by the unit test (the CHECK constraint prevents the row) and `ProfileChange_InvalidatesCacheAndBumpsEpoch` is unchanged endpoint behaviour, not re-tested here.

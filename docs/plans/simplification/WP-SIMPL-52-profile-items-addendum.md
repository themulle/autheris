## Decisions (default taken)
1. D-PI-1 Boundary: the domain model, `IAccessProfileRepository`, `InMemoryAccessProfileRepository`, the profile cache and the profile API stay unchanged. Only `AccessProfileStore` maps `MaskingMode`/`TargetTables` to the new tables. Rationale: smallest change with identical runtime semantics.
2. D-PI-2 Minimal schema (deviates from section 6, which listed per-item `object_kind`, `data_source`, `operation`, `column_set_mode`, `_columns`, `_row_scopes`, item-level `_classification_access`; none has a writer today):
   - `access_profile_items(tenant_id, profile_id, item_no INT, object_ref VARCHAR(512))`, PK `(tenant_id, profile_id, item_no)`, UNIQUE `(tenant_id, profile_id, object_ref)`, FK `(tenant_id, profile_id)` -> `access_profiles` ON DELETE CASCADE. Pattern vs object stays derived from the text (`AccessProfile.MatchesPattern` rules), so there is one source of truth.
   - `access_profile_classification_access(tenant_id, profile_id, code VARCHAR(64), access_level SMALLINT)`, PK `(tenant_id, profile_id, code)`, CHECK `access_level IN (0,1,2)`, same FK. Profile level, because the masking mode is profile-wide today.
   - Per-item columns, operations, row scopes (stay in `access_profiles.row_scope_json`) and `ACCESS_PROFILE_WRITE_RULES.item_no` are deferred to the WP that first writes them (additive step then).
3. D-PI-3 PII mapping, a bijection over the defined values: `Unmasked` <-> `CLEAR` (2), `Default` <-> `MASK` (1), `Strict` <-> `DENY` (0); code `PII`. Read back fail-closed: missing PII row, a level outside 0..2, or any non-`PII` row -> `Strict` (same as today's undefined-mode rule). Never widening: no read path yields a less restrictive mode than the stored one.
4. D-PI-4 API: `POST/GET` profile contract unchanged (`maskingMode`, `tables`). New validation: a `tables` entry longer than 512 characters -> 400 `BadRequest` (today it would only fail later in the DB).
5. D-PI-5 Step `0030_access_profile_items` (PostgreSQL + SQL Server, paired `.sql` + `.shape.json`, header `-- phase3: MIG-0030`), after `0028_data_products` (merged, #850) and the planned `0029_drop_role_grantee`; if 0030 is taken at merge, use the next free number. DDL PRs merge one at a time. One step creates, backfills and drops (no production yet; no dual write).
6. D-PI-6 Backfill (fail closed, the whole step aborts with `RAISE EXCEPTION` / `THROW 51030`, message names the first profile id only):
   - `masking_mode` not exactly one of `Default`, `Unmasked`, `Strict` (case-insensitive) -> abort.
   - `target_tables` not a JSON array of strings (PG `jsonb_typeof <> 'array'` or cast error; SQL Server `ISJSON = 0` or non-string `OPENJSON` type), an element NULL, blank or longer than 512 -> abort.
   - Items: element text verbatim (no trim, no rewrite), `item_no` = ordinal of first occurrence (1-based), duplicates collapsed (set semantics as in `MatchesPattern`); `[]` -> no items.
   - Then `DROP COLUMN masking_mode`, `target_tables` (PG `IF EXISTS`; SQL Server drops the default constraints first, as in step 0024).
7. D-PI-7 Follow-up (c), keep `consent_row_filters.key_set_strategy`, `key_set_duration_seconds`, `key_set_max_keys`: they are a live per-rule override read and written by `RowFilterEvaluationStore`, exposed by the admin API and used by the planner; `virtual_filters.evaluation_mode`/`key_set_max_age_seconds` cover the virtual filter, not the per-rule override. Dropping them would remove an admin-tuned bound (fail open on key-set size). Remove from the section 5.10/PR 6b drop list; revisit only if a WP removes the per-rule override API.

## Binding fail-closed notes for Phase 3 (to confirm as SEC-PI-*)
- SEC-PI-01 Backfill aborts on any unmappable row; no default value is invented for a bad `masking_mode` or `target_tables`.
- SEC-PI-02 Store read: missing/extra/out-of-range classification rows resolve to `Strict`; missing item rows resolve to an empty `TargetTables` (assignment is refused today by `ProfileAssignmentRequestService` l.62).
- SEC-PI-03 Upsert writes profile row, items and classification row in the existing transaction (`AccessProfileStore` l.213); delete-then-insert per profile, tenant-filtered; never a partial write.
- SEC-PI-04 All new SQL is fixed text with bound parameters (Cutover allowlist entry `AccessProfileStore` unchanged; no new interpolation).

# WP-SIMPL-45 Governed write access (grant-record-based write grants)
Status: Ready for implementation
Parent: [plan](../2026-11-05-plan-project-simplification.md) (supersedes the design of WP-SIMPL-36 sub-package 3 step 1 and the `IDmlWriteGrant` step 8 of WP-SIMPL-14) | Issues: #505 | Owner decisions: OD-26 (binding), OD-3, OD-22, OD-25, OD-19, OD-27 (groups via SCIM), OD-30, OD-31, OD-32, OD-33, OD-35 | Advisories (fixed by WP-SIMPL-36, details: private advisory): GHSA-jcf8-hchm-55h3 (WebSQL DML authorization), GHSA-3prq-qxg7-92qf (WebSQL DML scoping), GHSA-83g2-c2jr-c8vq (WebSQL DML token scopes), GHSA-v75c-28mx-7wm7 (WebSQL DML request handling) | Security conditions: SEC-SIMPL-01, 30, 31, 34, 70, 80, 81; SEC-SIMPL-120..131 (binding as amended in the sec plan section 11.2), SEC-AZ-11, SEC-AZ-13

> **Changed by OD-30, OD-32, OD-33, OD-35 (2026-11-05):** `IWriteGrantEvaluator` is invoked by the access decision point of [WP-SIMPL-46](WP-SIMPL-46-unified-authorization-model.md) as the grant step of every write decision; consumers call the decision point, not the evaluator. Write grants are approved, time-limited grant records (`valid_from`/`valid_until`), from consent requests or from access-profile assignments materialized by [WP-SIMPL-47](WP-SIMPL-47-external-catalog-and-consent-api.md) (OD-32). A write never requires a read grant (OD-33). Enforcement sits in the shared pipeline; this WP wires WebSQL only, every other transport rejects writes fail-closed (OD-35). No role-based write bypass (`DmlWriterRoles`, ClusterAdmin) remains. Sections 1-12 below already reflect these decisions.

## 1. Goal and outcome
Replace the global writer role (`WebSql.DmlWriterRoles`) plus read consent with explicit, data-owner-approved write grants: operation (INSERT, UPDATE, DELETE) x column set x row scope (`OwnRows` = the caller's row-level-security predicate, or `AllRows` = whole table), held as write rules on approved, time-limited grant records (consent requests, and access-profile assignments materialized per OD-32), assignable to users and AD groups, never inferred from read access, never requiring a read grant (OD-33) and independent of Casbin. Outcome, objectively checkable: zero `DmlWriterRoles` matches in `src` (except the fail-fast guard entry); every DML statement is authorized by the decision point (`IWriteGrantEvaluator` as its write grant step) and enforced column by column in the AST visitor; new rows and updated rows must satisfy the subject's row scope (check option); write-protected columns are never writable; write enforcement lives in the shared pipeline and is wired for the WebSQL transport only, with a write scope, an `Idempotency-Key`, a write-ahead audit and a write budget; every other transport rejects writes fail-closed; discovery shows the caller's write state and offers a write-access request; all mandatory tests of section 6 are green.

## 3. Scope
### In scope
- Domain model `WriteRule` (operation, columns, row scope, optional row filter, optional per-statement row cap) on grant records (`Consent`) and as template content on `AccessProfile`; governance schema step `NNNN_write_grants` (next free forward-only migration step at merge time, per the frozen v1.5.0 base policy; PostgreSQL and SQL Server, plus SQLite while it still exists).
- Consent workflow: write rules in consent requests, data-owner approval, revocation, expiry (same lifecycle and validity as read grants; validity bounds per WP-SIMPL-47).
- `IWriteGrantEvaluator` (core, no Casbin), invoked by the decision point as the write grant step, replacing both `CanWriteTableAsync` overloads and the writer-role block in `GovernedSqlRewriter`.
- Engine: `DmlWritePermit` in `GovernancePolicy`; column-level checks in `SecureAssignments` / `ResolveInsertColumns`; masked, denied and PII columns writable only when named by a write rule; write-protected columns; INSERT check option for consent IN-list row filters; DELETE behind a disabled-by-default switch; MERGE rejected.
- Catalog column flag `WriteProtected` (#505) with catalog API support; primary-key columns implicitly write-protected for UPDATE.
- Durable audit: write-ahead intent record and pre-commit outcome record (#505).
- Write budgets per subject (statements per minute, rows per hour) on top of `MaxAffectedRows`.
- Transport matrix (OD-35): write enforcement in the shared pipeline; only `SqlTransports.WebSql` is wired; every other transport (OData, GraphQL, REST, Trino, MCP and the rest) rejects writes fail-closed with a typed deny.
- DB-side least privilege: per-data-source write connection, required-privileges report (OD-25).
- Discovery write state and write-access request (WP-SIMPL-41 integration, through the decision point).
- Migration from `DmlWriterRoles` (fail-fast key, migration report endpoint).
- Re-scope note for WP-SIMPL-36 SP3 and WP-SIMPL-14 step 8 (spec text only, applied by the lead in `docs/plans/`).
### Out of scope
- DDL of any kind, adding columns, `CREATE`/`ALTER`/`GRANT` issued by Autheris (Autheris never changes source privileges itself).
- Wiring writes on any transport other than WebSQL (Trino protocol, MCP `query_sql`, Flight SQL, async jobs, SQL endpoints, REST data API, OData, GraphQL, Arrow export, Olap, federated cross-source statements). They reject writes fail-closed until a later, separately approved WP wires them through the same shared pipeline (OD-35; decisions D-45-3, D-45-4).
- Materializing access-profile assignments into grant records (WP-SIMPL-47, OD-32).
- MERGE and `INSERT ... SELECT` into row-filtered tables (stay rejected).
- Write grants on stored procedures (procedures follow WP-SIMPL-39).
- Bulk load / file upload endpoints.
- Returning before/after row values in audit (audit holds no values, SEC-SIMPL-81).

## 5. Implementation steps (TDD: write the section-6 tests of each step first)
1. **Domain model** (`src/Autheris.Domain/Model/WriteGrantModels.cs`, new):
   ```csharp
   public enum WriteOperation { Insert = 1, Update = 2, Delete = 3 }
   public enum WriteRowScope { OwnRows = 0, AllRows = 1 }
   public sealed record WriteRule(Guid Id, WriteOperation Operation, IReadOnlyList<string> Columns,
       WriteRowScope RowScope, RowFilterDefinition? RowFilter = null, long? MaxRowsPerStatement = null)
   { public void Validate(); } // Columns non-empty for Insert/Update, empty for Delete; distinct, case-insensitive; MaxRows > 0 when set
   ```
   `Consent.WriteRules` (`IReadOnlyList<WriteRule>`, default empty): every grant record (consent row, including the rows WP-SIMPL-47 materializes from approved access-profile assignments) may carry write rules; they are valid exactly within the record's `valid_from`/`valid_until` and end with its revocation. `AccessProfile.WriteRules` (`IReadOnlyList<AccessProfileWriteRule>` with an exact `TableIdentifier`) is template content only and grants nothing by itself (OD-32); `Validate` rejects wildcard tables for profile write rules. `Consent.Validate` rejects write rules on `GranteeType.Role` grantees (roles are no subjects, OD-30) and on `ConsentEffect.Deny`. `TableColumn.WriteProtected` (bool, `TableModels.cs:213`).
2. **Persistence**: step `NNNN_write_grants.sql` + `.shape.json` per governance dialect (next free forward-only migration step at merge time, per the frozen v1.5.0 base policy): `CONSENT_WRITE_RULES(id, tenant_id, consent_id FK CONSENTS, operation, row_scope, row_filter_json NULL, max_rows_per_statement NULL, columns_json)`, `ACCESS_PROFILE_WRITE_RULES(id, tenant_id, profile_id, table_identifier, operation, row_scope, row_filter_json NULL, max_rows_per_statement NULL, columns_json)` (template), `CONSENT_REQUESTS.requested_write_rules_json NULL`, `TABLE_COLUMNS.write_protected BIT/BOOLEAN NOT NULL DEFAULT 0`. No separate approval table: an approved profile write rule exists only as a `CONSENT_WRITE_RULES` row on a materialized grant record (WP-SIMPL-47). Load/save in `*GovernanceRepository.Consent*.cs`, `*.AccessProfiles.cs`, `AccessProfileStore.cs`, `InMemoryAccessProfileRepository.cs`; contract tests in the governance repository contract suite (WP-SIMPL-19) if merged, otherwise per-repository tests.
3. **Consent workflow**: `ConsentRequestSubmission` gains `IReadOnlyList<WriteRule>? RequestedWriteRules`; `ConsentRequestService.SubmitAsync` validates columns against the catalog, rejects write-protected columns, policy-dependency tables (step 6) and `Delete` while `WebSql:Dml:AllowDeleteGrants=false`. A write request needs no read request (OD-33). Approval runs the same approval path as any consent (internal workflow or, after WP-SIMPL-47, its decision pipeline and external webhook mode) and copies the approved rules (the owner may narrow, never widen) onto the created grant record, which carries `valid_from`/`valid_until` bounded by the configurable maximum of WP-SIMPL-47 (`GrantValidityPolicy`; before WP-SIMPL-47 the existing `IndividualGrantOptions` ceilings). Approver must be a data owner of the table (existing approver check). Access-profile write rules are approved only through an access-profile assignment request (WP-SIMPL-47 step 9a), which materializes one write-carrying grant record per table. Grant, approval, revocation and expiry write `WRITE_GRANT_CHANGED` audit events (required).
4. **Evaluator** (`src/Autheris.Application/Policy/WriteGrants/IWriteGrantEvaluator.cs`, `WriteGrantEvaluator.cs`, new; invoked only by the WP-SIMPL-46 decision point as the grant step of `Insert`/`Update`/`Delete` decisions):
   ```csharp
   public sealed record WriteGrantQuery(ClaimsPrincipal User, TenantId Tenant, TableMetadata Table,
       WriteOperation Operation, IReadOnlySet<string> WrittenColumns);
   public sealed record WriteGrantDecision(bool IsAllowed, WriteRowScope RowScope, IReadOnlySet<string> WritableColumns,
       long? MaxRowsPerStatement, IReadOnlyList<string> GrantIds, string? DenyCode);
   Task<WriteGrantDecision> EvaluateAsync(WriteGrantQuery query, CancellationToken ct);
   ```
   Sources: active (`valid_from <= now < valid_until`), non-revoked grant records of the table with write rules (consents and WP-SIMPL-47 materialized profile grants), matched by `GranteeMatcher` on user SID and canonical effective group SIDs (token plus SCIM; plugin-enriched SIDs never, OD-31). Profile templates and assignments without materialized records are never read. Per written column, the widest scope among rules of the requested operation covering it; statement scope = narrowest over all written columns (`OwnRows` < `AllRows`). Deny when any written column is uncovered, when operation is `Delete` and `AllowDeleteGrants=false`, when the table is a policy dependency, when the column is write-protected, when group resolution is `Degraded` (WP-SIMPL-43), or on any exception (fail closed, `DenyCode` set, never thrown to the caller as allow). Read grants are never consulted: a write needs no read allow and a read grant never implies a write (OD-33). `GrantIds` lists the contributing grant ids (audit, usage). Cluster admin gets no implicit write grant. Delete `TableAccessPolicy.CanWriteTableAsync` (both overloads) and the `"write"` action attribute path.
5. **Rewriter wiring** (`GovernedSqlRewriter.cs`): replace `:259-271` (writer roles) with: transport check (step 8), `user.HasWriteScope()` (WP-SIMPL-36), then per DML target the write decision with the written columns (INSERT column list; UPDATE assignment targets; DELETE empty set) replacing `:538-546` with `IAccessDecisionPoint.DecideAsync` with `AccessOperation.Insert|Update|Delete` (that call is wired by WP-SIMPL-46 PR 2; until then this step denies every DML statement fail-closed with `dml_decision_point_not_wired` and never calls `IWriteGrantEvaluator` directly; architecture test `IWriteGrantEvaluator_only_called_by_decision_point` of WP-SIMPL-46). Build `DmlWritePermit` for the compile request. Row scope (OD-33):
   - `OwnRows`: the statement is bounded by the caller's row-level-security predicate for the target, computed by the decision point: tenant predicate AND mandatory/virtual filters AND the OR over the row filters of the caller's active grant records on that table (read and write; an unfiltered record contributes TRUE). No read grant is required: a caller holding only the write grant is bounded by that grant's `RowFilter` (none = TRUE).
   - `AllRows`: tenant predicate plus mandatory/virtual filters only (grant row filters removed).
   MERGE: throw `WebSqlPolicyException` ("MERGE is not supported for governed writes").

## Decisions taken in this spec
- D-45-1: DELETE is a separate grant (`WriteOperation.Delete`), off by default via `WebSql:Dml:AllowDeleteGrants=false` (owner did not request DELETE).
- D-45-2 (OD-33): Row scope per statement is the narrowest scope over the written columns. `OwnRows` applies the caller's RLS predicate (tenant, mandatory filters and the OR over the row filters of the caller's grant records on the table, read or write); `AllRows` lifts only grant row filters, never tenant or mandatory filters.
- D-45-3 (OD-35, owner, binding): write enforcement sits in the shared pipeline and is wired for WebSQL only in this WP. OData, GraphQL, REST, Trino and MCP reject writes fail-closed until a later, separately approved WP wires them; OD-29 "identically" is met because any wired transport uses the same decision and engine permit. Async jobs, SQL endpoints and Flight (until deleted) are read-only.
- D-45-4: MERGE rejected; INSERT into row-filtered tables allowed only for IN-list/literal filters via check option.
- D-45-5: Write grants on roles are rejected; `DmlWriterRoles` is removed without automatic conversion (migration report instead).
- D-45-6 (OD-32): Access-profile write rules are template content with exact tables; they grant nothing by themselves. Approval of a profile assignment (WP-SIMPL-47 approval path) materializes one time-limited write-carrying grant record per table; there is no separate profile write-approval table or rules hash.
- D-45-7: Primary-key columns are implicitly write-protected for UPDATE.
- D-45-8: WP-SIMPL-36 SP3 keeps write scope, tenant-column refusal, interim dependency deny, replay protection, write-ahead audit and `MaxAffectedRows>0`; its step-1 grant design, write-protected columns and write budget move here. WP-SIMPL-14 step 8 shrinks to its four interim `DmlSecurityTests`.
- D-45-9: Least privilege is achieved by a separate write connection and an operator-applied privileges report; Autheris never alters or inspects source privileges.
- D-45-10 (OD-33): write grants are independent of read grants in both directions; the evaluator never reads read grants for the allow decision (only the RLS predicate of `OwnRows` uses the row filters of all the caller's grant records).
- D-45-11 (OD-32, R5): every write approval is a grant record with `valid_from`/`valid_until` in the same grant store and approval path as consent.

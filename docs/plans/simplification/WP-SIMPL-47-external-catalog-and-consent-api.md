## 1. Goal and outcome
External programs (ServiceNow, Jira or any workflow engine) can read the whole tenant catalog and every consent request through a stable, versioned REST contract (`/api/v1`), receive a signed webhook (or poll a cursor feed) when requests are created or change, and report approve, reject, expire and revoke decisions back. The workflow mode is configurable per tenant, optionally per data owner or data source: `Internal` (today's built-in engine: data-owner approval, four-eyes, self-approval rules) or `External` (Autheris dispatches a webhook and accepts the decision via API, rejecting only obvious violations). Both modes run through one decision pipeline and produce the same grant: time-limited (`valid_from`, `valid_until`, bounded by a configurable maximum, enforced on every request, revocable early, renewed only by a new request) and recorded as a signed, per-tenant hash-chained grant record with a verification endpoint that proves whether subject S could access object O at time T.

Measurable: (a) every `CONSENTS` insert has exactly one `GRANT_RECORDS` row in the same transaction (integration check over all write paths); (b) `git grep -n -E "IsItsmActor|isExternalItsmApproval|itsmApproverAccount|ExtendConsentExpiryAsync|AddYears\(100\)" -- src` returns 0; (c) every security test of section 6 is green; (d) the OpenAPI contract test passes against the mapped routes.

## 3. Scope
### In scope
- Workflow routing: per tenant / data owner / data source route (`Internal` or `External`), external system registration, mode stamped on each request, no orphaned requests on mode switch.
- One decision pipeline `IConsentDecisionPipeline` used by the GraphQL mutations (internal) and the REST decision endpoint (internal and external).
- Time-limited grants for every grant source (requests, bulk endpoint, declarative manifests): mandatory `valid_until`, effective maximum, check on every request and every cache hit, early revocation, renewal by new request, expiry notices.
- Signed, hash-chained grant records, proof and verification endpoints, public keys endpoint.
- Core consent outbox, signed webhook delivery to the external system, cursor event feed.
- External REST API: catalog read (objects, columns, properties, change feed, ETag), consent requests, decisions, grants, revocation; permissions for service principals; idempotency keys; `If-Match`; stable error codes; rate limits; audit of every external decision and every denied attempt; OpenAPI document and contract tests.
- Cleanup of ITSM leftovers in the consent core (section 5 step 3).
### Out of scope
- Any vendor-specific connector (ServiceNow/Jira code). Integration happens only through this generic API (section 10, integration pattern).
- Changing the internal approval rules (four-eyes for HIGH/RESTRICTED/SECRET, data-owner/delegate approvers).
- Row-filter or masking parameters set by an external decision (v1: an external decision may only narrow requested columns/write rules and the validity; row-level security and masking come from the owner-defined policies).
- Linking each data-access audit entry to the grant record ids it used (follow-up; proof in v1 is by subject, object and time).
- GraphQL parity for the external contract (GraphQL keeps today's internal mutations and queries).

### 6a. Proposed Phase 3 conditions (to be confirmed and numbered by `csharp-security-expert`)
- SEC-SIMPL-47-01: an external decision is accepted only from an enabled system registered in the request's tenant and stamped on the request; all other ids return 404.
- SEC-SIMPL-47-02: self-approval (requester, user grantee, group-grantee member, requesting system principal) is rejected in both modes.
- SEC-SIMPL-47-03: no `CONSENTS` change without a signed grant record in the same transaction; signer failure fails closed.
- SEC-SIMPL-47-04: validity is checked on every request and every cache hit; no grant without `valid_until`; no in-place extension.
- SEC-SIMPL-47-05: `Idempotency-Key` and `If-Match` are mandatory on state-changing calls; replays never create a second grant.
- SEC-SIMPL-47-06: webhook payloads carry no justification, approver identity or data; delivery only to the stamped system through the egress guard, HMAC-signed with timestamp.
- SEC-SIMPL-47-07: external catalog read follows WP-41 visibility; hidden content only with `Catalog.ReadAdmin`; never row data.
- SEC-SIMPL-47-08: every external decision, revocation and denied attempt is audited (Tier A, denial rate-bounded like `ConsentDecisionDenialRecorder`).
- SEC-SIMPL-47-09: signing key separate from the audit HMAC key, held in the secret provider, rotation keeps old public keys verifiable.
- SEC-SIMPL-47-10: rate limits per tenant and client on decision, revoke and proof routes.
- SEC-SIMPL-47-11: mode switch never leaves a request undecidable or decidable by two parties.
- SEC-SIMPL-47-12: the OpenAPI document and error codes are a versioned contract; breaking changes require `/api/v2`.

## 10. Risks, rollback, and things the developer must NOT do
- Integration pattern (replaces ITSM, OD-5): the admin registers the tool as an external system (Entra app registration with client credentials and the app roles of step 11) and routes a tenant, data owner or data source to it. On `request.created` the tool's inbound webhook (ServiceNow Scripted REST API / Jira Automation incoming webhook) verifies the HMAC, calls `GET /requests/{id}` and opens a ticket/approval with the request id as correlation key. On approval or rejection a business rule / automation rule calls `POST /requests/{id}/decision` with the approving users' UPNs, the ticket number as `externalReference`, `Idempotency-Key = <ticket id>:<transition id>` and `If-Match` from the GET. Tools behind a firewall (MID server) poll `/api/v1/consent/events?since=`. Revocation and expiry handling use `grant.expiring`/`grant.revoked` and `POST /grants/{id}/revoke`; renewal is a new request.
- Risk: signing key loss blocks all decisions (fail-closed by design). Mitigation: health check `GrantRecordSignerHealthCheck`, documented key rotation. Risk: backfill on large tenants; run in batches of 1,000 per transaction.
- Risk: cached envelopes from before the upgrade are discarded once (short cold-cache spike).
- Rollback: revert PRs in reverse order; schema step is forward-only, new tables are ignored by older code (no older-version support required, owner policy 2026-10-29).
- Do NOT: delete the internal workflow or relax its four-eyes/self-approval rules; let an external decision set row filters or masking; put justification, approver identities or data in webhook payloads; accept decisions for requests of another tenant or system (return 404, not 403); write unsigned or out-of-transaction grant records; extend a grant in place; add a vendor-specific connector; add an OpenAPI NuGet dependency; describe advisory details in PRs.

## Decisions taken in this spec
1. OD-29 (later, binding) narrows OD-28: in external mode Autheris does not enforce four-eyes; it records all asserted approvers and rejects only obvious violations (step 6). Internal mode keeps today's rules.
2. Workflow mode is stamped per request; mode switches never move a request implicitly except when its external system is disabled (re-route to internal); internal requests with a recorded first four-eyes step cannot be re-routed.
3. Owner-route conflict on multi-owner tables resolves to `Internal` (owner approval inside Autheris is the safe default).
4. Notifications: core consent outbox with HMAC webhook to the stamped system plus a cursor feed over the same table (no dependency on the events module); webhook primitives stay core (consequence for WP-SIMPL-29).
5. Grant records are signed individually (ECDSA P-256, separate key) and chained per tenant; proof is by subject, object and time; linking access-audit entries to record ids is a follow-up.
6. Every grant source is time-limited, including declarative manifests (mandatory `validUntil`, max 365 days default); renewal is always a new request or re-apply, which writes a new record.
7. Tenant default maximum 180 days (equals `IndividualGrantCeilings.RegularDays`); default expiry notice lead 72 h; default request timeout 30 days.
8. Approvers must resolve in the tenant directory by default (`require_resolvable_approver = true`, fail-closed; SCIM per OD-27).
9. The external contract is REST `/api/v1` with a hand-maintained OpenAPI 3.1 document checked by contract tests; GraphQL is unchanged for the external use case.
10. Catalog change tracking uses a hashing indexer (`CATALOG_CHANGES` sequence) instead of hooks in every catalog writer, so module ingestion paths (dbt, OpenMetadata) are covered without changes.

> **Changed by OD-30, OD-32, OD-34 (2026-11-05):** grant records written by the internal or external workflow are the only grant source of the access decision point of [WP-SIMPL-46](WP-SIMPL-46-unified-authorization-model.md). Data owners read through an owner grant record created and revoked with the ownership (step 9b). Sections 1-10 below already reflect these decisions.

## 1. Goal and outcome
External programs (ServiceNow, Jira or any workflow engine) can read the whole tenant catalog and every consent request through a stable, versioned REST contract (`/api/v1`), receive a signed webhook (or poll a cursor feed) when requests are created or change, and report approve, reject, expire and revoke decisions back. The same approval path also decides access-profile assignments to users and AD groups (OD-32) and materializes them into grant records. The workflow mode is configurable per tenant, optionally per data owner or data source: `Internal` (today's built-in engine: data-owner approval, four-eyes, self-approval rules) or `External` (Autheris dispatches a webhook and accepts the decision via API, rejecting only obvious violations). Both modes run through one decision pipeline and produce the same grant: time-limited (`valid_from`, `valid_until`, bounded by a configurable maximum and defaulting to a configurable duration, enforced on every request, revocable early, renewed only by a new request) and recorded as a signed, per-tenant hash-chained grant record with a verification endpoint that proves whether subject S could access object O at time T.

Measurable: (a) every `CONSENTS` insert has exactly one `GRANT_RECORDS` row in the same transaction (integration check over all write paths); (b) `git grep -n -E "IsItsmActor|isExternalItsmApproval|itsmApproverAccount|ExtendConsentExpiryAsync|AddYears\(100\)" -- src` returns 0; (c) every security test of section 6 is green; (d) the OpenAPI contract test passes against the mapped routes.

## 3. Scope
### In scope
- Workflow routing: per tenant / data owner / data source route (`Internal` or `External`), external system registration, mode stamped on each request, no orphaned requests on mode switch.
- One decision pipeline `IConsentDecisionPipeline` used by the GraphQL mutations (internal) and the REST decision endpoint (internal and external).
- Time-limited grants for every grant source (requests, profile assignments, bulk endpoint, declarative manifests): mandatory `valid_until`, configurable effective maximum and default duration, check on every request and every cache hit, early revocation, renewal by new request, expiry notices. Owner grants (OD-34) end with the ownership (step 9b).
- Access-profile assignment approval (OD-32, step 9a): assignment of a profile (request template, table patterns allowed) to a user or AD group runs the same approval path and materializes one time-limited grant record per table matched at approval time, incl. write rules (WP-SIMPL-45).
- Owner grants (OD-34, step 9b): an owner grant record is created when a data owner is assigned and revoked when unassigned.
- Signed, hash-chained grant records, proof and verification endpoints, public keys endpoint.
- Core consent outbox, signed webhook delivery to the external system, cursor event feed.
- External REST API: catalog read (objects, columns, properties, change feed, ETag), consent requests, decisions, grants, revocation; permissions for service principals; idempotency keys; `If-Match`; stable error codes; rate limits; audit of every external decision and every denied attempt; OpenAPI document and contract tests.
- Cleanup of ITSM leftovers in the consent core (section 5 step 3).
### Out of scope
- Any vendor-specific connector (ServiceNow/Jira code). Integration happens only through this generic API (section 10, integration pattern).
- Changing the internal approval rules (four-eyes for HIGH/RESTRICTED/SECRET, data-owner/delegate approvers).
- Row-filter or masking parameters set by an external decision (v1: an external decision may only narrow requested columns/write rules and the validity; row-level security and masking come from the owner-defined policies).
- Grant ids on the decision record (WP-SIMPL-46 step 1) and on the data-access audit entry and usage facts (WP-SIMPL-42 step 9f). This WP only guarantees that every grant id resolves to a signed grant record.
- GraphQL parity for the external contract (GraphQL keeps today's internal mutations and queries).

9. **Expiry and timeouts** (`src/Autheris.Application/Governance/Grants/GrantExpiryHostedService.cs`, new; replaces `ConsentRecertificationHostedService`, which WP-SIMPL-12 kept until here and which this step deletes together with its lock name and tests): every 5 min, per tenant: grants with `valid_until - lead <= now` (lead = route `expiry_notice_lead_hours`, for grants shorter than twice the lead: at half the lifetime) and `expiry_notice_sent_at IS NULL` -> `grant.expiring` event and in-app notification to grantee and owner, set `expiry_notice_sent_at`; grants past `valid_until` -> `EXPIRED` record (informational; enforcement never waits for it) and `grant.expired`; open requests older than `request_timeout_days` -> `EXPIRED`, `REQUEST_EXPIRED` record, `request.expired`. Multi-node safe through a lease row.
9a. **Access-profile assignment approval (OD-32)** (`src/Autheris.Application/ConsentRequests/ProfileAssignments/`, new: `ProfileAssignmentRequestService.cs`, `ProfileGrantMaterializer.cs`):
   - An access profile is a request template over many tables (table patterns allowed), with per-table operations, column set (Clear or Masked per PII column), row scope and WP-SIMPL-45 write rules. A profile and an assignment grant nothing by themselves.
   - Assigning a profile to a user or AD group (never a role: 400 `ROLE_ASSIGNEE_UNSUPPORTED`; OD-30) creates a request with `request_kind = PROFILE_ASSIGNMENT`, routed and decided through `IConsentDecisionPipeline` (step 3) in the stamped mode. Internal mode: the patterns are expanded to the current table set as `PROFILE_ASSIGNMENT_ITEMS`; each item is decided by a data owner/delegate of that table (same owner, four-eyes and self-approval rules as consent); the request is decided when every item is decided. External mode: the external system decides the request as a whole and may only narrow (fewer tables, columns, operations, shorter validity).
   - On approval, `ProfileGrantMaterializer` resolves the patterns **at approval time** and writes, through `IGrantWriter` in the decision transaction, one grant record per matched and approved table (`grant_source = ACCESS_PROFILE`, `profile_assignment_id`, operations, column rules with Clear/Masked per PII column, row filter, write rules, `valid_from`/`valid_until` per step 7). Tables created later that match a pattern are not covered until a new approval. Editing the profile never changes materialized records. Revoking or expiring the assignment revokes or expires all its records in one transaction.
   - Break-glass assignments do not exist (OD-5, OD-32); existing assignments are handled by the WP-SIMPL-46 migration.
   - Routes: `POST /api/v1/consent/requests` with `kind: profileAssignment, profileId, grantee` (GovernanceAdmin of the tenant, or a user for themselves), `POST /api/v1/consent/grants/{id}/revoke` revokes one record, `POST /api/v1/consent/profile-assignments/{id}/revoke` revokes all records of the assignment.
9b. **Owner grants (OD-34)** (`src/Autheris.Application/Governance/Grants/OwnerGrantService.cs`, new): assigning a data owner to a table (every write path of `IDataOwnershipRepository`, incl. dbt/catalog ingestion of owners) writes, in the same transaction and through `IGrantWriter`, an owner grant record (`grant_source = OWNER`, Read, all columns Clear, no grant row filter; tenant predicate, mandatory filters and explicit deny still apply in the PDP), `valid_from` = assignment time, `valid_until` = end of the ownership assignment (null while the assignment is open; the only grant source exempt from `MaxDuration`, OD-34 wins over OD-29 for this case). Unassigning the owner revokes the record in the same transaction (`REVOKED` record, epoch bump). The record is audited like any grant and counted in usage under its grant id (WP-SIMPL-42). There is no implicit owner access anywhere else. Owner grants are created only by the ownership assignment path (control plane), never by the owner for themselves.

### 6a. Phase 3 conditions (binding per the sec plan section 11.2; extended to profile assignments, OD-32, and owner grants, OD-34)
- SEC-SIMPL-47-01: an external decision is accepted only from an enabled system registered in the request's tenant and stamped on the request; all other ids return 404.
- SEC-SIMPL-47-02: self-approval (requester, user grantee, group-grantee member, requesting system principal) is rejected in both modes.
- SEC-SIMPL-47-03: no `CONSENTS` change without a signed grant record in the same transaction; signer failure fails closed.
- SEC-SIMPL-47-04: validity is checked on every request and every cache hit; no grant without `valid_until`; no in-place extension.
- SEC-SIMPL-47-05: `Idempotency-Key` and `If-Match` are mandatory on state-changing calls; replays never create a second grant.
- SEC-SIMPL-47-06: webhook payloads carry no justification, approver identity or data; delivery only to the stamped system through the egress guard, HMAC-signed with timestamp.
- SEC-SIMPL-47-07: external catalog read follows WP-41 visibility; hidden content only for an app-only registered external system with `Catalog.ReadAdmin`, or for GovernanceAdmin users and data owners/delegates of the object; a delegated `Catalog.ReadAdmin` scope reveals nothing hidden; never row data.

- SEC-SIMPL-47-09: signing key separate from the audit HMAC key, held in the secret provider, rotation keeps old public keys verifiable.
- SEC-SIMPL-47-10: rate limits per tenant and client on decision, revoke and proof routes.
- SEC-SIMPL-47-11: mode switch never leaves a request undecidable or decidable by two parties.
- SEC-SIMPL-47-12: the OpenAPI document and error codes are a versioned contract; breaking changes require `/api/v2`.
- Extension (OD-32/OD-34): a profile assignment grants only through materialized, approved, time-limited grant records written by `IGrantWriter`; owner grant records are created and revoked only by the ownership assignment path (SEC-AZ-04, SEC-AZ-12).

## 10. Risks, rollback, and things the developer must NOT do
- Integration pattern (replaces ITSM, OD-5): the admin registers the tool as an external system (Entra app registration with client credentials and the app roles of step 11) and routes a tenant, data owner or data source to it. On `request.created` the tool's inbound webhook (ServiceNow Scripted REST API / Jira Automation incoming webhook) verifies the HMAC, calls `GET /requests/{id}` and opens a ticket/approval with the request id as correlation key. On approval or rejection a business rule / automation rule calls `POST /requests/{id}/decision` with the approving users' UPNs, the ticket number as `externalReference`, `Idempotency-Key = <ticket id>:<transition id>` and `If-Match` from the GET. Tools behind a firewall (MID server) poll `/api/v1/consent/events?since=`. Revocation and expiry handling use `grant.expiring`/`grant.revoked` and `POST /grants/{id}/revoke`; renewal is a new request.
- Risk: signing key loss blocks all decisions (fail-closed by design). Mitigation: health check `GrantRecordSignerHealthCheck`, documented key rotation. Risk: backfill on large tenants; run in batches of 1,000 per transaction.
- Risk: cached envelopes from before the upgrade are discarded once (short cold-cache spike).
- Rollback: revert PRs in reverse order; schema step is forward-only, new tables are ignored by older code (no older-version support required, owner policy 2026-10-29).
- Do NOT: delete the internal workflow or relax its four-eyes/self-approval rules; let an external decision set row filters or masking; put justification, approver identities or data in webhook payloads; accept decisions for requests of another tenant or system (return 404, not 403); write unsigned or out-of-transaction grant records; extend a grant in place; add a vendor-specific connector; add an OpenAPI NuGet dependency; describe advisory details in PRs.

## Decisions taken in this spec
1. OD-29 (later, binding) narrows OD-28: in external mode Autheris does not enforce four-eyes; it records all asserted approvers and rejects only obvious violations (step 6). Internal mode keeps today's rules.
2. Workflow mode is stamped per request; mode switches never move a request implicitly except when its external system is disabled (re-route to internal); internal requests with a recorded first four-eyes step cannot be re-routed.
3. Owner-route conflict on multi-owner tables resolves to `Internal` (owner approval inside Autheris is the safe default).
4. Notifications: core consent outbox with HMAC webhook to the stamped system plus a cursor feed over the same table (no dependency on the events module); webhook primitives stay core (consequence for WP-SIMPL-29).
5. Grant records are signed individually (ECDSA P-256, separate key) and chained per tenant; proof is by subject, object and time. Per-access grant ids come from the WP-SIMPL-46 decision record (R6) and are written to the data-access audit entry and usage facts by WP-SIMPL-42 PR-3b.
6. Every grant source is time-limited, including declarative manifests (mandatory `validUntil`, bounded by the configured `DeclarativeMaxDuration`); renewal is always a new request or re-apply, which writes a new record. Exception: owner grants end with the ownership (OD-34).
7. Grant maximum and default durations are configuration only (R9; example values 2 days, 2 weeks, 2 months); there is no compiled-in maximum. Default expiry notice lead 72 h; default request timeout 30 days.
8. Approvers must resolve in the tenant directory by default (`require_resolvable_approver = true`, fail-closed; SCIM per OD-27).
9. The external contract is REST `/api/v1` with a hand-maintained OpenAPI 3.1 document checked by contract tests; GraphQL is unchanged for the external use case.
10. Catalog change tracking uses a hashing indexer (`CATALOG_CHANGES` sequence) instead of hooks in every catalog writer, so module ingestion paths (dbt, OpenMetadata) are covered without changes.
11. OD-32: an access-profile assignment is a request of kind `PROFILE_ASSIGNMENT` in the same pipeline; internal mode decides per table by that table's owners; materialization happens at approval time only. Roles are no assignees.
12. OD-34: owner grants are written by the ownership assignment path through `IGrantWriter` and end with the ownership; they are the only grant records without a maximum duration.
13. R9: `POST /api/v1/consent/requests` is the only REST route that creates consent requests; WP-SIMPL-41 discovery links to it.
14. R18: WP-SIMPL-12 keeps `ConsentRecertificationHostedService` and `PENDING_EXTERNAL_APPROVAL`; this WP replaces the hosted service (step 9) and reuses the status.
15. R8: hidden catalog objects are visible only to admins (GovernanceAdmin users, app-only registered external systems with `Catalog.ReadAdmin`) and data owners; a delegated `Catalog.ReadAdmin` scope adds nothing.

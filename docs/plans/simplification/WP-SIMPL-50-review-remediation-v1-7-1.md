## 1. Goal and outcome
Close the findings of both reviews so that the Stage 3 deletions, moves and the module host leave no fail-open path, no forgeable audit record, no dead ownership entry, no leftover secret plumbing and no lost security test coverage. Measurable: every item in section 5 has a Red test (or an architecture test for deletions) that fails on `origin/main` and passes after its PR.

## 2. Preconditions and dependencies
- WP-SIMPL-25 and WP-SIMPL-27 are merged (module host and Lakehouse module exist on `origin/main`).
- PR A is a release blocker. All other PRs are independent of each other and may follow in any order; PR B3 and PR B6 both touch `ErrorSanitizingFilter.cs` (rebase, no logical conflict).
- A1, A4 and A5 are exploitable under preconditions. This public plan and all PR texts state only the fail-closed rule and the fix, never reproduction steps.
- WP-SIMPL-46 later moves the read paths onto `IAccessDecisionPoint`; B15 keeps the decision point correct for every operation so that move needs no further authorization change.

Verdict: **APPROVED WITH CONDITIONS.** Code verified on `origin/main` 8fc7a66b. The conditions below are binding for Phase 4 and checked in Phase 5; they amend the items named. **IP contradiction, resolved.** Both earlier statements were partly wrong. True: `AccessDecisionPoint.cs:195` substitutes `IPAddress.None` when the IP is unknown, and the Casbin matcher evaluates operator `sub_rule` text against `r.ctx` (`SecurityEvaluationContext`, which carries `ClientIp`), so IP conditions are expressible (`CasbinSharedDecisionCacheTests.cs:84`, `PolicyShapeAnalyzer` treats the IP as a rule input). Not true: that such a rule ships; none does, and `DecisionKey` is not the only reader. Effect: an operator IP deny-list does not fire for an unknown IP (fail open); allow-lists fail closed. `HttpContextClientIpResolver` returns `None` only without an `HttpContext` or remote address, so exposure is low and ends with WP-SIMPL-14 (OD-30). ### Binding conditions
- SEC-50-01 (A1): `Gateway:Modules:WorkspacePath` set outside Development fails startup in `ProductionStartupChecks` (refused, not ignored). The workspace root is canonicalized, and the resolved DLL must stay under it after symlink resolution (reuse `EnsureNoSymlinkEscape`). Every workspace load logs a Warning naming the module id and "unsigned".
- SEC-50-02 (A2): `TableAccessPolicy` read path and `AccessDecisionPoint` deny with a generic reason when the policy service is missing; no hand-constructed production path (`modules/*`, `src/*`) may pass a null or no-op `IPolicyEnforcementService` (Arch test).
- SEC-50-03 (A2, PR A): until WP-SIMPL-14 lands, `CasbinEnforcementService` denies when `context.ClientIp` is null, `IPAddress.None` or `IPAddress.IPv6None` and any candidate rule's `sub_rule` references `ClientIp` (reuse the `PolicyShapeAnalyzer` identifier scan). Reason "client address unavailable"; the IP is never logged unsanitized. WP-SIMPL-14 deletes this guard with Casbin.
- SEC-50-04 (A4): `BuildModuleAuditDetails` writes `Request.Path` only (never `QueryString`); the 512-char cap also applies to `TargetTable`. The Arch test also flags `DetailsJson` built by `$@"`, `@$"`, raw `$"""`, `string.Format` or `+` concatenation.
- SEC-50-05 (A5): the signed payload starts with the fixed domain tag `hitl-broadcast-v1` so a ticket signature never verifies as a broadcast (same HMAC key). `IssuedAt` must also be no earlier than the ticket creation minus 30 s. On any failure the broadcast is dropped without changing state, and the log carries no `Reason` text. `CompletedAt` comes from `TimeProvider`.
- SEC-50-06 (B1): the private native root is per process, created 0700 and owned by the process user. If it already exists with other owner or mode, startup fails. On Windows it is under the per-user `LocalApplicationData`. The copy is re-hashed before `LoadUnmanagedDllFromPath`; a mismatch throws `ModuleLoadException`.
- SEC-50-07 (B3): versions are parsed strictly as SemVer (prerelease below release); an unparseable manifest or floor version is rejected. `RevokedKeyIds` can only remove keys; an empty keyring rejects every signed module with an explicit error; a manifest without `KeyId` is rejected.
- SEC-50-08 (B4): prefix checks run on the decoded route template and the raw pattern, module ids lowercase ordinal. The old `/v1/...` Iceberg routes return 404 and fall through to no other handler. Every module route requires authentication (SEC-PROD-01); `module-e2e` asserts 401 on the new route and 404 on the old one.
- SEC-50-09 (B11): the audit is written in `finally` exactly once per request. `ERROR` details carry the exception type only, never the message.
- SEC-50-10 (B15): the combiner wraps each operand in parentheses and ignores empty/whitespace operands. Masking merges keep the most restrictive level per column. Any caller that receives a non-null `RowFilterSql` or a non-Clear column level it cannot enforce denies (fail closed); the ADR-020 note states this.
- SEC-50-11 (B12): the guard also protects `IClientIpResolver`, `IHttpContextAccessor`, `TimeProvider`, `IDistributedClusterStateProvider` and the namespaces `Microsoft.AspNetCore.DataProtection`, `Autheris.Application.Policy`, `Autheris.Application.Identity`; the Lakehouse module must still load (its registrations touch none of them).
- SEC-50-12 (C12): a module whose `Gateway:<PascalModuleId>` equals any section known to `GatewayConfigurationSchema` or a `ProtectedConfigPrefixes` entry is rejected (module id `security` cannot claim `Gateway:Security`).
- SEC-50-13 (C11): the body hash is stored only after the HMAC check succeeds; key prefix `vf:webhook:`; if the cluster store fails, respond 503 and do not trigger.
- SEC-50-14 (C6): the size cap is enforced on the bytes read, not only on `FileInfo.Length`.
- SEC-50-15 (B14): the signer reads the key from an environment variable or stdin, never a CLI argument, and never logs it. The signing job runs only on protected release tags, never on `pull_request`, with `permissions: contents: write` only. The module key is distinct from the image signing identity.

### Answers to the open questions (security recommendation)
- Open question 1 (B14 key location): preferred is a non-exportable KMS/HSM key (e.g. Azure Key Vault or AWS KMS) that the release job signs with through GitHub OIDC federation, so the key never sits on the runner. The default (protected `module-release` environment secret, required reviewer, protected tags only) is acceptable as interim with SEC-50-15. Rotation and revocation use the B3 keyring.
- Open question 2 (C8 culture analyzers): keep them out of this WP. Recommend a follow-up that enables CA1307, CA1309 and CA1310 as errors in `src` first: culture-sensitive comparisons of identifiers, roles or SIDs are a bypass class (for example Turkish-I casing). CA1304, CA1305 and CA1311 are formatting-only and lower priority.
- Owner question (B4 Lakehouse route move): move it. Iceberg REST clients take the catalog base URI, so `/modules/lakehouse/iceberg` is a configuration change for them. The namespace stops modules from shadowing core routes and keeps the authorization and audit boundary per module. No production deployment exists, so the break is acceptable (SEC-50-08).

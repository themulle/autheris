# WP-SIMPL-43 Authentication and authorization core (direct and upstream-header modes)
Status: Ready for implementation
Parent: [plan](../2026-11-05-plan-project-simplification.md) (supersedes the plan section of WP-SIMPL-30; amends WP-SIMPL-16) | Issues: #482, #489 | Owner decisions: OD-21, OD-22 (core access model, owner clarification 2026-11-05), OD-27 (on-premises AD groups via SCIM), OD-26 (write grants consume the same groups), OD-9, OD-5 | Advisories: GHSA-x8g9-cm3h-p6jq (see private advisory) | Security conditions: SEC-SIMPL-02, 30 (amended), 32, 33, 34, 36 (re-scoped), 48 (re-scoped); new SEC-SIMPL-99..110 proposed in section 10 for Phase 3

## 1. Goal and outcome
Make authentication and authorization one documented core pipeline: **authenticate (scheme) -> normalize claims (`ClaimsNormalizer`) -> resolve realm, tenant, user SID and AD group SIDs -> authorize (policies, ReBAC, consent, access profiles, row filters, masks, column deny, Envoy ext_authz)**. Both deployment modes are first-class and explicitly configured: `Direct` (user authenticates at Autheris) and `Upstream` (trusted proxy passes the identity in headers, ForwardAuth). Outcome, objectively checkable:
- The same user in the same AD groups gets the same `SecurityContext.UserSid`/`GroupSids` (canonical SIDs) via JWT (Entra, AD FS), Negotiate, Basic, ForwardAuth, WebSocket and MCP; one parameterized test proves it.
- Unresolvable groups never shrink to "no groups": the request is marked degraded and data access is denied (fail closed).
- Startup fails on every unsafe mode combination listed in step 3; identity headers never override or join a direct credential.
- #482 and #489 are closed; dead auth code (section 4.4) is deleted; Envoy ext_authz stays core and uses the request `SecurityContext`.
- OD-27: an Entra-authenticated user whose on-premises AD group is not in the token gets that group from SCIM provisioning (correlated user, effective groups = token groups UNION SCIM groups); a stale sync, an ambiguous correlation or a deprovisioned user never grants access, and deprovisioning is effective on all nodes before the SCIM response returns.

## 3. Scope
### In scope
- Inventory and single selection logic for all schemes: JWT Bearer Entra (`Bearer`), AD FS (`BearerAdfs`), MCP OAuth metadata scheme, WebSocket token validation, Basic (+ dev cookie session), Negotiate (Kerberos/NTLM), ForwardAuth, SCIM (machine scheme), TOTP step-up (second factor, not a scheme), TestAuth (compile-gated).
- `Authentication:Mode` (`Direct` | `Upstream` | `Both`) with fail-closed startup validation.
- One identity pipeline service used by HTTP and WebSocket; canonical SID format; group SID resolution per mode incl. Entra overage, Kerberos PAC/LDAPS, ForwardAuth group header trust, SCIM-provisioned groups; caching and invalidation; fail-closed degraded handling.
- #482 (tenant-prefixed header roles; delete unregistered `AdminIpAllowlistMiddleware`/`DiagnosticsEndpointAuthMiddleware`), #489 (caller labels, CSRF scheme, ForwardAuth SID charset/length, read-only GET route test, privileged-SID check on all schemes, unused justification header).
- Envoy ext_authz alignment; dead code and duplication removal inside the auth area (section 4.4).
- OD-27 SCIM supplement (steps 13-18): SCIM provisioning of on-premises AD users, groups, memberships (nested groups), identity correlation, effective groups, SID-canonical group ids with display names, sync staleness, deprovisioning, SCIM endpoint hardening. Autheris only exposes the SCIM endpoint; the sync process (Entra provisioning, Cloud Sync/Connect-based flows, customer AD-to-SCIM job) is external.
- Doc-plan consequences for WP-SIMPL-30 (cancelled) and WP-SIMPL-16 (Mesh kept).
### Out of scope
- New authentication methods (PATs, API keys, SAML, OIDC login UI). `X-API-Key` stays a quota hint only (`ClientTierResolver.cs:197`), never an identity.
- Distributed revocation/lockout store (#489 "in-memory revocation" item): owned by WP-SIMPL-15 / SEC-SIMPL-34; this WP only references it.
- OD-9 admin scoping (WP-SIMPL-36 sub-package 0); #469 (WP-SIMPL-36 sub-package 1).
- Removing the `Autheris.Api -> Autheris.Extensions` project reference (was carried by WP-SIMPL-30): moves to the last module WP (WP-SIMPL-29), see Decisions.
- Feature docs (owner rule: only on request).
- Building or shipping any AD-to-SCIM sync agent, LDAP polling of on-premises AD by Autheris for the Entra realm, SCIM `/Bulk` (stays `supported=false`, `ScimDiscoveryEndpoints.cs:24`), SCIM `filter` beyond the current guard.

Depth limit exceeded -> Degraded (`scim_nesting_too_deep`). `ScimStoreRoleProvider` (:32) switches to this method and returns SIDs, never group ids or names.
15. **Identity correlation (PR 5b).** New `src/Autheris.Application/Identity/ScimIdentityCorrelator.cs` (`ValueTask<CorrelationResult> CorrelateAsync(ClaimsPrincipal normalized, IdentityRealm realm, TenantId tenant, CancellationToken)`), called by `GroupSidResolver` for every realm with `Provisioning=Scim`. Keys, in precedence order, each used only when the token carries it:
   1. on-premises user SID: Entra optional claim `onprem_sid` (or `primarysid`/WS-Fed `primarysid` for AD FS) == `object_sid`;
   2. `onPremisesImmutableId` claim (when emitted by a claims mapping policy) == `immutable_id`;
   3. Entra `oid` == `entra_object_id` or SCIM `externalId` (Entra provisioning default mapping `objectId -> externalId`);
   4. UPN (`upn`, else `preferred_username`) == `upn` or `userName`, ordinal ignore case; only when realm option `Scim.AllowUpnCorrelation=true` (default false: UPNs can be reused).
   Rules: evaluate all available keys; every key that matches must match the **same** SCIM user, and each key may match at most one user; otherwise `Ambiguous` -> Degraded (`scim_correlation_ambiguous`), audit `IdentityCorrelationAmbiguous` (required audit). A higher-precedence key present in the token that matches nobody while a lower key matches someone is also `Ambiguous` (prevents correlating to a different person by a weaker key). No match -> `NotProvisioned`: Degraded when realm option `Scim.RequireCorrelation=true` (default true for realms with `Provisioning=Scim`), else token groups only. A matched user with `Active=false` or locked -> 403 for the request (deprovisioned). The correlation result (SCIM user key) is cached with the groups (step 9 cache, same key and epoch).
16. **Effective groups (PR 5b).** `GroupResolution.GroupSids = token groups (step 6, incl. Graph overage) UNION SCIM effective group SIDs (step 14)`; `Source` lists both. Status is Degraded if either part is Degraded. All consumers read only `SecurityContext.GroupSids`: consent (`GranteeMatcher`), access profiles, row filters, masking, column deny, write grants (OD-26), `RebacEndpointFilter`, usage per AD group (WP-SIMPL-42), authorized discovery (WP-SIMPL-41), Envoy ext_authz (step 11). The architecture test `No_code_reads_raw_groups_claims_outside_pipeline` enforces it.
17. **Staleness and deprovisioning (PR 5b).** Every successfully authenticated SCIM request (any method; Entra provisioning queries each cycle even without changes) updates `last_contact_at`; every successful write updates `last_write_at` (one upsert, throttled to once per 30 s per realm per node). Realm option `Scim.MaxSyncAgeMinutes` (default 180, range 10..10080) and `Scim.StaleSyncBehavior` = `Degrade` (default: data access denied for users of the realm) | `DropScimGroups` (token groups only; startup warning that group-scoped row filters, masks and column denies assigned to SCIM-only groups are then not applied; Phase 3 decides whether to permit it). The sync state is read through a 30 s cache. Deprovisioning (`DELETE /Users`, `PATCH active=false`, group `DELETE`, member remove): the store write and membership removal commit in one transaction (`active=false` now also deletes memberships), then the node publishes `IdentityGroupsChanged` (step 9) **and** increments a per-realm identity epoch in the governance store; the cache key includes the epoch, so a node that missed the event cannot serve a pre-deprovisioning entry (GHSA-x8g9-cm3h-p6jq: invalidation must be cluster-wide, not node-local as at `ScimService.cs:166,213,314`). The SCIM response is sent only after the commit and the epoch increment.
18. **SCIM endpoint hardening (PR 5c).** (a) Authentication stays per-realm secret (`ScimAuthenticationHandler`, constant-time, >= 32 chars); the realm in the path must equal the realm of the secret (verify existing check at :85-100). (b) `Scim.AllowedIpRanges` becomes mandatory outside Development (startup failure instead of the warning at `IdentityRealmsScimOptionsValidator.cs:66`). (c) Rate limit: realm option `Scim.RequestsPerMinute` (default 600) via `IRateLimiterService.CheckPostAuthSidAsync` keyed `scim-client:{realmId}`, 429 with `Retry-After`; existing mass-change guard and quarantine stay. (d) Audit: replace `AuditConfigChanged` on SCIM writes with `ScimUserProvisioned`, `ScimUserUpdated`, `ScimUserDeprovisioned`, `ScimGroupProvisioned`, `ScimGroupDeleted`, `ScimGroupMembershipChanged` (one event per added/removed member: realm, group SID, user key, operation) written with `IAuditWriter.RecordRequiredAsync` inside the request (write refused when audit fails, consistent with WP-SIMPL-36 sub-package 2). (e) Request body limit 1 MiB and max 1000 members per PATCH (400 `tooMany`). (f) SCIM routes accept only the `Scim` scheme in every `Authentication:Mode` (never ForwardAuth or JWT).

## Decisions taken in this spec
1. Canonical subject ids are SID strings: AD SIDs, and Entra cloud SIDs (`S-1-12-1-*`) derived from object ids; group grants match only canonical SIDs (OD-22).
2. `Authentication:Mode` with three values; `Both` rejects ambiguous requests instead of choosing one identity.
3. ForwardAuth trusted peers are a ForwardAuth-specific list (not inherited from `ReverseProxy.KnownProxies`).
4. ForwardAuth group names (non-SID) are not supported; use `GroupSource=Resolver` for directory lookup. Non-canonical header values fail the request.
5. Unresolved groups mean Degraded and deny data access (a missing group could drop a group-scoped row filter, mask or column deny).
6. The Api -> Extensions reference removal goes to WP-SIMPL-29, not here (not authentication or authorization).
7. #482/#489 are owned by this WP (WP-SIMPL-36 does not list them); the distributed revocation item stays with WP-SIMPL-15/SEC-SIMPL-34.
8. OD-27 nested groups: stored as group-to-group edges and flattened at read time (recursive CTE, depth 32, cycle-safe), so both flattening and non-flattening pushers work and a nesting change needs no fan-out rewrite.
9. OD-27 correlation precedence: on-premises SID > immutable id > Entra object id / externalId > UPN (opt-in); all present keys must agree; an unmatched stronger key blocks weaker keys.
10. OD-27 SCIM data lives in the same realm as the Entra login realm (realm-bound `/scim/{realmId}`); no cross-realm linking.
11. OD-27 staleness is measured by last authenticated SCIM contact (not last write), default max age 180 min, default behaviour `Degrade`.
12. OD-27 `active=false` removes memberships immediately (same as delete) in addition to the existing lock.

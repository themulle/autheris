## 1. Executive Summary & Problem Statement

### 1.1 The Problem

When running Autheris on Linux containers connecting to Microsoft SQL Server with Windows Authentication (NTLM) via `Microsoft.Data.SqlClient` 7.1.1 and .NET managed NTLM (`System.Net.Security.UseManagedNtlm = true`), authentication fails under Extended Protection for Authentication (EPA / "Erweiterter Schutz"):

1. **Null Channel Binding in NTLM Handshake:**
   - In `Microsoft.Data.SqlClient` 7.1.1, `SspiContextProvider` is invoked during TDS login negotiation without receiving or propagating the underlying TLS Channel Binding Token (CBT).
   - In Autheris's `ManagedNtlmSspiContextProvider`, `NegotiateAuthentication` is instantiated without configuring `NegotiateAuthenticationClientOptions.Binding`.
   - Consequently, the outgoing `NTLM-AUTHENTICATE` message generated by .NET contains 16 null bytes (`00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00`) for the target information AV pair `MsvAvChannelBindings` (AV pair 10, RFC 5929 / MS-NLMP).

2. **Rejection by SQL Server Enforcing Extended Protection:**
   - When SQL Server has Extended Protection for Authentication (EPA) set to `Required` (or `Allowed` over a TLS-encrypted connection), the SQL Server security subsystem verifies the client's Channel Binding Token against the actual TLS session.
   - Finding 16 zero bytes instead of the expected cryptographic hash (MD5 over `gss_channel_bindings` with `tls-unique` or `tls-server-end-point`), SQL Server rejects the authentication attempt:
     ```
     SqlException (0x80131904): Login failed. The login is from an untrusted domain and cannot be used with Integrated authentication.
     Error Number: 18452, State: 1, Class: 14
     ```

3. **Production Impact:**
   - Enterprise environments requiring EPA compliance to prevent NTLM relay and MITM attacks cannot use containerized Autheris data sources with NTLM authentication.
   - Administrators previously faced only the option of weakening SQL Server security (setting EPA to `Off`) or migrating to Kerberos Keytabs.
   - With valid Channel Binding passed to `NegotiateAuthentication`, NTLM authentication under EPA succeeds completely.

### 1.2 Target Audience & Stakeholders
- **Enterprise Platform Administrators:** Operating Autheris in Kubernetes and container runtimes connecting to enterprise SQL Server databases where EPA is mandated by corporate compliance.
- **Security Operations & InfoSec:** Requiring protection against credential reflection and relay attacks while supporting secure integrated authentication.
- **Site Reliability Engineers:** Requiring transparent, actionable diagnostics if TLS channel binding extraction is unsupported or fails, rather than generic domain errors.

## 2. Strategic Fit, Architecture & Gatekeeping

### 2.1 Anti-Pattern Gatekeeping & Safe Alternatives

| Approach | Hazard / Vulnerability | Architectural Evaluation |
|---|---|---|
| Auto-disabling EPA or leaving CBT zeroed | Relies on weakening server security policy; leaves connections vulnerable to relay attacks. | **REJECTED.** Violates Zero-Trust principles. |
| Waiting for upstream SqlClient PR | Unpredictable release timelines for `Microsoft.Data.SqlClient`; blocks current deployments. | **REJECTED as sole fix.** We fix this in Autheris immediately while maintaining upstream compatibility. |
| **Extract TLS Channel Binding via Managed SNI Reflection** | Access underlying `SslStream` established by SqlClient managed SNI during connection initialization, extract `TransportContext.GetChannelBinding()`, and supply it to `NegotiateAuthenticationClientOptions.Binding`. Guard with SqlClient version verification. | **APPROVED.** Fixes EPA handshakes transparently and securely; gracefully falls back to clear diagnostics if unsupported. |

### 2.2 Mechanism & Protocol Specification

- **Channel Binding Extraction:**
  - In `Microsoft.Data.SqlClient` managed SNI on Linux, when a connection begins authentication, the TLS handshake has already completed on `TdsParserStateObjectManaged._sessionHandle` (`SniTcpHandle` or `SniNpHandle`).
  - The underlying TLS stream `SniTcpHandle._sslStream` is a `System.Net.Security.SslStream` (`SniSslStream`).
  - Via `SslStream.TransportContext`, Autheris retrieves the active `ChannelBinding`:
    - For TLS 1.3: `ChannelBindingKind.Endpoint` (`tls-server-end-point`).
    - For TLS 1.2 and earlier: `ChannelBindingKind.Unique` (`tls-unique`), falling back to `ChannelBindingKind.Endpoint` if `Unique` is unsupported or unavailable.
- **NegotiateAuthentication Integration:**
  - Before the first call to `_negotiateAuth.GetOutgoingBlob` (during context generation), `NegotiateAuthenticationClientOptions.Binding` is assigned with the extracted `ChannelBinding`.
  - .NET's `NegotiateAuthentication` generates the proper `MsvAvChannelBindings` structure in the NTLM-AUTHENTICATE message.

## 3. User Stories & Acceptance Criteria

### US-1: TLS Channel Binding Extraction in Managed NTLM
*As an Autheris administrator connecting to an EPA-enforced SQL Server, I want Autheris to automatically extract the TLS session channel binding and include it in the NTLM authentication handshake so that integrated authentication succeeds.*

- **AC-230-1.1:** In `ManagedNtlmSspiContextProvider`, when initiating negotiation (`incomingBlob.IsEmpty`), the provider extracts the TLS channel binding from the active `SslStream` associated with the connection's `SspiContextProvider._physicalStateObj`.
- **AC-230-1.2:** The extracted `ChannelBinding` is assigned to `NegotiateAuthenticationClientOptions.Binding`.
- **AC-230-1.3:** Both `ChannelBindingKind.Unique` (for TLS <= 1.2) and `ChannelBindingKind.Endpoint` (for TLS 1.3 / fallback) are supported.
- **AC-230-1.4:** Any allocated `ChannelBinding` handle is safely managed and disposed without handle leaks.

### US-2: Version Guard & Actionable Extraction Diagnostics
*As an SRE, if reflection fails or the SqlClient version is incompatible, I want actionable diagnostic logs and recorded status rather than silent nulls.*

- **AC-230-2.1:** The reflection extraction logic verifies the `Microsoft.Data.SqlClient` assembly version (supporting 7.x).
- **AC-230-2.2:** If reflection fails, the underlying stream is unencrypted, or the version is unsupported, an actionable diagnostic status is recorded on the provider and logged without crashing or leaking credentials.
- **AC-230-2.3:** A mockable channel binding accessor/hook is available for unit and security tests.

### US-3: Enhanced Error Classification for SqlException 18452
*As an operator encountering error 18452, I want the error message to explicitly identify that missing or mismatched TLS Channel Binding under Extended Protection is the primary cause.*

- **AC-230-3.1:** `SqlServerWindowsAuthConfigurator.ClassifyOpenException` updates the diagnostic message for Error 18452 to clarify that `Microsoft.Data.SqlClient` did not provide TLS Channel Binding and the server enforces Extended Protection (EPA).
- **AC-230-3.2:** The error message preserves all existing diagnostic indicators (`SqlNumber=18452`, `SqlState`, `SqlClass`), mentions EPA, CBT, TLS encryption (`Encrypt=True`), and provides concrete remediation steps.
- **AC-230-3.3:** Circuit breaker (`SqlLoginCircuitBreaker`) continues to correctly trip on `LoginRejected` for 18452.

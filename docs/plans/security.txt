[OPS-01] MEDIUM | security | GitHub PAT stored in plaintext in git remote URL
  Location : /root/autheris/.git/config (remote "origin" url) — local only, not committed
  Problem  : The origin URL embeds a classic GitHub personal access token
             (https://x-access-token:ghp_***@github.com/...). It is printed by
             `git remote -v`, copied into worktrees/clones' config, and visible
             to every process/agent with read access to the checkout.
  Scenario : Any tool output, log, CI artifact or support bundle that captures
             `git remote -v` or .git/config leaks a token with repo write access.
  Fix hint : Rotate the token; use a credential helper (gh auth / git-credential-store
             with 0600 perms) or a fine-grained, short-lived token; strip the
             token from the remote URL.

[MISC-01] MEDIUM | security | docker-publish workflow_dispatch from any branch can overwrite release/latest image tags
  Location : .github/workflows/docker-publish.yml:10-15, 36-40, 121-145, 177-186
  Problem  : The job condition only gates workflow_run events; workflow_dispatch runs on whatever ref the
             dispatcher selects (checkout uses github.sha of that branch). The tag computation accepts any
             INPUT_TAG matching [a-zA-Z0-9_.-]+, including "v1.0.0"/"latest", and adds :latest and
             :getting-started. The image is pushed BEFORE the cosign identity check (which only accepts
             refs/heads/main|refs/tags/v.+) - the verify step fails, but the registry tags are already moved.
  Scenario : A contributor with write access dispatches the workflow on an unreviewed feature branch with
             tag=v1.0.0. ghcr.io/.../autheris:v1.0.0, :latest and :getting-started now point to an image built
             from unreviewed code (signed with a feature-branch identity). docker-compose consumers pulling by tag
             receive it; only consumers pinning digests or enforcing the Kyverno identity are protected.
  Fix hint : Add `if: github.event_name != 'workflow_dispatch' || github.ref == 'refs/heads/main'` (or require
             refs/tags/v* for v*/latest tags), refuse v*/latest tags on dispatch, and use a protected environment
             with required reviewers for the push job. Push by digest first, verify, then retag.

[MISC-02] MEDIUM | security | release.yml workflow_dispatch builds an arbitrary branch and publishes it under any tag
  Location : .github/workflows/release.yml:7-12, 24-27, 129-135
  Problem  : On workflow_dispatch the checkout has no `ref`, so binaries are built from the dispatched branch,
             while the release is published as `tag_name: inputs.tag`. If the tag does not exist GitHub creates it
             on the default branch (source/binary mismatch); if it exists, action-gh-release updates the existing
             release and overwrites assets with the same name. Nothing checks that github.ref matches the tag.
  Scenario : Dispatch on branch `feature/x` with tag=v1.0.0 -> the published v1.0.0 Autheris-linux-x64.tar.gz
             and SHA256SUMS (cosign-signed, SLSA-attested) are replaced by binaries from unreviewed code while the
             git tag still points to the reviewed commit. Provenance looks valid because it is the same workflow.
  Fix hint : Check out `ref: refs/tags/${{ inputs.tag }}` on dispatch and fail if the tag does not exist or
             github.ref is not a tag; set `overwrite_files: false` / fail if the release already exists; protect
             with an environment requiring approval.

[VF-01] HIGH | security | SQL virtual filter tenant binding (SR-L-11) bypassed by alias shadowing in a subquery
  Location : src/Autheris.Application/VirtualFilters/SqlFilterCompiler.cs:279-305 (RequireTenantBinding/IsTenantBound),
             used by Validate (:218) and BindTenant (:351); tables collected via SqlQueryAnalyzer.EnterTableName (all depths)
  Problem  : Tenant binding is checked purely by qualifier text: for every tenanted referenced table (including tables
             inside IN/EXISTS subqueries) it looks for a TOP-LEVEL WHERE conjunct "<alias>.<tenantcol> = '{{tenant}}'".
             Tables are matched by alias/table-name only, so an inner table that re-uses the alias (or the bare table name)
             of an outer, correctly bound table is considered "bound" although nothing restricts it. Subqueries are not
             rejected by ValidateAstPredicates (no case -> accepted).
  Scenario : Tenant-A filter author stores
               from s.orders x where x.tenant_id = '{{tenant}}' and target.id = x.id
                 and target.k in (select x.k from s.orders x where x.secret like 'A%')
             Both s.orders references resolve to qualifier "x"; the outer conjunct satisfies both. The inner scan reads all
             tenants' rows -> the filter is evaluated over other tenants' data (wrong/over-permissive rows) and works as an
             existence oracle over another tenant's columns (visible target rows reveal whether B's data matches).
  Fix hint : Bind per table occurrence, not per qualifier: reject duplicate aliases/bare names across scopes, require the
             tenant conjunct in the WHERE of the query specification that owns the table (walk scopes on the AST), or
             reject subqueries in sql definitions; alternatively inject the tenant predicate on the AST for every
             NamedTableSource instead of checking author text.

[EXT-01] MEDIUM | security | OData $metadata CSDL cache key ignores per-caller column visibility (hidden column names leak)  [RESOLVED]
  Location : src/Autheris.Extensions/OData/ODataHandler.cs:56-67 (key), :178-187 (column filtering)
  Problem  : The CSDL cache key is "odata:csdl:{tenant}:s{structureVersion}:{visibilityHash}" where visibilityHash is
             CatalogVisibleBitSet.ComputeSha256 over the visible TABLE IDENTIFIERS only. The cached XML, however, is built
             from per-caller column-filtered metadata (Deny columns removed, keys restricted via TableKeyVisibility).
  Scenario : User A (full column access) and user B (column "salary"/"ssn" = Deny) in the same tenant can see the same
             set of tables. A requests /odata/$metadata first -> XML with all columns is cached for 60 s under the shared
             key. B's request hits the same key and receives A's CSDL including names/types/keys of columns B is denied
             (and vice versa B's reduced CSDL is served to A -> wrong schema, client breakage).
  Fix hint : Include the per-table allowed-column set (or a hash over table+allowed columns+keys) in the cache key, or
             key the CSDL cache by the same tenant+principal key used for the authorized-tables cache.

[GQL-01] MEDIUM | security | InvoiceItem DataLoader falls back to raw (unmasked/denied) values and misaligns rows after in-memory RLS  [RESOLVED]
  Location : src/Autheris.Application/Services/BatchRelationLoader.cs:174-196 (called from src/Autheris.GraphQL/Loaders/InvoiceItemDataLoader.cs:30, Types/InvoiceTypes.cs:18)
  Problem  : After GovernedConnectorReader.Apply (which strips Deny columns and, without RLS pushdown, DROPS rows via FilterRows), the

[EXT-02] LOW | security | OData authorized-tables cache keyed only by tenant+SID (ignores roles/groups/consents; null SID collides)
  Location : src/Autheris.Extensions/OData/ODataHandler.cs:139-143, :199-203
  Problem  : The list of authorized (column-filtered) tables is cached 60 s under "odata:tables:{tenant}:{sid}". The access
             decision (CheckTableAccessAsync) depends on the full principal (roles, group SIDs, ABAC claims, plugin role
             enrichment, consent grants), none of which is part of the key. GetUserSid() may also return null, in which case
             every SID-less principal of the tenant shares the key "odata:tables:{tenant}:".
  Scenario : (a) A user's token with an elevated/break-glass role populates the cache; a later token of the same SID without
             that role still gets the elevated table/column list for 60 s. (b) A consent/role revocation is not reflected in

             without sub/oid/appid) see each other's authorized schema.
  Fix hint : Key by a principal fingerprint (sid + sorted roles + group SIDs + relevant claims) and refuse caching when SID is

[EP-01] MEDIUM | security | Unmasked profile approval skips data-owner check when the pattern matches no catalogued table  [RESOLVED b1ae7a42]
  Location : src/Autheris.Api/Endpoints/GovernanceEndpoints.Access.cs:472-492
  Problem  : ApproveProfileAssignmentAsync enforces "route (b)" (approver must be the data owner/delegate of every matched
             table) by iterating the tables that the profile pattern matches *right now* in ITableMetadataRepository. If the
             pattern matches zero tables (e.g. "finance.*" before discovery/catalog sync, a typo-tolerant wildcard, or a schema

             catalogued), GovernanceAdmin B (not the HR data owner) approves -> 200. After catalog sync, U reads hr_new.salaries
             unmasked; the HR data owner never approved.
  Fix hint : Fail closed when an individual Unmasked approval matches zero tables (403 DATA_OWNER_APPROVAL_REQUIRED), scope the
             table list to the request tenant, and re-evaluate owner approval when new tables start matching (or forbid wildcard
             patterns for individual Unmasked grants).

[INF-01] HIGH | security | Consent revocation silently lost cluster-wide when the Redis epoch INCR fails or Redis is disconnected
  Location : src/Autheris.Infrastructure/Cache/EpochValidationService.cs:553-578 (and 78-86, 157-193)
  Problem  : InvalidateEpochAsync only bumps the node-local _epochs and swallows any failure of the Redis INCR (and skips it
             entirely when !IsConnected). Every subsequent validation that reaches Redis (GetCurrentEpochCoreAsync /
             ReconcileEpochAsync) overwrites _epochs[key] with the UNCHANGED Redis value, and ConnectionRestored clears the
             local bump altogether. The revoke caller (repositories after commit) is not told the invalidation failed.
  Scenario : Consent for table T is revoked while Redis times out on INCR (or during a short disconnect). Redis still holds
             epoch 5, all L1/L2 consent decisions were cached with epoch 5. On the next authoritative read (same node or any
             other node) epoch 5 == cached epoch 5 -> the revoked ALLOW decision (incl. unmasked column access) is served from
             L1/L2 until its TTL expires; L2 entries in Redis are not deleted either.
  Fix hint : Fail closed: on INCR failure / disconnect, record a pending "dirty" table set that is replayed (INCR) on reconnect
             before any epoch is trusted, keep the local bump as a floor in _highestSeenRedisEpoch (so Redis values <= floor are
             treated as rollback), and/or propagate the failure to the revoke caller (retry / outbox).

  Location : src/Autheris.Infrastructure/Persistence/SqliteGovernanceRepository.Audit.cs:717,785; PostgreSqlGovernanceRepository.Audit.cs:874,949,1155-1156; SqlServerGovernanceRepository.Audit.cs:933,1007,1212-1213

[API-01] MEDIUM | security | Entra ID tokens accepted as API access tokens (nonce heuristic only), bypassing read-only scope restriction  [RESOLVED eaaf7552]
  Location : src/Autheris.Api/Security/EntraTokenPolicy.cs:36-44,49-59 ; src/Autheris.Api/Extensions/GatewayServiceCollectionExtensions.cs:313-314
  Problem  : The JwtBearer scheme accepts the Entra ClientId as a valid audience (needed for v2 access tokens), so an OIDC ID token
             issued for the gateway's own app registration (aud = ClientId) passes signature/issuer/audience/lifetime validation.

             to the gateway client with scope "openid" and no nonce, takes the returned id_token and sends it as
             "Authorization: Bearer <id_token>". The token is accepted as a full (non read-only) user token, so
             ReadOnlyTokenMiddleware no longer restricts the caller to the query endpoints (mutations, admin/REST paths

             tokens never carry them), and/or require "scp" for user (non-app) tokens; drop the nonce heuristic as the only

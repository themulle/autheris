## 2. Cross-cutting conditions (all stages)

- **SEC-SIMPL-01 (advisory confidentiality, all simplification documents, commits, PR bodies, CHANGELOG, test names).** The repository is public and holds private draft advisories. Documents and commits refer to an advisory only by GHSA id and a neutral title (for example "GHSA-xxxx: input validation hardening"). They must not contain exploit details, payloads, affected-parameter names, reproduction steps or root-cause narrative for an unpublished advisory. A CI check (`Docs_and_changelog_contain_no_advisory_detail_markers`, Security) scans `docs/plans/*simplification*`, `docs/plans/simplification/**`, `docs/adr/ADR-019*`, `docs/adr/ADR-020*`, `docs/plans/**` and `docs/adr/**` (all plan and ADR files that mention a GHSA id), and `CHANGELOG.md`. It fails with the file and line when a line containing `GHSA-` also contains marker words ("payload", "exploit", "PoC", "bypass via", "root of", "root cause", "class of") or when a test name matches `GHSA`-adjacent defect wording; the owner of the check is WP-SIMPL-02. For every GHSA id a document gives only the id and the neutral title of `docs/plans/simplification/advisories-overview.md`; test names for advisory regressions are neutral (`AdvisoryRegressionTests.Ghsa_<first4>_<last4>_regression`, Category=Security) and the details live in the private advisory. Existing advisory detail in tracked plan and ADR text is neutralized in this program (R17); new text must comply.
- **SEC-SIMPL-02 (fail closed is the default of every deletion).** Each WP that removes a provider, option, scheme, endpoint or module declares in its PR description: (a) the old config keys and the exact failure mode when they are still present, (b) the old routes and their expected status (404), (c) the control(s) the removed code enforced and where the replacement enforces them. A PR without these three items fails Phase 5.
- **SEC-SIMPL-03 (no security test deleted without equivalent).** A security test (`[Trait("Category","Security")]` or in `Security/**`, or named in ARCH-MNT/ADR-016/ADR-017 conditions) may be deleted, moved or renamed only if the PR adds a coverage-map row (see SEC-SIMPL-60) pointing to the equivalent test. The test count of category Security must not decrease between WP merges unless the map lists the removed test with the reason "feature deleted" and the deleted feature's WP.
- **SEC-SIMPL-04 (secrets and defaults).** No simplification WP may introduce a default secret, a default password, `TrustServerCertificate=true`, `sslmode=disable`/`prefer`, or an anonymous default in any shipped config, compose file, Helm values or generated reference.
- **SEC-SIMPL-05 (stage order is binding).** Stage 1 (SQLite governance removal, WP-SIMPL-11) completes before WP-SIMPL-12 and WP-SIMPL-19; WP-SIMPL-46 (single decision point) precedes WP-SIMPL-14 (after WP-46 PR 1-5, the WP-43 Envoy step and WP-45 PR 1-3) and every WP part that consumes decisions (41 PR 3+, 42 PR-3b, 43 Envoy step, 45 PR 4-6, 47); WP-45 PR 1-3 merge before WP-46 PR 1 and contain no decision logic outside the decision point (DML stays denied until WP-46 PR 2); WP-SIMPL-19 (contract suite) precedes WP-SIMPL-20; module host (WP-SIMPL-25) precedes every module WP (27..29; WP-SIMPL-26 is OData core hardening, WP-SIMPL-30 is cancelled by OD-21; the runtime-vs-compile-time loading decision is taken in WP-27, OD-37); no endpoint-bearing code moves into a module before SEC-SIMPL-40..49 tests exist. Reordering needs a new Phase 3 addendum.

## 3. Stage 1: SQLite governance store removal (WP-SIMPL-11, REQ-SIMPL-12)

Gates: WP-SIMPL-11. Mandatory regression guard: nothing that persists audit, tenant or migration state may lose a guarantee because its SQLite twin is deleted.

- **SEC-SIMPL-10 (fail-closed provider guard).** `Provider=Sqlite` (any case, any whitespace, `Governance:Provider`, and a connection string with `Data Source=*.db`/`:memory:`/`Filename=`) fails host start before DI resolution of any repository. The error names OD-1 and the migration guide, contains no connection string value, and exits non-zero. There is no fallback to PostgreSQL, SQL Server or an in-memory store, also not in Development or Testing environments. Unknown provider strings fail the same way. Reuse `LegacySwitchGuard`; the guard runs in `FederationMaskingStartupCheck`-style early startup, not lazily.
- **SEC-SIMPL-11 (missing provider fails, never defaults silently).** With the key absent the default is PostgreSQL only if a PostgreSQL connection string is present; absent connection string fails startup. The shipped default changing from SQLite to PostgreSQL must not turn an empty config into a successful start with a localhost trust-auth instance.
- **SEC-SIMPL-12 (audit hash chain preserved).** After removal, `AuditChainAnchorStores`, `AuditChainViolationGate` and the batch insert path keep: append-only inserts, no UPDATE/DELETE on audit rows (database privilege or trigger as today), chain verification on read/export, and anchor persistence. Removal of the SQLite anchor store must leave no code path where an anchor store resolves to a no-op. If `IAuditChainAnchorStore` has no registration for the configured provider, startup fails.
- **SEC-SIMPL-13 (tenant predicate in every governance query).** The PostgreSQL and SQL Server repositories keep a tenant predicate in every query touching tenant-scoped tables; the reflection/arch test that enumerates governance queries (or the SQL text scan) must run against both remaining families and must not have contained the SQLite family as its only coverage for any table. Missing tenant id still throws, never selects across tenants.
- **SEC-SIMPL-14 (connection TLS policy).** PostgreSQL requires `SSL Mode=VerifyFull` (or `VerifyCA` with documented reason) outside Development; SQL Server requires `Encrypt=True` and `TrustServerCertificate=False` outside Development. A startup validator rejects weaker settings in non-Development environments with a message that names the setting, not the value of the connection string. Compose files for local quickstart may relax only via an explicit `Development` environment and say so in a comment.
- **SEC-SIMPL-15 (no default credentials).** `deploy/podman-compose.yaml`, Helm `values.yaml`, `governance-migration-job.yaml`, governance-seed and benchmark containers contain no literal database password. Compose uses an env-file/secret the operator must supply (the quickstart script generates a random one; the compose file fails with `${POSTGRES_PASSWORD:?set POSTGRES_PASSWORD}`); Helm requires `existingSecret` or fails `helm template` through `required`. Test: `Deploy_files_contain_no_default_database_password`.
- **SEC-SIMPL-16 (migration runner forward-only, v1.5.0 frozen base).** The PostgreSQL and SQL Server runners keep: checksum verification of applied steps, refusal to run when an applied step's checksum changed, refusal to downgrade, and the v1.5.0 base unchanged. The `governance-immutability` workflow stays and its path filter is extended to the new shared-core and fragment-provider files (WP-SIMPL-20). Deleting `Migrations/Steps/sqlite` must not touch `postgres`/`sqlserver` step files (verified by a byte-identical check of both folders in the PR).
- **SEC-SIMPL-17 (shared-state triage).** Types in the triage list (`SqliteSchemaCatalogReader`, `SqliteColumnMetadataReader`, `SqliteTypeAffinity`) are removed only with a recorded proof that no governance path uses them (grep and compile). If any shared AST or masking code used `SqliteTypeAffinity` for type-based masking decisions, the replacement must default unknown types to the most restrictive treatment (mask/deny), not pass-through.
- **SEC-SIMPL-18 (operator impact).** CHANGELOG says "unsupported provider fails startup" and links the migration guide; no mention of how to disable the guard. No env var or flag may re-enable SQLite governance.

## 4. Stage 2: structural refactoring

### 4.1 Unified governance persistence (WP-SIMPL-19, WP-SIMPL-20, REQ-SIMPL-05; gates 19, 20)

- **SEC-SIMPL-20 (contract suite first).** WP-SIMPL-19 lands the repository contract suite, including tenant isolation, audit append-only and soft-delete visibility, against the existing PostgreSQL and SQL Server implementations before any merge into the core (WP-SIMPL-20). The suite must pass on both engines with identical expectations; a divergence is a bug to fix before refactoring, not a skipped case.
- **SEC-SIMPL-21 (parameterization only).** The shared core and the SQL fragment provider build statements from constant fragments plus bound parameters. Identifiers (table, column, order-by, schema) come from a closed allowlist of `static readonly` names or from a typed enum, never from request input and never by string concatenation or interpolation of a variable. `FormattableString` is not accepted by the executor; the API takes `string` constants and a parameter bag. Bulk `IN (...)` lists use parameter arrays or table-valued parameters with a bounded count (see SEC-SIMPL-23).
- **SEC-SIMPL-22 (tenant predicate enforced in the shared core).** Tenant scoping is applied by the core (a mandatory `TenantId` argument in the query builder, compile error or runtime throw when absent), not by each fragment. Tables that are intentionally global are in an explicit allowlist with a code comment and a test that fails when the allowlist grows without updating the test expectation.
- **SEC-SIMPL-23 (DoS bounds retained).** Page-size caps, maximum batch sizes and command timeouts of the old repositories move unchanged into the core; the contract suite asserts the caps.
- **SEC-SIMPL-24 (no weaker audit path).** The audit write path stays a separate narrow component (`AuditSqlCore`, batch insert) and is not folded into the generic repository executor; it keeps its own tests (SEC-SIMPL-12). Any change to hash input fields requires an ADR addendum and a chain-compatibility test with v1.5.0 fixtures.
- **SEC-SIMPL-25 (confidentiality in logs).** The shared executor logs statement identifiers/fragment ids and durations only, never parameter values, never raw SQL with inlined values. Exceptions are wrapped without parameter payload.
- **SEC-SIMPL-26 (architecture test).** `ArchitectureTests.Governance_sql_is_built_only_from_constants_and_parameters` (Roslyn or reflection-based source scan) fails on `$"..."`, `string.Format`, `+` concatenation, or `StringBuilder.Append(<non-constant>)` in files of the shared core and fragment providers, except in an explicit, reviewed allowlist (each entry with justification).

Mandatory tests: `GovernanceCoreSecurityTests.Missing_tenant_id_throws_for_every_repository_method`; `GovernanceCoreSecurityTests.Cross_tenant_read_and_write_return_nothing_both_engines` (Testcontainers); `GovernanceCoreSecurityTests.Identifier_allowlist_rejects_unknown_column_and_order_by`; `GovernanceCoreSecurityTests.Injection_payloads_in_filters_are_treated_as_data` (both engines); `GovernanceCoreSecurityTests.Page_size_and_batch_caps_enforced`; `GovernanceCoreSecurityTests.Executor_logs_no_parameter_values`; `ArchitectureTests.Governance_sql_is_built_only_from_constants_and_parameters`. All Security, WP-SIMPL-20.

### 4.2 Deletions (WP-SIMPL-12, 13, 14, 15, 16, 32; authentication consolidation is WP-SIMPL-43)

- **SEC-SIMPL-30 (removed endpoints 404).** For each removed route group (Casbin admin, traffic shadowing admin, Flight-SQL-over-HTTP, Itsm, Backstage, ReBAC tuple API, dev portal (OD-37), FinOps only after WP-SIMPL-42 PR 5; Mesh/Envoy ext_authz is NOT removed, OD-21), a test sends an authenticated request (admin token) and an anonymous one and expects 404 for both, not 401/403 revealing existence and not a fall-through to a catch-all, SPA fallback or static file handler returning 200. The same test asserts the route is absent from the OpenAPI document and the ingress/rate-limit exemption list.
- **SEC-SIMPL-31 (removed config keys fail fast).** Every deleted option section or key is added to `UnknownGatewayKeyGuard` (or `LegacySwitchGuard` when it was a switch) with a message naming the replacement or "removed in vX". Startup fails when any is present with any value, including `false`/empty, because a stale `Enabled=false` copy can hide a stale `true` in another config source.
- **SEC-SIMPL-32 (no security flag silently ignored).** For each of `CasbinOptions.EnforceInQueryPipeline`, `ScimOptions.AllowedIpRanges`, `McpOptions.RequirePiiMasking`, and any other option whose name contains Enforce/Require/Allowed/Deny/Mask/Pii/Tls/Auth: before deletion the PR states whether the option is wired (grep of consumers). If wired, the option stays or the enforced behaviour becomes unconditional and secure (PII masking always on, IP allowlist enforced in the module or the key fails fast). If unwired, deletion is allowed only with the fail-fast guard of SEC-SIMPL-31 so an operator relying on it learns that it never worked. Phase 5 verifies by diff of options classes against consumer search.
- **SEC-SIMPL-33 (Casbin deletion, WP-SIMPL-14, amended by ADR-020).** There is no ReBAC gate and no native policy engine to replace Casbin. Authorization after removal is the access decision point of ADR-020 on the data plane (`IAccessDecisionPoint`, SEC-AZ-01) and `RequireAuthorization` with control-plane role policies on the admin plane; no `RebacEndpointFilter` exists. WP-SIMPL-14 runs only after WP-SIMPL-46 has moved every `IPolicyEnforcementService` consumer (all 18 files, including Envoy ext_authz) to the decision point; the PR proves with `git grep` and an architecture test that no consumer remains, then deletes Casbin. Casbin policies have no data-path replacement: operators re-express them as grants or deny consents (migration guide row), and a configured Casbin key fails fast (SEC-SIMPL-31). Test: `AuthorizationInventoryTests.Every_endpoint_has_authorization_or_is_on_the_public_allowlist` (reflection over `EndpointDataSource`) must be green before and after.
- **SEC-SIMPL-34 (Garnet and shadowing, WP-SIMPL-15).** Deleting the embedded Garnet server must not leave a distributed-state consumer (rate limit, token revocation, replay cache, HITL approvals, audit anchors cache) falling back to per-process memory silently in a multi-replica deployment. Where a consumer needs shared state and none is configured, startup logs an error and (for revocation, replay and rate-limit state) fails closed in non-Development, consistent with ADR-017. Traffic shadowing removal must remove its egress configuration; no residual outbound HTTP client with a target URL option remains.
- **SEC-SIMPL-35 (Flight-SQL-over-HTTP removal, WP-SIMPL-16).** The remaining Arrow export endpoints keep masking, row/column policy and audit on the same path as before; test `ArrowExportSecurityTests.Export_applies_masking_and_audit` stays. No second unauthenticated Arrow listener is opened.
- **SEC-SIMPL-36 (no anonymous fallback for any authentication scheme, WP-SIMPL-43).** No authentication scheme moves out of core (Kerberos/Negotiate, SCIM, TOTP, ForwardAuth, Envoy ext_authz stay core, OD-21/OD-27). The consolidation must not change the default or fallback scheme: `AddAuthentication().DefaultScheme` and `FallbackPolicy` stay explicit; with a scheme missing or misconfigured the pipeline returns 401 or startup fails, never anonymous. Test `AuthSchemeRemovalTests.Missing_scheme_does_not_open_anonymous_path` (Security, WP-SIMPL-43): configure `Authentication:Kerberos` without its prerequisites, host fails fast or all protected endpoints return 401. `EnterpriseClaimsTransformation` must not assume a scheme's claims exist (no default role or group grant when a claim is absent).
- **SEC-SIMPL-37 (rate limiting and ingress exemptions).** The rate limiting exemption list and the ingress/WAF exemption paths (deploy ingress, Helm) are updated in the same PR as each route removal and are tested for consistency: `IngressExemptionTests.Exemption_list_contains_only_existing_routes`. A stale exemption for a removed route is a failure, because a later route reusing the path would inherit the exemption.
- **SEC-SIMPL-38 (data source dialect deletions, WP-SIMPL-13).** Per OD-12 (2026-11-05) Oracle and Databricks generators, connection support, `DatabricksOboTokenProvider` and the Databricks executor are KEPT in core; nothing of them is deleted by WP-SIMPL-13. Per OD-14 the Snowflake generator is deleted (together with its function and type catalogs; tests that used it as a rejected-dialect example switch to another non-admitted value) and Ansi is kept as a generator-only dialect; it stays non-admissible as data sources (`SqlDialectMapper`, `DialectAdmissionTests`), and that admission denial is itself a security test. A query naming a deleted (or never supported) dialect fails with a typed "unsupported dialect" error before any SQL is generated; there is no fallback to a generic dialect. Test: `DialectGateTests.Unsupported_dialect_fails_closed_without_generic_fallback`.
- **SEC-SIMPL-39 (external connector deletions, WP-SIMPL-12).** Removing catalog connectors, Backstage and Itsm also removes their stored credentials handling and webhooks; startup fails fast when their keys are present (SEC-SIMPL-31). Inbound webhook routes are 404 (SEC-SIMPL-30). No residual secret store entries are read.

Mandatory tests for 4.2 (Security): `RemovedEndpointsTests.Removed_routes_return_404_for_admin_and_anonymous`; `RemovedConfigKeysTests.Every_removed_key_fails_startup`; `OptionsAuditTests.No_enforcement_option_deleted_while_wired` (compares a checked-in list of retained enforcement options with the options classes); `AuthorizationInventoryTests.Every_endpoint_has_authorization_or_is_on_the_public_allowlist`; `AuthSchemeRemovalTests.Missing_scheme_does_not_open_anonymous_path`; `DistributedStateTests.Missing_shared_state_fails_closed_in_production_for_revocation_replay_ratelimit`; `IngressExemptionTests.Exemption_list_contains_only_existing_routes`; `DialectGateTests.Unsupported_dialect_fails_closed_without_generic_fallback`.

### 4.3 Runtime-loaded modules (WP-SIMPL-25..29; WP-SIMPL-25 needs a Phase 3 re-review of the final host design before merge, this section is its binding minimum)

- **SEC-SIMPL-40 (signature verification, fail closed; aligned with PLAN AD-3).** A module loads only if the ECDSA P-256 signature over the canonical manifest verifies against the release public key embedded in `Autheris.Api` as a resource, every listed file hash matches, the manifest version equals the host version, and no file outside the manifest is present. Operators cannot add trust keys (first-party modules only); there is no operator trust-root mount and no `Required` flag. Any failure of a module listed in `Gateway:Modules:Enabled` (missing, malformed, unsigned, hash or version mismatch, duplicate id, exception in `ConfigureServices`) stops startup with an error naming the module; present-but-not-enabled modules are not loaded. The bytes that are loaded are the bytes that were verified: each managed DLL is read once into memory, hashed and loaded with `LoadFromStream` from that buffer (no TOCTOU between check and load); `Load(name)` resolves only host assemblies from the default context and module-private dependencies from the verified buffers.
- **SEC-SIMPL-41 (enable list and manifest validation).** Only modules named in the operator-controlled `Gateway:Modules:Enabled` list (configuration, not the module directory contents) load; directory scanning alone never activates a module. Manifest fields (`id`, `version`, `abstractionsVersion`, `entryAssembly`, `entryType`, `files[{path, sha256}]`, `signature`) are validated; unknown fields, duplicate ids and a private dependency whose name collides with a host assembly fail startup.
- **SEC-SIMPL-42 (load path not writable by app user).** Module directory is read-only for the runtime user in the image and in Helm (`readOnlyRootFilesystem: true`, module volume mounted `readOnly: true`). A startup check refuses (startup fails for an enabled module) to load from a directory that is writable by the process user (probe via file mode and a write attempt in a temp child) in non-Development environments. No module download at runtime.
- **SEC-SIMPL-43 (no unauthenticated endpoints from modules).** Modules register endpoints only through a host-provided `IModuleEndpointRegistrar` that wraps every route group with the default authorization policy, `EndpointSecurity`, the global rate limiter, the audit filter, the ingress transport tag and the module tag `module:<id>`; data-access decisions inside module handlers go through `IAccessDecisionPoint` (no `RebacEndpointFilter` exists). A module cannot call `MapGet`/`MapPost` on the root builder (the module API surface exposes only the registrar). The host verifies after mapping that every endpoint added by a module has authorization metadata; otherwise the module is unloaded and startup fails. `[AllowAnonymous]` metadata on a module endpoint is rejected unless the manifest declares it and the operator allowlist approves that specific route (for health or SCIM bootstrap, never default).
- **SEC-SIMPL-44 (permission and isolation).** Modules receive host services through narrow interfaces. The tenant context, principal and audit writer are host-owned; a module cannot replace `IAuditWriter`, authorization handlers, the claims transformation, `IAccessDecisionPoint`, the masking pipeline services, the plugin hook hosts (`IAuthPluginHost`) or the tenant context by DI override (post-mapping check; test `Module_replacing_access_decision_point_fails_startup`). Host service registrations of security-critical types are sealed (registered before modules and re-asserted after; a module registration of those types fails the load). Modules run in the host process; the review states that module code is trusted code, so signature and allowlist are the only barriers. `AssemblyLoadContext` is not a security boundary and is not described as one in docs.
- **SEC-SIMPL-45 (version compatibility).** The manifest version must equal the host version (one tag builds host and modules) and `abstractionsVersion` must match; a mismatch means startup failure for an enabled module, never best-effort. Downgrade of a module to an older signed version is refused (version equality).
- **SEC-SIMPL-46 (production images carry only signed modules).** Official images include only modules signed in CI by the release workflow; the image build fails when an unsigned module is copied into the module directory. An unsigned manifest is accepted only with `Gateway:Modules:AllowUnsignedInDevelopment=true` AND `ASPNETCORE_ENVIRONMENT=Development` (same pattern as `PluginManager`); with any other environment the flag fails startup (UnknownGatewayKeyGuard-style). The flag does not appear in the generated configuration reference of production profiles.
- **SEC-SIMPL-47 (supply chain).** Each module is built reproducibly in the release workflow, appears in the SBOM (CycloneDX) of the image, is scanned by Trivy (fail on HIGH/CRITICAL with the existing ignore-file process), and is signed with the same key policy as the image. Module package lock files are covered by CODEOWNERS (SEC-SIMPL-71).
- **SEC-SIMPL-48 (moved security features keep their controls).** Moving CDC/webhook event delivery, catalog sync, lineage, dbt/OpenMetadata and the Lakehouse pilot into modules (WP-SIMPL-27..29) must carry their existing tests with them (SEC-SIMPL-03) and keep their controls: webhook SSRF protections and signature secrets handling (the webhook core classes stay in core, R11), streamed rows still pass RLS and masking through the decision point, event types cannot bypass the decision point (scan over module assemblies). SCIM, TOTP, Kerberos/Negotiate, Envoy ext_authz and ForwardAuth stay core (WP-SIMPL-43). Test names stay stable or are mapped in the coverage map.
- **SEC-SIMPL-49 (absent module behaviour).** With a module absent its routes are 404 (SEC-SIMPL-30) and its configuration section fails fast if present (SEC-SIMPL-31), so an operator never believes a control is active when the module did not load.

Mandatory tests (Security, WP-SIMPL-25 unless stated): `ModuleLoaderSecurityTests.Unsigned_module_is_not_loaded`; `ModuleLoaderSecurityTests.Tampered_assembly_after_verification_is_not_loaded` (buffer-identity check); `ModuleLoaderSecurityTests.Module_not_in_enabled_list_is_not_loaded`; `ModuleLoaderSecurityTests.Writable_module_directory_refused_in_production`; `ModuleLoaderSecurityTests.Incompatible_version_not_loaded`; `ModuleLoaderSecurityTests.Enabled_module_failure_stops_startup` (any failure of an enabled module, no `Required` flag); `ModuleEndpointSecurityTests.Module_endpoint_without_authorization_unloads_module_and_fails_startup`; `ModuleEndpointSecurityTests.Anonymous_endpoint_requires_manifest_and_operator_approval`; `ModuleHostTests.Module_cannot_override_security_critical_services`; `ModuleHostTests.Module_replacing_access_decision_point_fails_startup`; `ModuleHostTests.AllowUnsigned_fails_startup_outside_development`; `ReleaseWorkflowTests.Image_build_rejects_unsigned_module` (workflow lint, WP-SIMPL-02/25); per module WP `ModuleParityTests.<Module>_security_tests_migrated` (coverage-map check).

## 5. Stage 3: full SQLite removal and test restructuring (WP-SIMPL-21, 22, 23, 31; OD-2)

- **SEC-SIMPL-50 (no silent skip in CI).** Real-database tests (Testcontainers PostgreSQL, SQL Server) use one shared `[RequiresContainerRuntimeFact]`-style attribute. In CI (`CI=true` or `GITHUB_ACTIONS=true`) a missing Docker/Podman runtime fails the test (fail, not skip). Locally, a missing runtime skips only with the explicit marker `Skipped: container runtime unavailable (local only)` and the run summary prints the skip count. A CI step asserts "Security-category tests skipped == 0" using the trx result. Test: `TestInfrastructureTests.Missing_runtime_fails_in_ci_and_skips_locally`.
- **SEC-SIMPL-51 (parity gaps documented, not hidden).** WP-SIMPL-21 produces a parity matrix per supported dialect (PostgreSQL, SQL Server, Oracle, Databricks; Ansi generator-only cells only for the admission denial; Snowflake is deleted, OD-14) for the security-relevant AST visitor outcomes (denied functions, DDL/DML rejection, system-schema access, identifier quoting, comment/stacked-statement handling, type-affinity masking). Each cell is a real-engine test or an explicit documented "not applicable" with reason. A pending cell for SQL Server, Oracle or Databricks blocks WP-SIMPL-31 and WP-SIMPL-13.

### 11.1 Authorization model (ADR-020, WP-SIMPL-46, WP-SIMPL-48, OD-30..OD-43) - binding SEC-AZ-01..19

- **SEC-AZ-01** `IAccessDecisionPoint` is the only component that decides data access on every transport (GraphQL, REST, WebSQL, OData, Trino, MCP, procedures, analytics, federation, export, streaming, Lakehouse, Envoy ext_authz, discovery, WP-45 writes, WP-47 delegated tokens). Architecture test over src and module assemblies: no other `TableAccessPolicy` construction or access decision. A module cannot replace it (SEC-SIMPL-44).
- **SEC-AZ-02** Deterministic precedence: fail-closed preconditions, then explicit deny (deny consents, column deny, hidden columns, virtual-filter deny, narrowing inputs), then union of matching grants, then default deny. Explicit deny always wins, including over profile-materialized and owner grants.
- **SEC-AZ-03** No role (including `ClusterAdmin`, `GovernanceAdmin`) and no `GranteeType.Role` record grants or bypasses data access; roles are control plane only (OD-30).
- **SEC-AZ-04 (rewritten per OD-32)** An access profile never grants by itself; only the approved, time-limited grant records materialized from it do. Assigning a profile to a user or AD group (never a role) runs the consent approval path (internal workflow or external webhook); on approval one grant record per profile item (object or pattern) is created (operation, column set with Clear/Masked per PII column, row scope, approving owners, workflow mode, `valid_from`/`valid_until`). Revised by OD-40: patterns are matched at decision time and cover objects created later, under the constraints of SEC-AZ-17. Masking level and row scope are attributes of the grant records, not of the profile. Break-glass assignments do not exist (OD-5). Explicit deny beats materialized grants. Revoking or expiring the assignment removes or expires its records.
- **SEC-AZ-05** The cross-transport parity matrix (columns include federated join, Olap endpoint, HTTP/API source, Databricks delegated source) is a required CI check; it replaces the former per-path ReBAC test.
- **SEC-AZ-06** Explain and grants APIs: authorization by control-plane role plus tenant, audited, uniform 404 for foreign or hidden objects, no foreign predicate values.
- **SEC-AZ-07** Decision cache key: tenant, subject, effective groups, object, operation, policy epoch, attribute epoch, catalog epoch (OD-40). Revocation is effective at the next request after the epoch bump; a cached decision is never served past the earliest `valid_until` of its grants; the decision record lists every contributing grant id (OD-42, WP-46 step 1).
- **SEC-AZ-08** Removed ReBAC and Casbin keys fail fast (SEC-SIMPL-31), removed routes return 404 (SEC-SIMPL-30).
- **SEC-AZ-09** Degraded group resolution and unresolved attributes deny. Denies assigned to SCIM-only groups always apply: `DropScimGroups` may never drop a group that carries a deny, and a stale or failed sync keeps those groups (OD-37).
- **SEC-AZ-10** Envoy ext_authz decides through the decision point and denies restricted decisions (WP-SIMPL-46 before the Envoy step of WP-43).
- **SEC-AZ-11 (OD-33)** Write grants are independent of read grants: INSERT and UPDATE need no read allow and a write grant never grants read; UPDATE scoped "own rows" applies the caller's RLS predicate to target and new values; DELETE is a separate grant, default off.
- **SEC-AZ-12 (OD-34)** A data owner reads own data only through an automatically created owner grant record (created on assignment, revoked on unassignment, audited, counted in usage under that grant id). No implicit owner access and no `basis:owner`.
- **SEC-AZ-13 (OD-35)** Write enforcement sits in the shared pipeline; WP-45 wires WebSQL only. OData, GraphQL, REST, Trino and MCP reject writes fail-closed until a later, separately approved WP wires them.
- **SEC-AZ-14 (OD-31)** Plugin `EnrichRolesAsync` output (including group SIDs) is control-plane only and never joins the group set used for grants or denies. Authorization hooks are narrowing-only (deny or extra row filter). Customer DLL plugins (SHA-256 list `Plugins:TrustedPluginHashes`) are a separate trust domain from signed modules (SEC-SIMPL-40).

- **SEC-AZ-15 (OD-38)** Row policies: parameter values are always bound as typed parameters; SQL policies are authored only by GovernanceAdmins and active only after approval by a data owner/delegate of every table they read (author never approves); any definition change requires re-approval; composite keys are compared pair-wise; a `NULL` key never matches; a policy reading another data source must use `KeySet`; key-set load failure, timeout or overflow deny; a row policy never grants. No free SQL in grant or profile models.

### 11.4 Residual risks
Hierarchical access relies on pattern grants evaluated at decision time (OD-40, SEC-AZ-17): objects created later in a granted pattern become accessible without a new approval. Accepted by the owner; mitigated by the literal data source in every pattern, Masked default for PII without explicit Clear, the internal-mode approving-owner rule, the approval-time statement that future objects are included (WP-47 step 9c) and the effective-access report. Overlapping grants are united by intent (OD-39); a restriction that must hold regardless of other grants must be a hard row policy or an explicit deny. The owner grant record (SEC-AZ-12) must never be creatable by the owner for self-elevation beyond owned tables; the assignment path is control-plane only.

### 11.7 Data products (OD-44, WP-SIMPL-49) - binding SEC-PROD-01..14

- **SEC-PROD-01** Creation and definition changes only by: owner or delegate of every base object; owner of the data source of every base object; `DataProductAdmin`; `DataProductSync` through the signed sync path. Procedures only by data-source owners, `DataProductAdmin` or the sync.
- **SEC-PROD-02** Products created by `DataProductAdmin` or the sync name a product owner different from the creator and the sync identity; transfers only by `DataProductAdmin`, never to itself.
- **SEC-PROD-03** The product owner decides grants, row policies, masking, hidden columns and refresh, never the definition, base objects or column classification.
- **SEC-PROD-04** Base owners have no approval and no veto; every create, change and retirement notifies them and is visible in the effective-access report.
- **SEC-PROD-05** `DataProductAdmin` and `DataProductSync` are tenant-scoped, implied by no other role (ClusterAdmin included) and mapped with four-eyes approval; the sync role reaches only the sync endpoints.
- **SEC-PROD-06** A product is decided by the decision point with the caller's grants, denies and hard row policies on the product only; base-table grants, denies and hard policies never widen or narrow it; no product grant means default deny.
- **SEC-PROD-07** Grants on products follow the consent rules incl. the self-approval ban.
- **SEC-PROD-08** PII-derived columns and columns with unresolved lineage are Masked by default; declassification only by the creator with a reason, audited; Clear needs a Clear-eligible class and a Clear rule on the grant.
- **SEC-PROD-09** A load (`schedule`, `onDemand`, `live`) executes only the current definition hash, under limits (rows, bytes, runtime), with a cluster-wide lease and single-flight; no DDL is ever sent to a source; columns never come from source metadata (OD-25).
- **SEC-PROD-10** One result is retained per product and shared by callers (policies apply at read); a failed load keeps it and marks it stale; idle `onDemand` results are dropped; `MaxStaleness` denies when exceeded; products are part of the GDPR disclosure report.
- **SEC-PROD-11** A procedure declared `read` needs an `Execute` grant, one declared `write` an `ExecuteWrite` grant; Autheris adds no transaction or read-only enforcement (OD-44); only creators with authority (SEC-PROD-01) can declare.
- **SEC-PROD-12** Write procedures need a separate write-execute grant (an execute grant never suffices), run only on wired transports (procedure REST route, MCP without read-only token) and are audited with intent and outcome.
- **SEC-PROD-13** Git-managed definitions are read-only through the API; the sync requires the sync role and a signed webhook; drift is reported, never overwritten silently.
- **SEC-PROD-14** Every product access and refresh is audited with product id and definition hash; discovery never reveals base objects hidden from the caller; `products` is a reserved data-source name.

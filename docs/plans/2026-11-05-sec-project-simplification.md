## 2. Cross-cutting conditions (all stages)

- **SEC-SIMPL-01 (advisory confidentiality, all simplification documents, commits, PR bodies, CHANGELOG, test names).** The repository is public and holds private draft advisories. Documents and commits refer to an advisory only by GHSA id and a neutral title (for example "GHSA-xxxx: input validation hardening"). They must not contain exploit details, payloads, affected-parameter names, reproduction steps or root-cause narrative for an unpublished advisory. A CI check (`Docs_and_changelog_contain_no_advisory_detail_markers`, Security) scans `docs/plans/*simplification*`, `docs/adr/ADR-019*`, `CHANGELOG.md` for the patterns `GHSA-` followed by words such as "payload", "exploit", "PoC", "bypass via", and fails with the file and line. Stripping of existing tracked advisory text is out of scope of this program; new text must comply.
- **SEC-SIMPL-02 (fail closed is the default of every deletion).** Each WP that removes a provider, option, scheme, endpoint or module declares in its PR description: (a) the old config keys and the exact failure mode when they are still present, (b) the old routes and their expected status (404), (c) the control(s) the removed code enforced and where the replacement enforces them. A PR without these three items fails Phase 5.
- **SEC-SIMPL-03 (no security test deleted without equivalent).** A security test (`[Trait("Category","Security")]` or in `Security/**`, or named in ARCH-MNT/ADR-016/ADR-017 conditions) may be deleted, moved or renamed only if the PR adds a coverage-map row (see SEC-SIMPL-60) pointing to the equivalent test. The test count of category Security must not decrease between WP merges unless the map lists the removed test with the reason "feature deleted" and the deleted feature's WP.
- **SEC-SIMPL-04 (secrets and defaults).** No simplification WP may introduce a default secret, a default password, `TrustServerCertificate=true`, `sslmode=disable`/`prefer`, or an anonymous default in any shipped config, compose file, Helm values or generated reference.
- **SEC-SIMPL-05 (stage order is binding).** Stage 1 (SQLite governance removal, WP-SIMPL-11) completes before WP-SIMPL-20; WP-SIMPL-19 (contract suite) precedes WP-SIMPL-20; module host (WP-SIMPL-25) precedes every module WP (26..30); no endpoint-bearing code moves into a module before SEC-SIMPL-40..49 tests exist. Reordering needs a new Phase 3 addendum.

## 3. Stage 1: SQLite governance store removal (WP-SIMPL-11, REQ-SIMPL-12)

Gates: WP-SIMPL-11. Mandatory regression guard: nothing that persists audit, tenant or migration state may lose a guarantee because its SQLite twin is deleted.

- **SEC-SIMPL-10 (fail-closed provider guard).** `Provider=Sqlite` (any case, any whitespace, `Governance:Provider`, and a connection string with `Data Source=*.db`/`:memory:`/`Filename=`) fails host start before DI resolution of any repository. The error names OD-1 and the migration guide, contains no connection string value, and exits non-zero. There is no fallback to PostgreSQL, SQL Server or an in-memory store, also not in Development or Testing environments. Unknown provider strings fail the same way. Reuse `LegacySwitchGuard`; the guard runs in `FederationMaskingStartupCheck`-style early startup, not lazily.
- **SEC-SIMPL-11 (missing provider fails, never defaults silently).** With the key absent the default is PostgreSQL only if a PostgreSQL connection string is present; absent connection string fails startup. The shipped default changing from SQLite to PostgreSQL must not turn an empty config into a successful start with a localhost trust-auth instance.
- **SEC-SIMPL-12 (audit hash chain preserved).** After removal, `AuditChainAnchorStores`, `AuditChainViolationGate` and the batch insert path keep: append-only inserts, no UPDATE/DELETE on audit rows (database privilege or trigger as today), chain verification on read/export, and anchor persistence. Removal of the SQLite anchor store must leave no code path where an anchor store resolves to a no-op. If `IAuditChainAnchorStore` has no registration for the configured provider, startup fails.
- **SEC-SIMPL-13 (tenant predicate in every governance query).** The PostgreSQL and SQL Server repositories keep a tenant predicate in every query touching tenant-scoped tables; the reflection/arch test that enumerates governance queries (or the SQL text scan) must run against both remaining families and must not have contained the SQLite family as its only coverage for any table. Missing tenant id still throws, never selects across tenants.
- **SEC-SIMPL-14 (connection TLS policy).** PostgreSQL requires `SSL Mode=VerifyFull` (or `VerifyCA` with documented reason) outside Development; SQL Server requires `Encrypt=True` and `TrustServerCertificate=False` outside Development. A startup validator rejects weaker settings in non-Development environments with a message that names the setting, not the value of the connection string. Compose files for local quickstart may relax only via an explicit `Development` environment and say so in a comment.
- **SEC-SIMPL-15 (no default credentials).** `deploy/podman-compose.yaml`, Helm `values.yaml`, `governance-migration-job.yaml`, governance-seed and benchmark containers contain no literal database password. Compose uses an env-file/secret the operator must supply (the quickstart script generates a random one; the compose file fails with `${POSTGRES_PASSWORD:?set POSTGRES_PASSWORD}`); Helm requires `existingSecret` or fails `helm template` through `required`. Test: `Deploy_files_contain_no_default_database_password`.
- **SEC-SIMPL-16 (migration runner forward-only, v1.5.0 frozen base).** The PostgreSQL and SQL Server runners keep: checksum verification of applied steps, refusal to run when an applied step's checksum changed, refusal to downgrade, and the v1.5.0 base unchanged. The `governance-immutability` workflow stays and its path filter is extended to the new shared-core and fragment-provider files (WP-SIMPL-20). Deleting `Migrations/Steps/sqlite` must not touch `postgres`/`sqlserver` step files (verified by a byte-identical check of both folders in the PR).
- **SEC-SIMPL-17 (shared-state triage).** Types in the triage list (`SqliteSchemaCatalogReader`, `SqliteColumnMetadataReader`, `SqliteTypeAffinity`) are removed only with a recorded proof that no governance path uses them (grep and compile). If any shared AST or masking code used `SqliteTypeAffinity` for type-based masking decisions, the replacement must default unknown types to the most restrictive treatment (mask/deny), not pass-through.
- **SEC-SIMPL-18 (operator impact).** CHANGELOG says "unsupported provider fails startup" and links the migration guide; no mention of how to disable the guard. No env var or flag may re-enable SQLite governance.

## 4. Stage 2: structural refactoring

### 4.1 Unified governance persistence (WP-SIMPL-19, WP-SIMPL-20, REQ-SIMPL-05; gates 19, 20)

- **SEC-SIMPL-20 (contract suite first).** WP-SIMPL-19 lands the repository contract suite, including tenant isolation, audit append-only and soft-delete visibility, against the existing PostgreSQL and SQL Server implementations before any merge into the core (WP-SIMPL-20). The suite must pass on both engines with identical expectations; a divergence is a bug to fix before refactoring, not a skipped case.
- **SEC-SIMPL-21 (parameterization only).** The shared core and the SQL fragment provider build statements from constant fragments plus bound parameters. Identifiers (table, column, order-by, schema) come from a closed allowlist of `static readonly` names or from a typed enum, never from request input and never by string concatenation or interpolation of a variable. `FormattableString` is not accepted by the executor; the API takes `string` constants and a parameter bag. Bulk `IN (...)` lists use parameter arrays or table-valued parameters with a bounded count (see SEC-SIMPL-23).
- **SEC-SIMPL-22 (tenant predicate enforced in the shared core).** Tenant scoping is applied by the core (a mandatory `TenantId` argument in the query builder, compile error or runtime throw when absent), not by each fragment. Tables that are intentionally global are in an explicit allowlist with a code comment and a test that fails when the allowlist grows without updating the test expectation.
- **SEC-SIMPL-23 (DoS bounds retained).** Page-size caps, maximum batch sizes and command timeouts of the old repositories move unchanged into the core; the contract suite asserts the caps.
- **SEC-SIMPL-24 (no weaker audit path).** The audit write path stays a separate narrow component (`AuditSqlCore`, batch insert) and is not folded into the generic repository executor; it keeps its own tests (SEC-SIMPL-12). Any change to hash input fields requires an ADR addendum and a chain-compatibility test with v1.5.0 fixtures.
- **SEC-SIMPL-25 (confidentiality in logs).** The shared executor logs statement identifiers/fragment ids and durations only, never parameter values, never raw SQL with inlined values. Exceptions are wrapped without parameter payload.
- **SEC-SIMPL-26 (architecture test).** `ArchitectureTests.Governance_sql_is_built_only_from_constants_and_parameters` (Roslyn or reflection-based source scan) fails on `$"..."`, `string.Format`, `+` concatenation, or `StringBuilder.Append(<non-constant>)` in files of the shared core and fragment providers, except in an explicit, reviewed allowlist (each entry with justification).

Mandatory tests: `GovernanceCoreSecurityTests.Missing_tenant_id_throws_for_every_repository_method`; `GovernanceCoreSecurityTests.Cross_tenant_read_and_write_return_nothing_both_engines` (Testcontainers); `GovernanceCoreSecurityTests.Identifier_allowlist_rejects_unknown_column_and_order_by`; `GovernanceCoreSecurityTests.Injection_payloads_in_filters_are_treated_as_data` (both engines); `GovernanceCoreSecurityTests.Page_size_and_batch_caps_enforced`; `GovernanceCoreSecurityTests.Executor_logs_no_parameter_values`; `ArchitectureTests.Governance_sql_is_built_only_from_constants_and_parameters`. All Security, WP-SIMPL-20.

### 4.2 Deletions (WP-SIMPL-12, 13, 14, 15, 16, 30, 32)

- **SEC-SIMPL-30 (removed endpoints 404).** For each removed route group (Casbin admin, traffic shadowing admin, Flight-SQL-over-HTTP, Itsm, Backstage, FinOps, Mesh, dev portal where deleted), a test sends an authenticated request (admin token) and an anonymous one and expects 404 for both, not 401/403 revealing existence and not a fall-through to a catch-all, SPA fallback or static file handler returning 200. The same test asserts the route is absent from the OpenAPI document and the ingress/rate-limit exemption list.
- **SEC-SIMPL-31 (removed config keys fail fast).** Every deleted option section or key is added to `UnknownGatewayKeyGuard` (or `LegacySwitchGuard` when it was a switch) with a message naming the replacement or "removed in vX". Startup fails when any is present with any value, including `false`/empty, because a stale `Enabled=false` copy can hide a stale `true` in another config source.
- **SEC-SIMPL-32 (no security flag silently ignored).** For each of `CasbinOptions.EnforceInQueryPipeline`, `ScimOptions.AllowedIpRanges`, `McpOptions.RequirePiiMasking`, and any other option whose name contains Enforce/Require/Allowed/Deny/Mask/Pii/Tls/Auth: before deletion the PR states whether the option is wired (grep of consumers). If wired, the option stays or the enforced behaviour becomes unconditional and secure (PII masking always on, IP allowlist enforced in the module or the key fails fast). If unwired, deletion is allowed only with the fail-fast guard of SEC-SIMPL-31 so an operator relying on it learns that it never worked. Phase 5 verifies by diff of options classes against consumer search.
- **SEC-SIMPL-33 (Casbin deletion, WP-SIMPL-14).** Authorization after removal is the existing RBAC/ReBAC filters. The PR proves every endpoint previously guarded by a Casbin check is still behind `RequireAuthorization` plus `RebacEndpointFilter`/policy. Test: `AuthorizationInventoryTests.Every_endpoint_has_authorization_or_is_on_the_public_allowlist` (reflection over `EndpointDataSource`) must be green before and after.
- **SEC-SIMPL-34 (Garnet and shadowing, WP-SIMPL-15).** Deleting the embedded Garnet server must not leave a distributed-state consumer (rate limit, token revocation, replay cache, HITL approvals, audit anchors cache) falling back to per-process memory silently in a multi-replica deployment. Where a consumer needs shared state and none is configured, startup logs an error and (for revocation, replay and rate-limit state) fails closed in non-Development, consistent with ADR-017. Traffic shadowing removal must remove its egress configuration; no residual outbound HTTP client with a target URL option remains.
- **SEC-SIMPL-35 (Flight-SQL-over-HTTP removal, WP-SIMPL-16).** The remaining Arrow export endpoints keep masking, row/column policy and audit on the same path as before; test `ArrowExportSecurityTests.Export_applies_masking_and_audit` stays. No second unauthenticated Arrow listener is opened.
- **SEC-SIMPL-36 (authentication scheme removal).** Removing Kerberos/NTLM/SCIM/TOTP from the core (moved to modules in WP-SIMPL-30) must not change the default or fallback authentication scheme: `AddAuthentication().DefaultScheme` and `FallbackPolicy` stay explicit; with a scheme missing the pipeline returns 401, never anonymous. Test `AuthSchemeRemovalTests.Missing_scheme_does_not_open_anonymous_path` (Security): configure `Authentication:Kerberos` while the module is absent, host fails fast or all protected endpoints still return 401. `EnterpriseClaimsTransformation` must not assume the removed scheme's claims exist (no default role grant when a claim is absent).
- **SEC-SIMPL-37 (rate limiting and ingress exemptions).** The rate limiting exemption list and the ingress/WAF exemption paths (deploy ingress, Helm) are updated in the same PR as each route removal and are tested for consistency: `IngressExemptionTests.Exemption_list_contains_only_existing_routes`. A stale exemption for a removed route is a failure, because a later route reusing the path would inherit the exemption.
- **SEC-SIMPL-38 (data source dialect deletions, WP-SIMPL-13).** Per OD-12 (2026-11-05) Oracle and Databricks generators, connection support, `DatabricksOboTokenProvider` and the Databricks executor are KEPT in core; nothing of them is deleted by WP-SIMPL-13. Per OD-14 the Snowflake generator is deleted (together with its function and type catalogs; tests that used it as a rejected-dialect example switch to another non-admitted value) and Ansi is kept as a generator-only dialect; it stays non-admissible as data sources (`SqlDialectMapper`, `DialectAdmissionTests`), and that admission denial is itself a security test. A query naming a deleted (or never supported) dialect fails with a typed "unsupported dialect" error before any SQL is generated; there is no fallback to a generic dialect. Test: `DialectGateTests.Unsupported_dialect_fails_closed_without_generic_fallback`.
- **SEC-SIMPL-39 (external connector deletions, WP-SIMPL-12).** Removing catalog connectors, Backstage and Itsm also removes their stored credentials handling and webhooks; startup fails fast when their keys are present (SEC-SIMPL-31). Inbound webhook routes are 404 (SEC-SIMPL-30). No residual secret store entries are read.

Mandatory tests for 4.2 (Security): `RemovedEndpointsTests.Removed_routes_return_404_for_admin_and_anonymous`; `RemovedConfigKeysTests.Every_removed_key_fails_startup`; `OptionsAuditTests.No_enforcement_option_deleted_while_wired` (compares a checked-in list of retained enforcement options with the options classes); `AuthorizationInventoryTests.Every_endpoint_has_authorization_or_is_on_the_public_allowlist`; `AuthSchemeRemovalTests.Missing_scheme_does_not_open_anonymous_path`; `DistributedStateTests.Missing_shared_state_fails_closed_in_production_for_revocation_replay_ratelimit`; `IngressExemptionTests.Exemption_list_contains_only_existing_routes`; `DialectGateTests.Unsupported_dialect_fails_closed_without_generic_fallback`.

### 4.3 Runtime-loaded modules (WP-SIMPL-25..30; WP-SIMPL-25 needs a Phase 3 re-review of the final host design before merge, this section is its binding minimum)

- **SEC-SIMPL-40 (signature verification, fail closed).** A module assembly loads only if its detached signature (or Sigstore/cosign bundle, decision in the host ADR) verifies against a trust root shipped in the image or provided by the operator as a read-only mount. Missing, malformed, expired or unknown-key signature means the module is not loaded and the host logs a warning; if the module is listed as `Required` in configuration, startup fails. Signature is verified over the assembly bytes and the manifest, and the bytes that are loaded are the bytes that were verified (read once into memory, verify, load from the same buffer, no TOCTOU between check and `LoadFromStream`).
- **SEC-SIMPL-41 (manifest allowlist).** Only modules named in an operator-controlled allowlist (configuration, not the module directory contents) load. Directory scanning alone never activates a module. Manifest fields (id, version, minimum host version, declared endpoints, declared permissions) are validated; unknown fields or duplicate ids fail.
- **SEC-SIMPL-42 (load path not writable by app user).** Module directory is read-only for the runtime user in the image and in Helm (`readOnlyRootFilesystem: true`, module volume mounted `readOnly: true`). A startup check refuses to load from a directory that is writable by the process user (probe via file mode and a write attempt in a temp child) in non-Development environments. No module download at runtime.
- **SEC-SIMPL-43 (no unauthenticated endpoints from modules).** Modules register endpoints only through a host-provided `IModuleEndpointRegistrar` that wraps every route group with `RequireAuthorization` (named policy) and the ingress policy tag, and applies the global rate limiter and audit filter. A module cannot call `MapGet`/`MapPost` on the root builder (the module API surface exposes only the registrar). The host verifies after mapping that every endpoint added by a module has authorization metadata; otherwise the module is unloaded and startup fails. `[AllowAnonymous]` metadata on a module endpoint is rejected unless the manifest declares it and the operator allowlist approves that specific route (for health or SCIM bootstrap, never default).
- **SEC-SIMPL-44 (permission and isolation).** Modules receive host services through narrow interfaces. The tenant context, principal and audit writer are host-owned; a module cannot replace `IAuditWriter`, authorization handlers, the claims transformation or a masking pipeline by DI override. Host service registrations of security-critical types are sealed (registered before modules and re-asserted after; a module registration of those types fails the load). Modules run in the host process; the review states that module code is trusted code, so signature and allowlist are the only barriers. `AssemblyLoadContext` is not a security boundary and is not described as one in docs.
- **SEC-SIMPL-45 (version compatibility).** A module declares `MinHostVersion`/`MaxHostVersion` (or contract version); a mismatch means not loaded, never best-effort. Downgrade of a module to an older signed version is refused when a revocation/minimum-version list in the allowlist says so.
- **SEC-SIMPL-46 (production images carry only signed modules).** Official images include only modules signed in CI by the release workflow; the image build fails when an unsigned module is copied into the module directory. Unsigned loading exists only with `Modules:AllowUnsigned=true` AND `ASPNETCORE_ENVIRONMENT=Development`; with any other environment the flag fails startup (UnknownGatewayKeyGuard-style). The flag does not appear in the generated configuration reference of production profiles.
- **SEC-SIMPL-47 (supply chain).** Each module is built reproducibly in the release workflow, appears in the SBOM (CycloneDX) of the image, is scanned by Trivy (fail on HIGH/CRITICAL with the existing ignore-file process), and is signed with the same key policy as the image. Module package lock files are covered by CODEOWNERS (SEC-SIMPL-71).
- **SEC-SIMPL-48 (moved security features keep their controls).** Moving Kerberos/NTLM/SCIM/TOTP, CDC/webhooks, catalog sync and lineage into modules (WP-SIMPL-26..30) must carry their existing tests with them (SEC-SIMPL-03) and keep: SCIM inbound token/IP policy (SEC-SIMPL-32), webhook SSRF protections and signature secrets handling, TOTP secret at-rest protection and brute-force lockout, Kerberos keytab handling. Test names stay stable or are mapped in the coverage map.
- **SEC-SIMPL-49 (absent module behaviour).** With a module absent its routes are 404 (SEC-SIMPL-30) and its configuration section fails fast if present (SEC-SIMPL-31), so an operator never believes a control is active when the module did not load.

Mandatory tests (Security, WP-SIMPL-25 unless stated): `ModuleLoaderSecurityTests.Unsigned_module_is_not_loaded`; `ModuleLoaderSecurityTests.Tampered_assembly_after_verification_is_not_loaded` (buffer-identity check); `ModuleLoaderSecurityTests.Module_not_in_allowlist_is_not_loaded`; `ModuleLoaderSecurityTests.Writable_module_directory_refused_in_production`; `ModuleLoaderSecurityTests.Incompatible_version_not_loaded`; `ModuleLoaderSecurityTests.Required_module_failure_stops_startup`; `ModuleEndpointSecurityTests.Module_endpoint_without_authorization_unloads_module_and_fails_startup`; `ModuleEndpointSecurityTests.Anonymous_endpoint_requires_manifest_and_operator_approval`; `ModuleHostTests.Module_cannot_override_security_critical_services`; `ModuleHostTests.AllowUnsigned_fails_startup_outside_development`; `ReleaseWorkflowTests.Image_build_rejects_unsigned_module` (workflow lint, WP-SIMPL-02/25); per module WP `ModuleParityTests.<Module>_security_tests_migrated` (coverage-map check).

## 5. Stage 3: full SQLite removal and test restructuring (WP-SIMPL-21, 22, 23, 31; OD-2)

- **SEC-SIMPL-50 (no silent skip in CI).** Real-database tests (Testcontainers PostgreSQL, SQL Server) use one shared `[RequiresContainerRuntimeFact]`-style attribute. In CI (`CI=true` or `GITHUB_ACTIONS=true`) a missing Docker/Podman runtime fails the test (fail, not skip). Locally, a missing runtime skips only with the explicit marker `Skipped: container runtime unavailable (local only)` and the run summary prints the skip count. A CI step asserts "Security-category tests skipped == 0" using the trx result. Test: `TestInfrastructureTests.Missing_runtime_fails_in_ci_and_skips_locally`.
- **SEC-SIMPL-51 (parity gaps documented, not hidden).** WP-SIMPL-21 produces a parity matrix per supported dialect (PostgreSQL, SQL Server, Oracle, Databricks; Snowflake/Ansi only while retained) for the security-relevant AST visitor outcomes (denied functions, DDL/DML rejection, system-schema access, identifier quoting, comment/stacked-statement handling, type-affinity masking). Each cell is a real-engine test or an explicit documented "not applicable" with reason. A pending cell for SQL Server, Oracle or Databricks blocks WP-SIMPL-31 and, if Snowflake/Ansi deletion is confirmed, WP-SIMPL-13.
- **SEC-SIMPL-52 (security tests move, not die).** When tests leave `Autheris.Tests.Unit` for an integration project (WP-SIMPL-22), the integration project is in the CI required checks and in the same test categories; `SecurityFindingsRemediationTests` and siblings keep their names or are mapped (SEC-SIMPL-60). Tests that used SQLite only as a convenient in-memory store are rewritten against fakes or Testcontainers; they must still assert the same security property (tenant isolation, audit append-only, masking).
- **SEC-SIMPL-53 (WP-SIMPL-31 step 3 gate).** SQLite as data-source dialect is removed only after SEC-SIMPL-51 matrix is complete and the mutation and fuzz floors of SEC-SIMPL-55 hold on the merge commit. Removal includes `Ast/Security/SqliteTypeAffinity` and the dialect function allowlist; a data source of type sqlite fails with the typed unsupported-dialect error (SEC-SIMPL-38). The owner may stop before this step; the stage 1 conditions remain valid either way.
- **SEC-SIMPL-54 (test data hygiene).** Testcontainers fixtures use random per-run passwords, bind only to localhost, and are torn down; test credentials are not reused in shipped config (SEC-SIMPL-15).

### 5.1 SQL engine scope and ADR-019

- **SEC-SIMPL-55 (AST security visitor and floors).** Whatever ADR-019 chooses (keep own parser, adopt a library, or hybrid), the security visitor stays the single enforcement point: parse, then visitor allowlist, then generation. Constructs the parser or generator does not model (unknown node, unknown function, dialect-specific syntax) produce a deny, never pass-through of raw text. Fuzz corpus and seed set are retained and extended for all retained dialects (PostgreSQL, SQL Server, Oracle, Databricks; see SEC-SIMPL-92); the Stryker mutation score floor for the AST security namespace stays at its current ARCH-MNT value and is not lowered by deleting dialect code; the floor is measured on the merge commit of each dialect WP.
- **SEC-SIMPL-56 (library adoption conditions, if chosen).** A parser/generator dependency requires: pinned version in lock files, license check, Trivy/SBOM coverage, no reflection-based dynamic code loading, no network access, and a differential test that every statement accepted by the visitor round-trips to the same semantic tree (no parse differential between what is checked and what is executed). Execution always uses the regenerated SQL from the checked tree, never the original user text.
- **SEC-SIMPL-57 (dialect set closed).** The allowlist of dialect ids is a closed set in code; adding a dialect needs a parity matrix (SEC-SIMPL-51) and a Phase 3 note. Governance store dialects stay PostgreSQL and SQL Server only (OD-12); Oracle and Databricks are data sources, never governance stores.

Mandatory tests (Security): `AstSecurityVisitorTests.Unsupported_construct_is_denied_not_passed_through` (per dialect); `AstFuzzTests.Corpus_retained_and_runs_for_postgres_and_sqlserver`; `AstDifferentialTests.Checked_tree_equals_executed_sql_semantics`; `MutationFloorTests` (CI gate, not a unit test) with floor recorded in the workflow file; `DialectGateTests.Dialect_set_is_closed`.

## 6. Configuration, versioning and release

- **SEC-SIMPL-60 (coverage map).** WP-SIMPL-23 creates `docs/plans/` coverage map (generated by a script from the base commit test list): old test id, new test id or "feature deleted (WP-SIMPL-NN)", category. CI check `TestCoverageMapTests.No_security_test_lost_without_mapping` compares the Security test list at the base commit of the program with the current list through the map. The map is updated in each test-moving PR.
- **SEC-SIMPL-61 (generated configuration reference, WP-SIMPL-06/32).** The generator reads option types and defaults only, never configuration sources or environment. Properties annotated or named as secret (`Password`, `Secret`, `Key`, `Token`, `ConnectionString`, `Credential`, `PrivateKey`) are rendered as `<secret>` with no default value, and the generator fails the build when a secret-like property has a non-empty default. Pre-release tags never move the `latest` or a stable minor tag.
- **SEC-SIMPL-64 (Helm default image).** Helm `values.yaml` pins `image.tag` to the chart's `appVersion` (or a digest) and never defaults to `latest` or a tag without migration support for the configured schema; the chart refuses to install when the app version's migration steps cannot upgrade from the stored schema version (migration job fails closed, the Deployment waits on it). Test: `HelmValuesTests.Image_tag_is_pinned_and_not_latest`.
- **SEC-SIMPL-65 (ReadyToRun removal, WP-SIMPL-01).** Changing publish settings must not alter trimming/analyzers that carry security-relevant behaviour; the image keeps non-root user, read-only root filesystem and the existing Trivy gate. Verified by the existing deploy hygiene tests.

## 7. Process (WP-SIMPL-07, WP-SIMPL-08)

- **SEC-SIMPL-70 (freeze exceptions).** The program freeze (no new features) never applies to security fixes: any PR labelled `security` or linked to a GHSA id, a Dependabot/Trivy alert or a Phase 3 condition bypasses freeze, ratchets that would block it (LOC, folder, file-count ratchets are advisory for these PRs) and the PR size limit. The exception requires CODEOWNERS security approval and a neutral title (SEC-SIMPL-01). A ratchet failure on a security PR is waived by a documented label, never by weakening the ratchet itself.

- **SEC-SIMPL-72 (PR size limit).** A size limit applies to feature and refactor PRs; deletion PRs of whole subsystems are allowed to exceed it only if the PR description holds SEC-SIMPL-02 items. Security fixes are exempt (SEC-SIMPL-70).

Permissions of workflows stay least privilege; no `pull_request_target` with checkout of PR code.
- **SEC-SIMPL-74 (agent and doc cleanups, WP-SIMPL-03..05, 09).** Documentation and agent-definition cleanups must not remove security guidance (fail-closed, Phase 3 conditions, advisory confidentiality).

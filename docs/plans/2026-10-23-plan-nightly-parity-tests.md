# REQ-PARITY-NIGHTLY: Implementation plan (Phase 2)

Input: [`2026-10-23-req-nightly-parity-tests.md`](2026-10-23-req-nightly-parity-tests.md). Origin: master plan row `REQ-PARITY-NIGHTLY`. Verified against branch `feat/nightly-parity-tests` (base `3dba661a`).

## 1. Inputs and defaults taken

Owner decisions: sibling `.github/workflows/parity-nightly.yml` (cron `0 2 * * *` + `workflow_dispatch`); SQLite first; PostgreSQL/SQL Server as a separate nightly job; green-to-red fails the workflow; REST/OData and MCP cells `Pending` (cheap REST no-500 included); no auto issue creation; function list source decided here (D-12).

Code facts this plan relies on:
1. SQLite is a supported in-process data source (`Gateway:DataSources:Connections:<name>:Provider=Sqlite`, see `EndToEndSqliteTests`, `TypedAggregationEndToEndTests`). All blocks run in-process on SQLite; no container is needed for the default job. Local verification is possible.
2. Test auth: `Gateway:Authentication:EnableTestAuthHandler=true`, build with `-p:AutherisIncludeTestAuth=true`, headers `X-Test-User-Sid`, `X-Test-Roles`, `X-Test-Tenant`.
3. WebSQL: `POST /api/v1/sql` body `{ "sql": ... }`; 200 body has `columns`, rows, `rowCount`; errors are `{ error, message[, code] }` (`BadRequest`, `NotImplemented` 501, `TooManyRequests`/`TOO_MANY_REQUESTS`, `InternalServerError` 500). GraphQL: `POST /graphql`, typed aggregation field `<source>_<schema>_<table>_aggregate(groupBy, aggregates: [{fn, alias}], where, orderBy)`, enabled by default; errors in `errors[].extensions.code` (sanitizer emits `INTERNAL_SERVER_ERROR` for unexpected faults). REST: `GET /api/v1/data/{domain}/{schema}/{table}`. MCP: `/mcp`, codes in `McpErrorCodes`.
4. xunit is 2.9.3 (no `Assert.Skip`); test projects pin versions per csproj (no central package management). `DuckDB.NET.Data.Full 1.5.6` is already referenced by `Autheris.Application` (approved), so DuckDB is reachable transitively without a new package. `Testcontainers.PostgreSql`/`MsSql 4.16.0` are approved (Integration csproj).
5. Advertised SQL functions: `TrinoSqlEngine.SqlFunctionAllowlists.Sqlite` / `GetDefault(TargetSqlDialect)` (public).
6. `Autheris.Tests.SqlCompilerGate/Parity/*` is an unrelated compiler-parity folder; no name clash because the new project uses namespace `Autheris.Tests.Parity`.

## 5. Gap drafts (PARITY-GAP-NNN, to become GitHub issues)

Candidates from code reading; each is confirmed (or deleted) by the first run of the WP that covers it. Only confirmed ids may be used in `KnownGap`.

### PARITY-GAP-001
Capability: request validation. Channel: WebSQL. Input: `POST /api/v1/sql` with an empty body, `{`, `[]`, `{"sql":123}`, `{"sql":null}`, `{"sql":""}`, `{"sql":"   "}`, `null`, `{"sql":"SELECT 1","parameters":5}`. Observed: HTTP 400 with `{"error":"Invalid JSON payload."}` or `{"error":"Missing 'sql' query parameter in request body."}`; no `code`, and the `error` field holds the human message instead of a token (the governed-SQL errors, by contrast, carry `error` token plus stable `SQL_*` code). Expected: every 4xx carries a stable `code` (for example `INVALID_JSON`, `MISSING_REQUIRED_FIELD` from `ApiErrorCodes`). Issue draft: "WebSQL request-validation 400s have no stable error code". Found by: WP2 boundary sweep (`raw.*` cases). Earlier candidate wording (generic `BadRequest` for all WebSQL errors) is refuted: governed-SQL failures already return `SQL_SYNTAX_ERROR`, `SQL_POLICY_DENIED`, `SQL_CONSTRUCT_NOT_SUPPORTED`, `SQL_PROVIDER_ERROR`.

### PARITY-GAP-002
Candidate, not confirmed in WP2: WebSQL answers unsupported capabilities with HTTP 501 `NotImplemented`, a 5xx. No 501 occurred in the WP2 sweeps (unsupported constructs answer 422 `SQL_CONSTRUCT_NOT_SUPPORTED`). D-9 keeps tolerating 501 `NotImplemented`. Re-check in WP4/WP6; the id is not used by any KnownGap.

### PARITY-GAP-003
Capability: error contract. Channel: GraphQL. Input: unknown field/argument (`{ nope }`, `orderBy: [{ North: ASC }]`), unknown operation name, `mutation { nope }`, wrong literal type (`amount: { eq: "NaN" }`, `qty: { eq: "x" }`), variable coercion (`$v: Int` with `"abc"`), `in: [..., null]`. Observed: HTTP 400 `errors[]` with `message`, `locations`, no `extensions.code`. Expected: every error carries an `extensions.code` from a documented set (the sanitizer already emits codes for resolver errors). Issue draft: "GraphQL validation and variable-coercion errors have no extensions.code". 207 sweep cells.

### PARITY-GAP-004
Capability: error contract. Channel: REST `GET /api/v1/data/{domain}/{schema}/{table}`. Input: unknown column in `filter`/`orderBy`/`select`, malformed `orderBy`, `offset` above 100000, SQL text above 64000 characters, unknown table or domain (404), unterminated quote in `filter`. Observed: 400/404 with `{"error":"<message>"}`, no `code`; messages expose internal parameter names (`(Parameter 'intent')`, `'rawSql'`, `'request'`) and echo the submitted token. Expected: RFC 7807 problem bodies with a stable `code` from `ApiErrorCodes` and no internal parameter names. Issue draft: "REST data endpoint 4xx bodies lack a stable code and name internal parameters". 37 sweep cells.

### PARITY-GAP-005
Capability: string equality/LIKE with a literal operand. Channels: WebSQL and REST `filter` (parameters and GraphQL variables work). Input: literal strings `North'; DROP TABLE parity_sales; --`, `' UNION SELECT 1 --`, `/* c */ North` and `back\slash`, in `region = '...'`, `note = '...'`, `note LIKE '...'` (quotes doubled correctly). Observed: HTTP 400 `SQL_SYNTAX_ERROR` "Invalid SQL syntax." although the literal is well-formed. Strings with a quote but without `--`, `/*` or a backslash (`O'Brien`, `' OR '1'='1`) work. Expected: a quoted literal is data whatever it contains (or the rejection is a documented hardening with its own code). Issue draft: "Literals containing comment markers or backslash rejected as SQL syntax errors". 20 sweep cells.

### PARITY-GAP-006
Capability: typed date literal. Channel: WebSQL. Input: `SELECT id FROM parity_sales WHERE sale_date = DATE '2024-02-29'` (same for `TIMESTAMP '...'`). Observed: HTTP 422 `SQL_CONSTRUCT_NOT_SUPPORTED`. Expected: the ANSI typed literal is accepted and matches row 5, or the limitation is documented. Issue draft: "WebSQL does not support DATE/TIMESTAMP typed literals".

### PARITY-GAP-007
Capability: date comparison via cast. Channel: WebSQL on SQLite. Input: `SELECT id FROM parity_sales WHERE sale_date = CAST('2024-02-29' AS DATE) ORDER BY id` (column holds ISO text). Observed: HTTP 200 with zero rows; `sale_date = '2024-02-29'` returns row 5. Expected: row 5 (the cast yields a date comparable to the column). Issue draft: "WebSQL CAST(... AS DATE) comparison on a SQLite text date column returns no rows".

### PARITY-GAP-008
Capability: filter equality on a DATE column. Channel: GraphQL (`default_main_parity_sales(where: { sale_date: { eq: "2024-02-29" } })`, variable and literal). Input: `2024-02-29`, `2024-03-31`, `2024-12-31`. Observed: HTTP 200 with an empty list; the same filter via WebSQL and REST returns rows 5, 6 and 10 (the column type maps to `AutherisDateTimeFilter`). Expected: the same rows on every channel. Issue draft: "GraphQL date equality on a DATE column returns no rows". 6 sweep cells.

### PARITY-GAP-009
Capability: equality with null. Channel: GraphQL. Input: `{ eq: null }` and variable `null` on any column. Observed: HTTP 200 with `errors[0].extensions.code = INVALID_QUERY` ("cannot be null"), `data: null`; WebSQL (`= NULL`) and REST accept it and return zero rows. Expected: one documented behaviour on all channels (zero rows per SQL three-valued logic, or a stable 4xx everywhere). Issue draft: "GraphQL rejects eq: null while WebSQL/REST accept it". 16 sweep cells.

### PARITY-GAP-010
Capability: paging parameters. Channel: REST. Input: `limit=-1`, `offset=-1`, `limit=0`. Observed: HTTP 200; negative values are ignored (default page of 50 rows from offset 0) and `limit=0` returns the default page instead of zero rows. Expected: negative values rejected with a stable 4xx, `limit=0` returns zero rows. Issue draft: "REST silently ignores negative limit/offset and treats limit=0 as default". 3 sweep cells.

### PARITY-GAP-011
Capability: paging. Channel: GraphQL. Input: `first: 0`. Observed: HTTP 400 `QUERY_TOO_COMPLEX` (cost 110000: the list is costed as unbounded). Expected: zero rows, as `LIMIT 0` on WebSQL. Issue draft: "GraphQL first: 0 is costed as an unbounded list". 1 sweep cell.

### Observed server errors and leaks (SEC-PAR-05, not gaps)

These cases are a 5xx or leak internals. They are never a `KnownGap`: they live in the data row list `BoundaryKnownGapData` (kind `ObservedServerError`), are excluded from `Boundary_Case`/`Invariant_NoServerError`, and run in `Invariant_ObservedServerErrors`, where they fail hard until production is fixed. Owner decision needed (fix, or accept and document). Ids are `<slot>.<column>.<value id>`; `none` = no column.

- WebSQL, HTTP 502 `SQL_PROVIDER_ERROR` (18 cases): unknown identifier reaching the provider. `ORDER BY "<key>"` for every key that is not a column (`North`, `north`, ` North`, `O'Brien`, `'`, `"`, `back\slash`, `50%`, `under_score`, emoji, unicode, bidi, `SELECT * FROM x`, `' OR '1'='1`, empty string, 1 KiB of `a`, a single `N`) and `SELECT id FROM parity_sales WHERE nope = 1` (`raw.none.unknown_column`). Expected: 4xx with a stable code (unknown column), as WebSQL already does for an unknown table (403 `SQL_POLICY_DENIED`).

- SEC-PAR-01 Workflow trigger and permissions: only `schedule` and `workflow_dispatch`; never `pull_request`, `pull_request_target`, `push`, `workflow_run`.

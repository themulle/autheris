# REQ-PARITY-NIGHTLY: Implementation plan (Phase 2)

Input: [`2026-10-23-req-nightly-parity-tests.md`](2026-10-23-req-nightly-parity-tests.md). Origin: master plan row `REQ-PARITY-NIGHTLY`. Verified against branch `feat/nightly-parity-tests` (base `3dba661a`).

## 1. Inputs and defaults taken

Owner decisions: sibling `.github/workflows/parity-nightly.yml` (cron `0 2 * * *` + `workflow_dispatch`); SQLite first; PostgreSQL/SQL Server as a separate nightly job; green-to-red fails the workflow; REST/OData and MCP cells `Pending` (cheap REST no-500 included); no auto issue creation; function list source decided here (D-12).

Code facts this plan relies on:
1. SQLite is a supported in-process data source (`Gateway:DataSources:Connections:<name>:Provider=Sqlite`, see `EndToEndSqliteTests`, `TypedAggregationEndToEndTests`). All blocks run in-process on SQLite; no container is needed for the default job. Local verification is possible.
2. Test auth: `Gateway:Authentication:EnableTestAuthHandler=true`, build with `-p:AutherisIncludeTestAuth=true`, headers `X-Test-User-Sid`, `X-Test-Roles`, `X-Test-Tenant`.
3. WebSQL: `POST /api/v1/sql` body `{ "sql": ... }`; 200 body has `columns`, rows, `rowCount`; errors are `{ error, message[, code] }` (`BadRequest`, `NotImplemented` 501, `TooManyRequests`/`TOO_MANY_REQUESTS`, `InternalServerError` 500). GraphQL: `POST /graphql`, typed aggregation field `<source>_<schema>_<table>_aggregate(groupBy, aggregates: [{fn, alias}], where, orderBy)`, enabled by default; errors in `errors[].extensions.code` (sanitizer emits `INTERNAL_SERVER_ERROR` for unexpected faults). REST: `GET /api/v1/data/{domain}/{schema}/{table}`. MCP: `/mcp`, codes in `McpErrorCodes`.
4. xunit is 2.9.3 (no `Assert.Skip`); test projects pin versions per csproj (no central package management). `DuckDB.NET.Data.Full 1.5.6` is already referenced by `Autheris.Application` (approved), so DuckDB is reachable transitively without a new package. `Testcontainers.PostgreSql`/`MsSql 4.16.0` are approved (Integration csproj).
5. Advertised SQL functions: `TrinoSqlEngine.SqlFunctionAllowlists.Sqlite` / `GetDefault(TargetSqlDialect)` (public).
6. `Autheris.Tests.SqlCompilerGate/Parity/*` is an unrelated compiler-parity folder; no name clash because the new project uses namespace `Autheris.Tests.Parity`.

## 5. Gap drafts (PARITY-GAP-NNN, to become GitHub issues)

Candidates from code reading; each is confirmed (or deleted) by the first run of the WP that covers it. Only confirmed ids may be used in `KnownGap`.

### PARITY-GAP-001
Capability: request validation. Channel: WebSQL. Input: `POST /api/v1/sql` with an empty body, `{`, `[]`, `{"sql":123}`, `{"sql":null}`, `{"sql":""}`, `{"sql":"   "}`, `null`, `{"sql":"SELECT 1","parameters":5}`. Observed: HTTP 400 with `{"error":"Invalid JSON payload."}` or `{"error":"Missing 'sql' query parameter in request body."}`; no `code`, and the `error` field holds the human message instead of a token (the governed-SQL errors, by contrast, carry `error` token plus stable `SQL_*` code). Expected: every 4xx carries a stable `code` (for example `INVALID_JSON`, `MISSING_REQUIRED_FIELD` from `ApiErrorCodes`). Issue draft: "WebSQL request-validation 400s have no stable error code". Found by: WP2 boundary sweep (`raw.*` cases). Earlier candidate wording (generic `BadRequest` for all WebSQL errors) is refuted: governed-SQL failures already return `SQL_SYNTAX_ERROR`, `SQL_POLICY_DENIED`, `SQL_CONSTRUCT_NOT_SUPPORTED`, `SQL_PROVIDER_ERROR`.
- Robin-100 (2026-10-23), hard failures kept red, never `KnownGap`: `Robin_30_FederatedUnknownSourceSameCode` (existence oracle: an unknown federated source answers `SQL_POLICY_VIOLATION` while a known but unreachable one answers `SQL_POLICY_DENIED`; draft issue: "Federated unknown source must answer the same 403 `SQL_POLICY_DENIED` as a denied one (no source-existence oracle)") and `Robin_Proactive_SetOperations|WebSql|mismatch` (502 `SQL_PROVIDER_ERROR` for a column-count mismatch in UNION; draft issue: "UNION/INTERSECT/EXCEPT with mismatching column counts must be a 4xx stable code, not a provider 502").
- Robin-100 (2026-10-23), hard failure kept red: `Robin_Proactive_RowNumberOverPartition|WebSql|masked` (`SELECT id, ROW_NUMBER() OVER (ORDER BY amount) FROM parity_masked`). Denied with 403, but the code is `SQL_POLICY_VIOLATION` where the designed code is `AGGREGATION_ON_MASKED_COLUMN` (window wrap, `AstSecurityVisitor.MaskGuards.cs` :436/:462). Guard order is ambiguous: the ORDER BY masked-reference guard (:75) can fire before the window aggregation scope. Draft issue: "A masked column in a window ORDER BY must answer one documented stable code (decide between `AGGREGATION_ON_MASKED_COLUMN` and `SQL_POLICY_VIOLATION`) and the guard order must be pinned by a test."

Fixed 2026-10-23 on fix/parity-gaps (#293): WebSQL request-validation 4xx bodies carry a stable code with a fixed message.


### PARITY-GAP-002
Observed (WP3). Capability: unsupported function for a dialect. Channel: WebSQL on a SQLite source. Input: `SELECT CAST(convert_timezone('UTC','Europe/Berlin', CAST(sold_at AS timestamp)) AS date) ... GROUP BY ...`. Observed: HTTP 501 `NotImplemented` with code `SQL_FUNCTION_UNSUPPORTED_DIALECT`, a 5xx. D-9 tolerates it as Unsupported and records it as an observation (JSONL `observation`, listed by `parity-report.py` under "Tolerated 501"). Expected (the ask): a 4xx (for example 422 with the same code), because a 5xx should mean a server fault and monitoring cannot tell the two apart. The capability itself is tracked by PARITY-GAP-019. This id is not used by any KnownGap; the observation stays visible until production answers with a 4xx.

Fixed 2026-10-23 on fix/parity-gaps (#308): `SQL_FUNCTION_UNSUPPORTED_DIALECT` answers 422 instead of 501; the parity harness keeps its tolerance for a catalogue-coded 501 (Unsupported, D-9) unchanged.


### PARITY-GAP-003
Capability: error contract. Channel: GraphQL. Input: unknown field/argument (`{ nope }`, `orderBy: [{ North: ASC }]`), unknown operation name, `mutation { nope }`, wrong literal type (`amount: { eq: "NaN" }`, `qty: { eq: "x" }`), variable coercion (`$v: Int` with `"abc"`), `in: [..., null]`. Observed: HTTP 400 `errors[]` with `message`, `locations`, no `extensions.code`. Expected: every error carries an `extensions.code` from a documented set (the sanitizer already emits codes for resolver errors). Issue draft: "GraphQL validation and variable-coercion errors have no extensions.code". 207 sweep cells.

Fixed 2026-10-23 on fix/parity-gaps (#294): every GraphQL validation, coercion and variable error carries `extensions.code` (`GRAPHQL_VALIDATION_FAILED`, `GRAPHQL_VARIABLE_INVALID`, `GRAPHQL_PARSE_FAILED`) with a fixed message in every environment.


### PARITY-GAP-004
Capability: error contract. Channel: REST `GET /api/v1/data/{domain}/{schema}/{table}`. Input: unknown column in `filter`/`orderBy`/`select`, malformed `orderBy`, `offset` above 100000, SQL text above 64000 characters, unknown table or domain (404), unterminated quote in `filter`. Observed: 400/404 with `{"error":"<message>"}`, no `code`; messages expose internal parameter names (`(Parameter 'intent')`, `'rawSql'`, `'request'`) and echo the submitted token. Expected: RFC 7807 problem bodies with a stable `code` from `ApiErrorCodes` and no internal parameter names. Issue draft: "REST data endpoint 4xx bodies lack a stable code and name internal parameters". 37 sweep cells.

Fixed 2026-10-23 on fix/parity-gaps (#295): REST data endpoint 4xx bodies carry a stable `code` (`INVALID_QUERY` and catalogue codes) with fixed messages.


### PARITY-GAP-005
Capability: string equality/LIKE with a literal operand. Channels: WebSQL and REST `filter` (parameters and GraphQL variables work). Input: literal strings `North'; DROP TABLE parity_sales; --`, `' UNION SELECT 1 --`, `/* c */ North` and `back\slash`, in `region = '...'`, `note = '...'`, `note LIKE '...'` (quotes doubled correctly). Observed: HTTP 400 `SQL_SYNTAX_ERROR` "Invalid SQL syntax." although the literal is well-formed. Strings with a quote but without `--`, `/*` or a backslash (`O'Brien`, `' OR '1'='1`) work. Expected: a quoted literal is data whatever it contains (or the rejection is a documented hardening with its own code). Issue draft: "Literals containing comment markers or backslash rejected as SQL syntax errors". 20 sweep cells.

Fixed 2026-10-23 on fix/parity-gaps (#296): a string literal with a comment marker or backslash is a documented rejection: 400 `SQL_LITERAL_NOT_PERMITTED` on WebSQL and REST; parameters and GraphQL variables remain the supported path.


### PARITY-GAP-006
Capability: typed date literal. Channel: WebSQL. Input: `SELECT id FROM parity_sales WHERE sale_date = DATE '2024-02-29'` (same for `TIMESTAMP '...'`). Observed: HTTP 422 `SQL_CONSTRUCT_NOT_SUPPORTED`. Expected: the ANSI typed literal is accepted and matches row 5, or the limitation is documented. Issue draft: "WebSQL does not support DATE/TIMESTAMP typed literals".

Fixed 2026-10-23 on fix/parity-gaps (#297): DATE and TIMESTAMP typed literals are accepted; on SQLite the value is bound and compared as ISO text.

### PARITY-GAP-007
Capability: date comparison via cast. Channel: WebSQL on SQLite. Input: `SELECT id FROM parity_sales WHERE sale_date = CAST('2024-02-29' AS DATE) ORDER BY id` (column holds ISO text). ## Phase 3 security conditions

Verdict: APPROVED WITH CONDITIONS (test-only code plus CI workflow; the plan's D-4/D-5/D-18 already cover the base controls).

- SEC-PAR-01 Workflow trigger and permissions: only `schedule` and `workflow_dispatch`; never `pull_request`, `pull_request_target`, `push`, `workflow_run`. Top-level `permissions: {}`, job `contents: read` only; no `secrets.*` and no `GITHUB_TOKEN` write scope; checkout with `persist-credentials: false`; all actions pinned by full SHA identical to `ci.yml`/`sql-compiler-gate-nightly.yml` (no tag refs).
- SEC-PAR-02 Input handling: `inputs.filter` and `inputs.seed` reach the shell only via `env:`; never `${{ }}` inside `run:`. Validate with the D-18 regexes (reject, not strip) BEFORE use, fail closed with exit 1. The filter is expanded quoted (`"$FILTER"`) and wrapped as `Category=Parity&Dialect!=Container&(<filter>)` so `|` cannot widen the selection beyond Parity; empty filter adds nothing. No `eval`, no unquoted expansion, no writing inputs to `$GITHUB_ENV`/`$GITHUB_OUTPUT`.
- SEC-PAR-03 Test auth: the parity project must not edit any file under `src/`, `Directory.Build.props`, Dockerfiles or production appsettings. `AutherisIncludeTestAuth=true` and `EnableTestAuthHandler=true` are set only in the Parity workflow, the test host (`ConfigureAppConfiguration`) and WP-local commands, never as a default. `ReleaseBuildExcludesTestAuthTests` stays green and is extended: neither `parity-nightly.yml` nor the Parity project may be referenced by `release.yml`/`docker-publish.yml` build steps, and no Dockerfile copies `tests/Autheris.Tests.Parity`.
- SEC-PAR-04 Isolation guard fail-closed: the D-4 architecture tests must FAIL (not skip) when the repo root, `.github/workflows`, or a workflow file cannot be found/parsed, and when zero `dotnet test` lines are matched (a vacuous pass is a failure). The guard also asserts that every workflow job that runs `Autheris.sln` or `tests/Autheris.Tests.Architecture` cannot reach Parity (via filter), and `ParityRunGuard` requires `AUTHERIS_PARITY_RUN=1` exactly (any other value throws). Each guard test has the negative self-check from D-4.
- SEC-PAR-05 KnownGap cannot hide security failures: (a) `KnownGap` is only legal on capability/error-code/dialect-shape cells and never on an authorization, tenant-isolation, masking, deny, or no-5xx assertion; the runner throws `InvalidOperationException` when a gapped cell carries `ParityAspect.Security`. (b) `KnownGapMessageBus` converts only `KnownGapObservedException`; any other exception, or a failure thrown from a `ParityAssert.Security*`/`NoServerError`/`NoLeak` call, stays a failure. (c) A gapped body that returns 2xx with data for a request the oracle expects denied/masked is a hard failure, never a gap. (d) `ParityIsolation_KnownGapIdsHaveDrafts` also forbids gap reasons/ids on Security-trait tests. (e) Gap count is capped by the baseline: a new `gap` outcome for a cell previously `pass` fails the report (already D-6).
- SEC-PAR-06 Report script: treat JSONL and baseline as untrusted data. Parse with `json` only, bound input (max 50 MB, max 200k lines, reject non-object lines, enforce `outcome` enum and `cellId` regex `^[A-Za-z0-9_.\-]{1,200}$`; invalid line => exit 1). Output to the step summary: HTML-escape and strip pipe/newline/backtick from every cell value, use no `eval`/`subprocess`/`shell=True`, write only to the given out path and `$GITHUB_STEP_SUMMARY`. Residual markdown injection after escaping is accepted (data originates from our own tests, summary is read-only, no secrets). Never print raw response bodies or seeds-of-data values into the summary.
- SEC-PAR-07 No-500 invariant leak check: `NoServerError` additionally fails when any error body/message/GraphQL `errors[].message` matches: .NET stack frames (`\bat [\w.<>`]+\(`, `\.cs:line \d+`), `System\.\w+Exception`, `Microsoft\.\w+`, SQL fragments/engine messages (`SQLite Error`, `SqliteException`, `near ".*": syntax error`, `no such (table|column)`, `Npgsql`, `SqlException`), file-system paths (`[A-Za-z]:\\`, `/(home|root|src|app|tmp)/`), connection-string tokens (`Data Source=`, `Password=`), and raw submitted SQL echoed back for 5xx. The check applies to ALL status codes (4xx and 501 too), not only 5xx. Matchers are unit-tested with positive and negative fixtures.
- SEC-PAR-08 Artifacts and logs: the parity run uses synthetic seed data only (no real tenant data, no secrets); uploaded artifacts contain trx/jsonl/markdown only, retention <= 14 days; test-auth headers are never logged in JSONL.

- Evidence: runner Verify throws drift (GovernanceMigrationRunnerBase.cs:125-165, diagnostics BuildDrift :229-240 with SchemaDeviation list); docs state no-upgrade policy (docs/configuration-guide.md:211, docs/features/f-gov-12-...md:35,73).

- Options (owner decision):
  A. Status quo + docs: release notes flag baseline-changing releases; document the schema-diff (drift report already lists deviations). Cost XS; pro: policy intact; con: pilot data lost.
  B. Publish DDL delta per baseline-changing release (generated from shape JSON diff, e.g. docs/upgrade/<from>-<to>.sql), caller (Talos) applies it. Cost S-M; pro: policy intact (Autheris still never migrates), data survives; con: maintenance and untested-in-prod risk, audit-trigger/PK changes (access_profile_assignments PK) need data backfill = caller's burden.
  C. Tooling: `--schema-diff`/`--emit-upgrade-ddl` CLI that prints (never executes) DDL from deviations. Cost M; pro: no hand-written deltas; con: PK changes/backfill not derivable.
  D. Export/import of consents+catalog+audit chain with anchor hand-over. Cost L-XL, Phase 3 mandatory (audit-chain integrity); con: new attack surface, conflicts with append-only audit guarantees.
  E. Forward-only migrations (reporter ask 1). Contradicts policy; L ongoing; listed only for completeness.
- Recommendation: A now (release-note rule + runbook section "upgrading a pilot DB") plus C-lite/B: ship the DDL delta per release generated from shape JSON diffs as a CI artifact; defer D/E until a stable-schema decision. Owner decides.

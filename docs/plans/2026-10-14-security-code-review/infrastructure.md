# Security review: src/Autheris.Infrastructure (excluding Plugins)

### Medium — Caller-managed audit writes (PostgreSQL / SQL Server) skip the chain lock, causing seq collisions and a latched false "chain violation"
- **File:** `src/Autheris.Infrastructure/Persistence/PostgreSqlGovernanceRepository.Audit.cs:343-429` (enrolled path) vs `:431-460` (locked path), `:246-272`, `:1034-1039`; same structure in `src/Autheris.Infrastructure/Persistence/SqlServerGovernanceRepository.Audit.cs:345-440` and `:450-470`
- **CWE:** CWE-362 (race condition) / CWE-693
- **Confidence:** Likely (code path traced end to end, not executed)
- **Issue:** `WriteAuditBatchOnceAsync` serialises writers with `pg_advisory_xact_lock` / `sp_getapplock`, but `WriteAuditBatchEnrolledAsync` (used by every consent create/revoke/extend/approve/reject via `RecordAuditEventAsync(entry, tx, ct)`) takes no lock. It reads the committed tail, inserts seq n+1 inside the still-open business transaction, and immediately and tentatively advances the process-wide `_lastAuditSeq`/`_lastAuditHash` to n+1 before the commit. A concurrent locked writer (Tier-B flush every >=10 ms, any Tier-A audit event, another replica) reads the DB tail n (the row is uncommitted), sees `dbTailSeq < knownSeq` and calls `FlagAuditChainViolation(...)`. That method uses `_auditChainViolation ??= reason`, so the flag is permanent for the process lifetime. Two overlapping enrolled transactions (two approvals, or two replicas) both choose seq n+1; the second blocks on `idx_audit_seq` and then fails with a unique violation, which is not retried on this path, so the consent mutation fails.
- **Exploit scenario:** Any authenticated user who can submit consent requests / approvers who act concurrently with normal query traffic (which produces TABLE_QUERY audit events flushed by the background writer) hit the window between the audit INSERT and `CommitAsync` (it also spans `IncrementTableEpochInternalAsync`). The process latches a violation: `VerifyAuditHashChainAsync` returns false forever, the signed anchor stops advancing (`_auditChainViolation == null` guard), `AuditWormExportService` aborts with "tampering detected", and readiness fails if `FailReadinessOnChainViolation` is set. An attacker with the ability to generate concurrent consent traffic can therefore blind WORM export/anchoring (and, conversely, a real tamper alert is indistinguishable from this noise) until restart.
- **Remediation:** Acquire the same advisory/app lock inside the enrolled transaction before `ReadAuditTail` (`SELECT pg_advisory_xact_lock(@k)` / `sp_getapplock @LockOwner='Transaction'` on `tx`), and do not mutate `_lastAuditSeq/_lastAuditHash` before commit; keep tentative state only in `_pendingAuditTxStates` and publish it in `OnTransactionCommitted`. In `WriteAuditBatchOnceAsync`, compare the DB tail against the last *committed* state only (ignore pending transaction state), and wrap enrolled writes in the same retry-on-unique-violation logic as the locked path.

### Medium — Regression/incomplete fix of SEC-H-06: ITSM ticket lookup is not tenant-scoped on PostgreSQL and SQL Server
- **File:** `src/Autheris.Infrastructure/Persistence/PostgreSqlGovernanceRepository.Consent.cs:1391-1399`; `src/Autheris.Infrastructure/Persistence/SqlServerGovernanceRepository.Consent.cs:1366-1376`; default interface method `src/Autheris.Application/Interfaces/IGovernanceRepository.cs:99-103`; caller `src/Autheris.Extensions/Itsm/ItsmWebhookHandler.cs:323`
- **CWE:** CWE-639 (authorization bypass through user-controlled key) / CWE-284
- **Confidence:** Confirmed (only SQLite overrides the `TenantId` overload, `SqliteGovernanceRepository.Consent.cs:674`)
- **Issue:** The interface documents that persistent repositories override the tenant overload with `WHERE itsm_ticket_id = @t AND tenant_id = @tenant`. PostgreSQL and SQL Server do not: the default implementation runs the unscoped `SELECT id ... WHERE itsm_ticket_id = @ticket ORDER BY requested_at, id LIMIT 1` and post-filters the single oldest row by tenant. The PG-12 unique index is per `(tenant_id, itsm_ticket_id)`, so identical ticket ids in different tenants are explicitly allowed (separate ServiceNow/Jira instances reuse `INC0010001`, `GOV-1`).
- **Exploit scenario:** Tenant A (controlling its own ITSM instance or ticket numbering) holds an older request with ticket id `INC0010001`. A signed webhook for tenant B's ticket `INC0010001` resolves `GetConsentRequestByTicketIdAsync(ticket, tenantB)` to tenant A's row, the post-filter discards it and returns null, so tenant B's approval/rejection/revocation callbacks are silently dropped and B's requests stay pending (cross-tenant denial of governance workflow). With `warn_fallback_default_tenant_for_webhooks` enabled the unscoped fallback returns tenant A's request for tenant B's callback.
- **Remediation:** Override `GetConsentRequestByTicketIdAsync(string, TenantId, CancellationToken)` in the PostgreSQL and SQL Server repositories with `WHERE itsm_ticket_id = @ticket AND COALESCE(tenant_id,'') = @tenant`, and remove the unscoped one-row-then-filter default from the interface (make the tenant overload abstract).

### Low — External audit anchor can be moved backwards by the caller-transaction commit path (PostgreSQL / SQL Server)
- **File:** `src/Autheris.Infrastructure/Persistence/PostgreSqlGovernanceRepository.Audit.cs:246-272` (compare `:524-545`); `src/Autheris.Infrastructure/Persistence/SqlServerGovernanceRepository.Audit.cs:246-272`
- **CWE:** CWE-367 / CWE-354
- **Confidence:** Likely
- **Issue:** `OnTransactionCommitted` calls `_auditAnchorStore.Save(CreateSignedAnchor(state.LastSeq, ...))` unconditionally, whereas the batch path explicitly guards "replicas sharing one anchor store must never move the anchor backwards" (loads the current anchor and saves only if `current.Sequence < anchor.Sequence`). A replica that commits a consent transaction at seq 100 after another replica/thread already anchored seq 105 overwrites a `FileAuditChainAnchorStore` anchor with the older value (the primary file store is last-writer-wins).
- **Exploit scenario:** After the regression, an attacker with DB write access who truncates the tail between seq 100 and 105 is not detected at the next restart (`InitializeAuditChainAnchor` compares only against the regressed anchor). Requires concurrent writers on a shared anchor path and DB write access.
- **Remediation:** Apply the same monotonic check (and ideally a compare-and-swap in the store) in `OnTransactionCommitted`; make `FileAuditChainAnchorStore.Save` refuse a lower sequence than the signed anchor on disk.

### Low — Detected audit chain violation does not fail closed; PostgreSQL even clears the fault flag on the next successful batch
- **File:** `src/Autheris.Infrastructure/Persistence/PostgreSqlGovernanceRepository.Audit.cs:48-52,130-137,1034-1039`; `src/Autheris.Infrastructure/Persistence/SqliteGovernanceRepository.Audit.cs:38-42,1040-1045`; `src/Autheris.Infrastructure/Persistence/SqlServerGovernanceRepository.Audit.cs:1068`
- **CWE:** CWE-636 (not failing securely)
- **Confidence:** Confirmed
- **Issue:** Tier-B admission checks only the field `_isAuditPipelineFaulted`, not the `IsAuditPipelineFaulted` property that includes `_auditChainViolation`. On SQLite `FlagAuditChainViolation` does not touch the field at all. On PostgreSQL/SQL Server it sets `_isAuditPipelineFaulted = true`, but the background writer resets it to false after the next successful batch ("AU-05 recovered"), while `_auditChainViolation` remains. Tier-A writes never consult either. The only reactions are the readiness probe (optional) and a log line; the gateway keeps serving data and appending to a chain known to be tampered.
- **Exploit scenario:** An insider truncates/rewrites audit rows; the violation is flagged, yet queries on sensitive tables continue to be answered with the "tamper-evident" audit trail silently continuing, which contradicts the documented fail-closed behaviour.
- **Remediation:** Gate Tier-B and Tier-A admission on `IsAuditPipelineFaulted` (property) or make the recovery path clear only the write-failure flag and never an integrity violation; make the response to a violation configurable (deny data access vs. alert only) and default it to deny outside Development.

### Low — Hardcoded legacy HMAC key accepted when verifying SQLite audit rows without `seq`
- **File:** `src/Autheris.Infrastructure/Persistence/SqliteGovernanceRepository.Audit.cs:703-714`
- **CWE:** CWE-798
- **Confidence:** Likely
- **Issue:** Rows whose `seq` is NULL are accepted if their hash validates under the compile-time constant `"AutherisAuditLogHmacTamperEvidenceSecret2026!"`. The key is public (source repository), so any party with DB write access can create valid "legacy" rows without knowing the audit key. Rows after the first sequenced row are rejected, which limits the abuse to the head of the chain.
- **Exploit scenario:** In an environment with no or a removable anchor (default `<db>.audit-anchor.json` sits next to the database; Development/Test trust-on-first-use), an attacker rewrites the entire table as NULL-seq rows sealed with the public key and deletes the anchor file; `VerifyAuditHashChainAsync` then succeeds after restart.
- **Remediation:** Only accept the legacy path when an explicit migration flag is set and a signed anchor proves the sequenced boundary; otherwise drop the fallback. Better: migrate legacy rows once (re-seal under the real key, record the boundary in the signed anchor) and delete the constant.

### Low — Token revocation lookups fail open when Redis/Garnet is unreachable
- **File:** `src/Autheris.Infrastructure/Security/RedisTokenRevocationService.cs:131-189`
- **CWE:** CWE-636 / CWE-613
- **Confidence:** Likely (documented as intended in the class comment, but there is no option to fail closed)
- **Issue:** `IsRevokedAsync` swallows Redis exceptions (outer catch and per-key catch) and returns false; only revocations issued on this node (`_local`) survive. Revocation events published while a node was disconnected (pub/sub is lossy) are never replayed after `ConnectionRestored`, but the Redis key itself remains authoritative afterwards, so exposure is limited to the outage window.
- **Exploit scenario:** A user's token is revoked on node A; an attacker (or the DoS-ing user) degrades Redis connectivity to node B (or exploits an outage) and keeps using the revoked token against B until the outage ends or the token expires.
- **Remediation:** Add `Caching.Redis.FailClosedOnRevocationLookupError` (default true in production): when `_multiplexer.IsConnected` is false or a lookup faults, return `true` (revoked) for tokens older than a short grace, or force re-authentication, mirroring `FailClosedOnSensitiveTables` in `EpochValidationService`.

## Verified strengths
- All SQL in the SQLite/PostgreSQL/SQL Server governance repositories, `TenantRegistryStore`, `VirtualFilterStore` and the catalog metadata readers is parameterised; the only interpolated fragments are fixed `tenantFilter`/`whereSql` fragments built from constants and `@cid{i}` parameter names (`PostgreSqlGovernanceRepository.Audit.cs:557,614`, `SqliteGovernanceRepository.Consent.cs:463,505`). No LIKE patterns built from input were found.
- Consent/virtual-filter/access-profile reads carry tenant predicates and the GraphQL mutation layer re-checks `req.TenantId`/`consent.TenantId` against the caller tenant before calling repository methods that take only a GUID.
- Audit canonicalisation (`AuditCanonicalizer`) escapes `\`, `|`, CR, LF, TAB, so field concatenation is unambiguous; HMAC-SHA256 key is HKDF-separated from masking, anchor and L2 keys; production requires a Key Vault key, anchor store and rejects in-memory SQLite; hash comparisons use `FixedTimeEquals`; the PG/SQL Server locked writer path uses advisory/app locks plus a unique index on `seq` with retry.
- Anchor stores: signed anchors, append-only WORM directory, composite newest-wins with conflict detection, asymmetric KMS signature option, poisoned-file skipping.
- Consent L2 cache entries are HMAC-framed over key, expiry and payload with a domain-separated HKDF key, epoch-validated, never TTL-extended on promotion; the epoch service detects Redis rollback and fails closed for sensitive tables.
- Redis security: auth required outside Development, TLS enforced for non-loopback endpoints, certificate pinning, embedded Garnet always password-protected and loopback-only outside Development; `ConnectionTlsPolicy` enforces VerifyCA/VerifyFull and Encrypt for governance DBs and is also applied to data sources at startup.
- Rate limiter uses atomic Lua scripts, hash-tag sanitisation, bounded in-memory maps and degrades to a halved local budget then fails closed; idempotency keys are scoped by user, operation, tenant and argument fingerprint.
- Databricks client: exact DNS host policy, URLs built only from the configured host, redirects rejected, bounded response buffers, tokens never logged, hardened outbound handlers.
- `DefaultEnvironmentSecretProvider`: path allow-list and symlink check for `file:` refs, minimum key length, no secret echo in errors, instance-specific ITSM refs never fall back to global secrets.

## Areas not covered
- `src/Autheris.Infrastructure/Plugins` (other reviewer); the Application/Extensions-side callers were only read where needed to confirm reachability.
- `Cdn/*PurgeService` (`CloudflareCdnPurgeService` reports success when unconfigured, and interpolates `ZoneId` unescaped) is registered but `PurgeTagsAsync` has no caller, so no finding was raised; revisit when it is wired.
- Repository-level cross-tenant hardening: `RevokeConsentAsync`, `ExtendConsentExpiryAsync`, `ApproveConsentRequestStepAsync`, `RejectConsentRequestAsync` and the catalog/data-owner tables are GUID- or name-keyed with no tenant parameter (DATA_OWNERS/TABLE_OWNERS are global); only the GraphQL layer enforces tenancy. The nullable `TenantId?` parameters (`GetAuditLogEntriesAsync`, `QueryAuditLogsAsync`, `GetActiveConsentsForSubjectsAsync`) mean "all tenants" when null; all call sites reviewed pass a tenant, but `LineageImpactAnalyzerService` passes `callerContext?.TenantId` (line 406) which I did not trace to a non-null guarantee.
- Redis ReBAC tuples, idempotency payloads and cluster-state values are stored as plain JSON without integrity protection (unlike consent L2); treated as inside the Redis trust boundary, not reported.
- `PostgreSqlLogicalReplicationService` is a stub (no replication connection), `AI/` contains only a local deterministic embedding generator (no external endpoints, so no SSRF/prompt-leak surface); SQL Server/PostgreSQL schema DDL and `OracleConnectionSupport`/`BindByNameOracleConnection` were skimmed, not line-audited.
- No code was executed; race findings are from static tracing.

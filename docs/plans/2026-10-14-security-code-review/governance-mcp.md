# Security review: Governance / Security / Policy / Audit / MCP / Extensibility / State / Domain

Scope: `src/Autheris.Application/{Governance,Security,Policy,Audit,Mcp,Extensibility,State,ResourceGroups,Common}`, `src/Autheris.Domain/{Security,Audit,Model,Options}`. Read-only review; callers in Api/GraphQL were traced only to confirm reachability.

### High — MCP Four-Eyes (and MCP-specific ABAC pre-check) evaluate the wrong table for `query_sql` and `invoke_api`
- **File:** `src/Autheris.Application/Mcp/Services/McpDatasetTools.cs:65-90,120-135`; `src/Autheris.Application/Mcp/Services/AiDataGuardrailService.cs:433-470`
- **CWE:** CWE-863 (Incorrect Authorization) / CWE-807
- **Confidence:** Confirmed
- **Issue:** `RequiresFourEyes` is enforced only in `AiDataGuardrailService` (grep: no other enforcement site), and only for the table(s) returned by `ParseTablesFromTool`. For `query_sql` the table is taken from the *first* regex match of `\bFROM\s+([a-zA-Z0-9_\.]+)` over the raw SQL (`ExtractTableFromSql`). Comments, string literals, JOINs, comma joins, UNIONs and subqueries are ignored. For `invoke_api` the "table" is the constant `governance.api.invoke`, although the tool reads arbitrary datasets via `/api/v1/data/{domain}/{schema}/{table}` and `POST /api/v1/statement` (ApiDispatcherService). The downstream governed pipeline still enforces consent/Casbin/ReBAC per table, but nothing there enforces Four-Eyes, so the HitL step-up gate is skipped. The same wrong object is also what the MCP-purpose Casbin pre-check (`PurposeId = MCP_AI_AGENT_QUERY`) and the inactive-table check are evaluated against.
- **Exploit scenario:** A caller with a consent on `finance.dbo.salaries` (`RequiresFourEyes = true`) sends `query_sql {"query":"SELECT s.* FROM public.dbo.dummy d JOIN finance.dbo.salaries s ON 1=1"}`, or `SELECT /* FROM public.dbo.dummy */ * FROM finance.dbo.salaries`, or `invoke_api {"endpoint":"/api/v1/data/finance/dbo/salaries"}`. The gate resolves `public.dbo.dummy` / `governance.api.invoke`, finds no `RequiresFourEyes`, and the query runs with no approver. Art. 9 / L3-L4 data is read without the mandatory human approval, and any Casbin deny rule keyed on the MCP purpose for the real table is bypassed as well.
- **Remediation:** Do not derive tables in the guardrail from text. Either (a) let the SQL engine's analysis (`_sqlEngine.Analyze(...).ReferencedTables`, already used in `GovernedSqlRewriter`) supply the full table set and run the ABAC/inactive/Four-Eyes loop over every referenced table, failing closed when analysis fails; or (b) move the Four-Eyes check into `TableAccessPolicy`/`GovernedSqlRewriter` where each resolved table is known. For `invoke_api`, resolve the endpoint (`ApiDispatcherService.ExtractTableIdentifier`) before the guardrail and return that `TableIdentifier`; deny unknown endpoints. Example: `var tables = await _sqlAnalyzer.GetReferencedTablesAsync(sql, ct) ?? throw new SecurityException("unresolvable");` then `foreach (var t in tables) { ...four-eyes... }`.

### High — MCP admin tools gate accepts `TenantAdmin` but operates on global state and ignores the caller's tenant
- **File:** `src/Autheris.Application/Mcp/Services/AiDataGuardrailService.cs:231-247`; `src/Autheris.Application/Governance/Services/AccessPlanningService.cs:256,278,342,374-420`; `src/Autheris.Application/Mcp/Tools/McpAdminTools.cs:134-186`
- **CWE:** CWE-639 / CWE-284 (tenant isolation, authorization bypass through user-controlled key)
- **Confidence:** Confirmed
- **Issue:** The admin gate is `ClusterAdmin || GovernanceAdmin || TenantAdmin` (the tool description and the error message both say only Governance/Cluster admin). `McpAdminTools.ExecuteAdminToolAsync` passes only `adminSid`, never `sessionContext.TenantId`, to `IAccessPlanningService`. `SetDatasetStateAsync` loads and upserts the catalog `TableMetadata` by `TableIdentifier` only (the catalog is shared across tenants) and flips `IsActive`; the audit entry is written with `TenantId.LegacySingleTenant`. `ApplyAccessAsync` derives the ReBAC tenant from the dataset's *domain* (`tableId.Domain`), so the admin picks the tenant namespace for the tuples, and calls `ReloadPoliciesAsync(new TenantId(domain))`.
- **Exploit scenario:** A holder of an unprefixed `TenantAdmin` role in tenant A calls `admin_set_dataset_state {"datasetId":"sales.public.orders","state":"inactive"}` for a table used by tenant B. `TableAccessPolicy` denies inactive tables for every tenant, so tenant B is cut off (or, conversely, `state:"active"` re-enables a table governance had quarantined). The action is audited under the legacy single tenant, so tenant B's audit trail does not show it. `admin_apply_access` with `datasetId:"B.s.t"` writes ReBAC tuples into namespace `B` and forces a policy reload for `B`.
- **Remediation:** Restrict the MCP admin gate to the documented roles (`ClusterAdmin`, `GovernanceAdmin`) via `SecurityPrincipalContext.HasRole(GatewayRole...)` rather than raw role-string `Contains`. If TenantAdmin must be allowed, add `TenantId callerTenant` to every `IAccessPlanningService` method, verify the target table/domain is owned by that tenant, use the caller's tenant for ReBAC tuples, reload and audit, and reject mismatches. Add a read-only-session check (see below).

### Medium — HitL approval HMAC key is derived from the Key Vault *reference string*, not the secret
- **File:** `src/Autheris.Application/Mcp/Services/HitLStepUpApprovalService.cs:30-44` (consumers 182-218, 454-455, 587-590, 612-624)
- **CWE:** CWE-321 (Hard-coded/Predictable Cryptographic Key) / CWE-798
- **Confidence:** Confirmed
- **Issue:** `ResolveHitLHmacKey` runs `HKDF(UTF8(options.DataMasking.HmacSecretKeyVaultRef))`. Every other consumer (`ColumnMaskingProvider`, governance repositories) resolves that value through `IKeyVaultSecretProvider.GetSecretBytes`, and the startup validator requires it to be "a valid Key Vault secret reference", i.e. a non-secret locator such as `vault://kv/hmac`. The HKDF has no salt and the info string is constant, so the ticket/broadcast signing key is a function of a value that is in configuration, deployment manifests and logs. If the option is unset or the dev literal, a per-process random key is used (cluster approvals then fail on other nodes, fail-closed but non-functional).
- **Exploit scenario:** An attacker with write access to the shared Redis/Garnet (a different trust level than the gateway) reads the config reference, derives the key, and publishes a correctly signed `HitLApprovalBroadcast{IsApproved=true, ApproverSid="x"}` on `hitl:events:{approvalId}` (the approval id is visible on pub/sub), or forges `hitl:ticket:{id}` records. The waiting MCP request is released without any human approver or TOTP.
- **Remediation:** Resolve the secret first: `var bytes = secretProvider.GetSecretBytes(ref); SecretKeyRequirements.EnsureMinimumLength(bytes, "HitL signing key", isDev); HKDF.DeriveKey(SHA256, bytes, 32, salt: clusterSalt, info: "Autheris:HitLStepUp:v1")`. Fail startup outside Development when no cluster-shared key is available while `IDistributedClusterStateProvider` is configured. Include `TenantId` and `ExpiresAt` in the broadcast signature.

### Medium — TOTP replay protection is a non-atomic check-then-set (same code usable more than once)
- **File:** `src/Autheris.Application/Security/Totp/Services/TotpVerificationService.cs:96-131`
- **CWE:** CWE-367 (TOCTOU) / CWE-294
- **Confidence:** Confirmed
- **Issue:** `VerifyAndConsumeTotpAsync` does `_localConsumed.TryGetValue` → `await _clusterState.GetAsync` → `_localConsumed[key] = ...` → `await SetAsync`. Two concurrent calls with the same code both pass the checks before either writes (the awaited cluster read widens the window to a network round trip, and across nodes there is no coordination at all). If the cluster store throws, only the node-local cache remains.
- **Exploit scenario:** An approver (or an attacker who shoulder-surfed/phished one valid code) submits the same code concurrently to `/hitl/approve` for two tickets, or to `ConfirmPlanAsync` plus a HitL approval, on two nodes. Both are accepted although the code is "single use" (RFC 6238 §5.2).
- **Remediation:** Use an atomic primitive: `_localConsumed.TryAdd(replayKey, expiry)` locally and `IncrementAsync(replayKey, 1, ttl) == 1` (already atomic in `IDistributedClusterStateProvider`) cluster-wide. Treat `null`/exception from the store as failure when `RequireTotp2Fa` is set (fail-closed) instead of silently falling back to the local cache. Consume only after all other preconditions pass.

### Medium — TOTP secret revocation is ineffective on nodes that cached the secret
- **File:** `src/Autheris.Application/Security/Totp/Services/ClusterTotpSecretStore.cs:55-73,82-95`
- **CWE:** CWE-613 (Insufficient Session/Credential Expiration) / CWE-459
- **Confidence:** Confirmed
- **Issue:** `GetSecretAsync` writes every remote read into the unbounded, TTL-less `_localSecrets`. When the remote key is absent it falls through to the local cache. `RemoveSecretAsync` removes the secret from Redis and only the *local* map of the node that handled the call; other nodes keep returning the revoked seed indefinitely (until restart). A failed remote `RemoveAsync` is swallowed too.
- **Exploit scenario:** Security revokes the enrolled TOTP of a compromised approver. Node B still holds the seed from earlier approvals, so the attacker's generated codes keep passing `HitLStepUpApprovalService`/`AccessPlanningService` step-up on node B.
- **Remediation:** Treat the cluster store as authoritative when configured: on a successful read returning null, evict the local entry and return null; use the local map only when the store throws and then with a short TTL. Publish a revocation event (like the other caches) to clear local copies; propagate `RemoveAsync` failures.

### Medium — No attempt throttling or lockout in TOTP verification
- **File:** `src/Autheris.Application/Security/Totp/Services/TotpVerificationService.cs:74-97,159-206`; callers `HitLStepUpApprovalService.cs:369-411`, `AccessPlanningService.cs:215-221`, `ClassificationWorkflowStateMachine.cs:166-193`
- **CWE:** CWE-307 (Improper Restriction of Excessive Authentication Attempts)
- **Confidence:** Likely
- **Issue:** Failed verifications are neither counted nor delayed per user. `TryMatchStep` accepts 3 time steps × (SHA-1 and SHA-256), i.e. ~6 valid values out of 10^6 per attempt. The only lockout in the codebase is `BasicAuthAttemptGuard` (Basic auth); I found no TOTP-specific limiter. An invalid code does not invalidate the ticket, so the approval endpoint can be retried for the 15 s default timeout (and for tickets with longer timeouts).
- **Exploit scenario:** A hijacked approver session (without the second factor) scripts guesses against `/api/hitl/approve`; expected ~170k guesses to hit a valid code. Only generic rate limiting (if any) slows this.
- **Remediation:** Add a per-`userSid` failure counter (`IncrementAsync("totp:fail:{sid}", 1, window)`) with lockout after N failures (e.g. 5/5 min), return the same error while locked, audit lockouts, and accept only SHA-1 unless the enrolment explicitly recorded SHA-256.

### Medium — A matching Access Profile replaces consent resolution, including Deny consents and purpose limits
- **File:** `src/Autheris.Application/Policy/TableAccessPolicy.cs:255-300` (`CreateDecisionFromProfile` 640-690)
- **CWE:** CWE-863 / CWE-285
- **Confidence:** Likely (code path confirmed; intended semantics per `docs/features/f-gov-11-declarative-access-profiles.md` is only a *masking exemption*)
- **Issue:** `DecideCoreAsync` branches `if (profile != null) decision = CreateDecisionFromProfile(...)`, `else if (consentBypassed) ... else ResolveConsentAsync(...)`. When any active profile with `MatchesTable` exists for the subject, the consent repository is never consulted. The decision is `Allowed` for the table regardless of whether any Allow consent exists, ignores Deny consents (Deny-precedence), consent validity/purpose/row filters, and, with `MaskingMode.Unmasked`, returns `Clear` for all columns even where consent says `Mask`/`Deny`. Profiles with patterns such as `*.*` grant table access to all tables. `FirstOrDefault` also makes the choice between several matching profiles order-dependent (a broad `Unmasked` profile can shadow a stricter one).
- **Exploit scenario:** A user who has an `Unmasked` profile for `sales.*` (granted as a masking exemption) is later put under a Deny consent (objection/legal hold) or never had an Allow on `sales.payroll`. Both are ignored: the user reads `sales.payroll` unmasked. Casbin still applies if the tenant has rules.
- **Remediation:** Resolve consents first and apply the profile only as a restriction/exemption on an already-allowed decision (never as an allow source): `decision = await ResolveConsentAsync(...); if (decision.IsAllowed && profile != null) decision = ApplyProfileMasking(decision, profile)`. Honor Deny consents before profiles; pick the most restrictive matching profile deterministically.

### Medium — MCP hybrid tools run as the OAuth client instead of the user and drop groups, claims and the read-only marker
- **File:** `src/Autheris.Application/Mcp/Services/McpToolExecutionHandler.cs:63-92,273-296`; caller construction `src/Autheris.Api/Endpoints/McpEndpoints.cs:175-226`
- **CWE:** CWE-287 / CWE-266 (identity confusion) / CWE-639
- **Confidence:** Confirmed (principal construction); impact applies to tokens whose `client_id`/`appid` differs from the user
- **Issue:** `ResolveCaller` sets `ServicePrincipalId` to `client_id ?? appid ?? NameIdentifier ...` and `UserSid` to the user. `BuildUserPrincipal` puts `ServicePrincipalId` into `ClaimTypes.NameIdentifier` and the user only into `sub`, with no `PrimarySid`. `ClaimsPrincipalExtensions.GetUserSid()` (Sid.cs:25-36) prefers `NameIdentifier` over `sub`, so `GovernedSqlRewriter` (`user.GetUserSid()` at line 259) evaluates consent, Casbin, RLS and audit for the **client application** SID for `query_sql` and `invoke_api /api/v1/statement`. Group SID claims, `AdditionalClaims` (department/region/clearance/scope/contract) and the `TokenAccessScope` read-only marker are also not copied (the sibling builders `GatewayMcpQueryExecutor.BuildPrincipal` and `McpProtocolHandler.BuildPrincipalFromSession` do copy them). `query_dataset` uses `CallerSecurityContext(UserSid ?? SP)` so the same request is authorized under two different identities.
- **Exploit scenario:** Every user of a shared MCP client app (e.g. an internal copilot with a broad app-level consent) obtains that app's access through `query_sql`, regardless of their own consents; a user who is denied in `query_dataset` succeeds in `query_sql`. Audit records name the app, not the user, and per-user RLS attributes are lost.
- **Remediation:** Build the principal exactly like `GatewayMcpQueryExecutor.BuildPrincipal` (PrimarySid = UserSid, group SIDs, `AdditionalClaims`, `TokenAccessScope.MarkReadOnly`). Better, share one `McpPrincipalFactory`. Add a unit test asserting `GetUserSid()` equals `session.UserSid` when both are set.

### Medium — Read-only tokens are not enforced for MCP admin tools, and the SQL/API path loses the read-only marker
- **File:** `src/Autheris.Application/Mcp/Services/AiDataGuardrailService.cs:231-270`; `src/Autheris.Application/Mcp/Services/McpToolExecutionHandler.cs:273-296`; `src/Autheris.Application/Sql/Services/GovernedSqlRewriter.cs:207-211`
- **CWE:** CWE-863 / CWE-693
- **Confidence:** Confirmed (no `IsReadOnly` check outside `McpDocTools`; DML part needs `WebSql.AllowDml` + writer role)
- **Issue:** `ReadOnlyTokenMiddleware` deliberately lets `POST /mcp` through for read-only tokens (it is a query path) and relies on the tools. Only `McpDocTools.deposit_documentation` checks `sessionContext.IsReadOnly`. `admin_apply_access`, `admin_register_datasource` and `admin_set_dataset_state` do not. For `query_sql`/`invoke_api` the principal built by `McpToolExecutionHandler` lacks the marker, so `GovernedSqlRewriter` (`user.IsReadOnly()`) never rejects DML for a delegated-agent/app-only token.
- **Exploit scenario:** A read-only app-only token that carries a `TenantAdmin`/`GovernanceAdmin` app role calls `admin_set_dataset_state`/`admin_apply_access`. A read-only token whose subject holds a `DmlWriterRoles` role runs `INSERT/UPDATE/DELETE` through `query_sql`.
- **Remediation:** At the top of `ExecuteToolWithGuardrailAsync`, if `sessionContext.IsReadOnly` deny every non-read tool (admin tools, `deposit_documentation`, any `ReadsRows == false` mutating path) and propagate the marker in `BuildUserPrincipal`.

### Medium — Classification workflow state machine has no state precondition, no distinct-approver binding, and trusts caller-supplied proposal/reviewer
- **File:** `src/Autheris.Application/Governance/Services/ClassificationWorkflowStateMachine.cs:82-205,215-266`; reachability `src/Autheris.Api/Endpoints/GovernanceClassificationEndpoints.cs:70-78`
- **CWE:** CWE-841 (Improper Enforcement of Behavioral Workflow) / CWE-639
- **Confidence:** Confirmed
- **Issue:** `TransitionAsync` never checks `proposal.Status`. A `DATA_GOVERNANCE_REVIEWER` APPROVE moves any proposal (`UNCLASSIFIED`, `PENDING_OWNER_REVIEW`, `REJECTED`, `CLASSIFIED`) straight to `CLASSIFIED`, skipping the Data-Owner stage. The second stage is not required to differ from the first (the stage-1 approver is not recorded, SoD only compares the Data Owner with the governance reviewer). Step-up is only validated when both TOTP services are non-null; otherwise any non-blank `StepUpAuthToken` string passes (line 166-167 falls into the `else` at 193). `POST /api/governance/classification/transition` deserializes the whole `Proposal` and `Request` (ReviewerSid, ReviewerRole, StepUpAuthToken, column ranks) from the body, and `SaveProposalAsync` persists the client-supplied proposal with the new status.
- **Exploit scenario:** A single GovernanceAdmin posts a forged proposal (`DataOwnerSid=null`, all column ranks 0, `Status=PENDING_OWNER_REVIEW`) and a request with `ReviewerRole="DATA_GOVERNANCE_REVIEWER"`: one call yields `CLASSIFIED` with no second person and no step-up, downgrading a table's sensitivity (which later drives masking and Four-Eyes). A reviewer with the Compliance role can also seal a proposal that the data owner never reviewed, or re-approve a rejected one.
- **Remediation:** Load the stored proposal by `proposalId` inside the service (ignore the supplied one), assert allowed predecessor states (`PENDING_OWNER_REVIEW→PENDING_GOVERNANCE_REVIEW→CLASSIFIED`), persist stage-1 approver SID and require `ReviewerSid != stage1Approver && != DataOwnerSid` at stage 2, derive reviewer SID/role from the authenticated principal, and fail closed when the step-up services are missing and the rank exceeds the threshold.

### Low — `":ClusterAdmin"` / `":GovernanceAdmin"` role values bypass the tenant-prefix guard in `GatewayRoleEvaluator`
- **File:** `src/Autheris.Application/Security/GatewayRoleEvaluator.cs:196-209`; `src/Autheris.Domain/Security/GatewayRole.cs:50-60`
- **CWE:** CWE-20 / CWE-285
- **Confidence:** Confirmed
- **Issue:** Prefix handling uses `raw.IndexOf(':') > 0`. A role value starting with `:` (index 0) takes the "global role" branch, where `TryParseRole` uses `LastIndexOf(':')` and strips everything before it, so `":ClusterAdmin"` parses as the global `ClusterAdmin` (implies all roles). `ClusterAdminPolicy`/`SecurityPrincipalContext` use exact matching and are not affected, so the two evaluators disagree.
- **Exploit scenario:** An IdP that lets a tenant administrator define role/app-role values (multi-tenant app registrations) can emit `:ClusterAdmin`, which `GatewayRoleEvaluator.HasRole` honours although tenant-scoped assignment of `ClusterAdmin` is meant to be ignored.
- **Remediation:** In the global branch use exact `NameToRole` lookup without prefix stripping (`TryParseRole` strict overload that rejects any `:`), and treat a leading `:` as malformed.

### Low — TOTP seeds are stored and cached in plaintext
- **File:** `src/Autheris.Application/Security/Totp/Services/ClusterTotpSecretStore.cs:25-40`; `InMemoryTotpSecretStore.cs`
- **CWE:** CWE-312 / CWE-256
- **Confidence:** Confirmed
- **Issue:** Base32 seeds are written as plain strings to the shared cluster state (key `totp:secret:{sid}`, 365 d TTL) and kept in process memory. Redis read access yields all second factors, which also defeats the HitL signing (see above).
- **Exploit scenario:** Read-only access to Redis (backup, MONITOR, misconfigured ACL) lets an attacker generate valid codes for every enrolled approver/admin.
- **Remediation:** Envelope-encrypt seeds with a key from `IKeyVaultSecretProvider` (AES-GCM, key id in the record) before `SetAsync`; store only ciphertext in the cluster store.

### Low — Access-plan state is per-node, unbounded, and the apply step is not bound to the confirming admin
- **File:** `src/Autheris.Application/Governance/Services/AccessPlanningService.cs:44-50,96-134,226-254,452-480`
- **CWE:** CWE-770 / CWE-841
- **Confidence:** Confirmed
- **Issue:** `_plans` and `_consumedTokens` are never pruned (each `admin_plan_access` adds an entry for the life of the process; any admin-role holder can grow memory without bound). The confirmation HMAC key is `RandomNumberGenerator.GetBytes(32)` per process, so a token issued on one node cannot be applied on another. `ApplyAccessAsync` checks the token HMAC and plan id but not that the caller `adminSid` equals the plan/confirming admin, so a leaked token is usable by any admin session. `ResolvePrincipalAsync` returns a hard-coded demo directory (`S-1-5-21-1001`...) in production.
- **Exploit scenario:** A looped `admin_plan_access` call exhausts memory; a token pasted into a ticket/chat can be replayed by another admin within 10 minutes (once).
- **Remediation:** Persist plans in the cluster store with TTL, use a shared signing key from the secret provider, compare `stored.AdminSid` in `ApplyAccessAsync`, cap plans per admin, remove the demo directory outside Development.

## Verified strengths
- Casbin evaluation (`CasbinEnforcementService`): immutable snapshots, deny-first with fail-closed on unevaluable deny `sub_rule`, `MatchObjectPattern` is segment-bounded (M-18), decision cache key covers every context field used by `sub_rule`, time-dependent rules are never cached, wildcard tenant rules cannot be defined from tenant files, empty-reload guard keeps last-known-good, startup fails closed on missing model/policy.
- RLS interpolation (`InterpolateRlsFilter`): literal-state tracking, strict claim character set, fail-closed on missing attributes; client `action`/`gql.action` claims are dropped (`BuildEvaluationContext`).
- ReBAC evaluator: empty-field rejection, cycle and depth bounds, generation-validated cache, fail-closed on store exception, batch tenant mismatch denied.
- HitL: status check under per-ticket lock (no double approval), self-approval compares all identifiers, tenant-scoped lookup returns "not found", signed tickets and broadcasts with `FixedTimeEquals`, fail-closed timeout.
- Cluster-admin policy: literal unprefixed role only, ForwardAuth identities never cluster admin; `SecurityPrincipalContext` ignores prefixed roles for global checks.
- SSRF/egress rules (`EgressAddressRules`, `SsrfProtectionHandler`): IPv4-mapped/NAT64/6to4 normalization, metadata and CGNAT always forbidden, trusted hosts fail closed on resolution errors.
- Audit canonicalization: escapes `\`, `|`, CR/LF/TAB; sequence-prefixed HMAC-SHA256; anchor signatures use ECDSA/RSA-PSS with verify-only mode; MCP audit failures abort execution (fail-closed).
- MCP: session cap per principal, SSE/session cleanup, policy `Tool not registered` deny, prompt guard normalizes NFKC/zero-width and decodes JSON/base64, token budget truncation, PII scrub on result path; admin tools hidden from `tools/list` for non-admins.
- DP engine uses CSPRNG and atomic budget counter; policy simulation enforces effective tenant.

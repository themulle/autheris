# Security review: Autheris.Application data/SQL/OLAP/jobs/procedures scope

Scope: `src/Autheris.Application/{Data,Sql,Federation,Olap,Procedures,VirtualFilters,SqlEndpoints,Jobs,OData,Streaming,Services,Caching,Performance,Serialization,Interfaces}`. Read-only review. Findings below are NEW unless stated.

### High — Async job request controls its own row cap and timeout (WebSQL/transport row limits bypassed, unbounded buffering)
- **File:** `src/Autheris.Application/Jobs/Services/AsyncQueryJobBackgroundWorker.cs:90-93` (also `src/Autheris.Domain/Model/AsyncJobModels.cs:14-18`, `src/Autheris.Application/Jobs/Services/AsyncQueryJobManager.cs:61-111`)
- **CWE:** CWE-770 / CWE-400
- **Confidence:** Confirmed
- **Issue:** `AsyncQueryJobRequest` is bound directly from the client JSON body (`AsyncJobEndpoints` `POST /api/v1/jobs/query`). The worker builds `new SqlRowLimit(maxRows, maxRows)` with `maxRows = Math.Max(1, item.Request.MaxRows)`, so the client-supplied `MaxRows` is both the default and the maximum allowed. It is never intersected with `WebSql.MaxAllowedRows`, `Gateway:RowLimits:*` (there is no `AsyncJob` channel in `TransportRowLimitsOptions`) or any hard cap (`SqlRowLimit.CappedAt` exists but is not used here). The result is then fully materialised by `ExecuteQueryBufferedAsync` (a `List<Dictionary<..>>`) and serialised in memory. `Timeout` is also client-controlled: if omitted or very large no cancellation is armed (`cts.CancelAfter` only when supplied), while the DB command timeout is `WebSql.ExecutionTimeoutSeconds`. No per-user/tenant quota on queued jobs exists either (bounded channel of 1000 with `FullMode=Wait`, so a full channel blocks the HTTP handler in `WriteAsync`).
- **Exploit scenario:** Any authenticated user sends `POST /api/v1/jobs/query {"query":"SELECT * FROM big_table","maxRows":2147483647,"format":"csv"}`. The statement runs through the governed pipeline with an effective limit of 2^31-1 rows even though WebSQL is configured with e.g. `MaxAllowedRows=10000`; the gateway buffers the whole table in memory (OOM / GC pressure for all tenants) and writes it to disk. Repeating this 1000 times fills the channel and stalls further submissions. This is also a bulk-exfiltration path that skips the configured per-channel egress ceilings.
- **Remediation:** Treat the job limit as a request for a lower value only:
  ```csharp
  var webSql = _options.Value.WebSql ?? new WebSqlOptions();
  var channel = SqlRowLimit.For(webSql, _options.Value.RowLimits?.AsyncJob);   // add AsyncJob to TransportRowLimitsOptions
  var capped = channel.CappedAt(Math.Clamp(item.Request.MaxRows, 1, _options.Value.AsyncJobs.MaxRowsHardCap));
  ```
  Clamp `Timeout` to a configured maximum and always arm `cts.CancelAfter(min(requested ?? max, max))`. Stream rows to the result file instead of buffering (`ExecuteGovernedQueryAsync` with a row writer). Enforce per-user/tenant active-job limits in `SubmitJobAsync` and use `TryWrite`/reject with 429 when the channel is full.

### High — Tenant data-source allowlists (`WebSql.TenantDataSourceAllowlist`, `WebSql.AllowedDataSources`) are not enforced on cross-source, OLAP and HTTP-table paths
- **File:** `src/Autheris.Application/Sql/Services/GovernedSqlRewriter.cs:282-310` (throws `CrossSourceRoutingException` before any allowlist check); `src/Autheris.Application/Sql/Services/CrossSourceQueryRouter.cs:72-135`; `src/Autheris.Application/Sql/Services/FederatedDuckDbExecutionService.cs:232-330`; `src/Autheris.Application/Data/Services/GovernedDataQueryService.cs:180-216`; `src/Autheris.Api/Endpoints/DuckDbOlapEndpoints.cs:150-215`
- **CWE:** CWE-639 / CWE-863 (cross-tenant authorization bypass)
- **Confidence:** Confirmed (control absent on these paths); impact depends on `WebSql.CrossSource.Enabled=true` (default false) or the OLAP engine being enabled, and on a consent/ReBAC grant existing for the table
- **Issue:** The only per-tenant data-source isolation control is `SqlDataSourceResolver.ResolveAllowedDataSource` (-> `IsDataSourceAllowedForTenant` + global `AllowedDataSources`). It is called only on the homogeneous single-catalog path (`GovernedSqlRewriter` lines 304/308, `GovernedSqlExecutor` line 147). For a statement referencing two catalogs the rewriter throws `CrossSourceRoutingException` at line 282-285 before the resolver is reached; `CrossSourceQueryRouter.RouteAsync` resolves tables by name from the catalog and never consults the allowlists; `FederatedDuckDbExecutionService` and `FederatedStagingService` only run consent/ABAC decisions and stage via connectors. `GovernedDataQueryService` sends `HttpDeclarative` tables straight to the federated service, and `DuckDbOlapEndpoints` stages tables after only `ICrossDomainAccessResolver`. `ArrowFlightSqlServer.GetTablesAsync` shows the intended rule (`IsDataSourceQueryable`) but it is not applied where tables are actually read.
- **Exploit scenario:** Tenant `acme` is restricted to data source `acme_db` via `TenantDataSourceAllowlist`; `globex_db` is another tenant's database registered in the shared catalog. With cross-source enabled, `acme` user runs `SELECT a.id, g.* FROM acme_db.public.orders a JOIN globex_db.public.orders g ON a.id = g.id` (or only selects a `HttpDeclarative` table sourced from a foreign system). The multi-catalog path skips the allowlist; the only remaining barrier is a consent for `globex_db.public.orders`, i.e. the explicit tenant-to-source boundary is gone. `POST /api/v1/olap/query {"sql":"SELECT * FROM orders","tableNames":["globex_db.public.orders"]}` has the same effect without the cross-source flag.
- **Remediation:** Enforce the allowlist in one choke point used by every path: in `CrossSourceQueryRouter.RouteAsync` (for every `ResolvedSourceTable.EffectiveDataSource`) and in `FederatedStagingService.StageAsync`/OLAP endpoint before any read:
  ```csharp
  if (!SqlDataSourceResolver.TryResolveGloballyAllowedDataSource(webSql, source, out var ds) ||
      !GovernedSqlExecutionService.IsDataSourceAllowedForTenant(webSql, tenantId, ds))
      throw new WebSqlTableDeniedException(...);   // fail closed, same message as unknown table
  ```
  Add a regression test with two catalogs, one outside the tenant allowlist.

### Medium — DuckDB OLAP SQL validator is bypassed by quoted identifiers (function blocklist, `range`/`repeat` limits)
- **File:** `src/Autheris.Application/Olap/DuckDbOlapEngine.cs:405-505` (`ExtractTokens` at ~558, `DisallowedTableFunctionsRegex` at 506-509)
- **CWE:** CWE-184 (incomplete list of disallowed inputs) / CWE-400
- **Confidence:** Likely (validator bypass confirmed by reading the lexer; DuckDB resolves `"name"(...)` as a function call)
- **Issue:** `ExtractTokens` deliberately skips everything inside `'...'` and `"..."`, and the regex requires `\bname\s*\(`. A quoted function name `"range"(...)` is therefore invisible to both the keyword/function token check (`read_*`, `glob`, `duckdb_*`, `pragma_*`, `current_setting`, `getenv`, ...) and the `range|generate_series|repeat|...` regex, because the character after the name is `"`, not `(`. The SQL comes unchanged from `POST /api/v1/olap/query` (`OlapQueryRequestDto.Sql`, only ASCII/`$` checks). File/network access is still stopped by `enable_external_access=false` + `lock_configuration=true`, so the impact is the removal of the documented defence in depth: unbounded generators (SQL2-9) and introspection functions.
- **Exploit scenario:** `{"sql":"SELECT count(*) FROM \"range\"(1, 100000000000)"}` or `SELECT \"repeat\"('A', 2000000000) FROM \"generate_series\"(1,1000000)` burns CPU/memory/spill up to `QueryTimeoutSeconds` x `MaxConcurrentQueries`, exhausting the OLAP concurrency semaphore (503 for everyone else). `SELECT * FROM \"duckdb_settings\"()`, `SELECT \"current_setting\"('temp_directory')`, `\"getenv\"('X')` return server configuration/paths (the blocklist was meant to forbid these).
- **Remediation:** Do not blocklist on raw text. Parse the statement with a real parser (the repo already has `TrinoSqlEngine`/AST + `SqlFunctionAllowlists.DuckDb`) and allow only allowlisted function names after unquoting and case-folding; at minimum make `ExtractTokens` emit the content of double-quoted identifiers as tokens and change the regex to `\b(?:range|...)"?\s*\(` plus an unquoted-name pass. Prefer running user SQL against a DuckDB connection with `SET disabled_filesystems`, a read-only view layer and `memory_limit` per query, and cap generated rows (`SET max_expression_depth`, etc.).

### Medium — GEO_JITTER masking returns the raw value when it is not numeric (fail-open)
- **File:** `src/Autheris.Application/Services/ColumnMaskingProvider.cs:428-431` (called from `MaskValue` `case "GEO_JITTER"` at ~86)
- **CWE:** CWE-209/CWE-693 (protection mechanism failure, fail-open masking)
- **Confidence:** Confirmed
- **Issue:** `MaskGeoJitter` does `else if (!double.TryParse(value.ToString(), ..., out d)) { return value; }`, i.e. any value that is not a plain number is returned in clear text. Every other rule type fails closed (`default:` -> `Replacement ?? "REDACTED"`; byte[] -> redacted). This path is used by every gateway-side masking consumer (`GovernedConnectorReader.ProjectRow` for connectors/HTTP/OLAP staging, OData/GraphQL via `IColumnMaskingProvider`, `StreamRlsPolicyEnforcer`, `SubgraphResultMasker`).
- **Exploit scenario:** A catalog column `location` (varchar, `"52.5200,13.4050"`), a WKT/GeoJSON string, a `DateTime`, or a `"N/A"`/localized-decimal (`"52,52"`) value is configured `GEO_JITTER`. A user with Mask access reads the column through REST/OData/OLAP and receives the exact coordinates, while the catalog and audit say the column is masked.
- **Remediation:** Fail closed: `return rule.Replacement ?? null;` (or `"REDACTED"`) when parsing fails, and for non-numeric CLR types; add a unit test with string/WKT/date inputs.

### Medium — Async job results and job descriptors are never purged (indefinite retention of query text and result data)
- **File:** `src/Autheris.Application/Jobs/Services/AsyncQueryJobManager.cs:253-275` (`PurgeExpiredJobsAsync`), `src/Autheris.Application/Jobs/Services/AsyncQueryJobBackgroundWorker.cs:104-123`
- **CWE:** CWE-459 / CWE-404 / CWE-312
- **Confidence:** Confirmed (`grep` finds no caller of `PurgeExpiredJobsAsync` anywhere in `src/`)
- **Issue:** Completed jobs write `scratch/jobs/<tenant>/<jobId>.json|csv` (plain text, world-default permissions, post-masking data) and keep the full SQL `Query` in the in-memory `_jobs` dictionary; nothing ever expires them (and failed jobs that already wrote nothing still leave descriptors). Results also outlive revoked consents/policy changes: a download re-reads the file with no policy re-evaluation.
- **Exploit scenario:** A user submits jobs for rows they are entitled to today; after consent revocation, role removal or the user being offboarded, the file remains downloadable (by that user's still-valid token) indefinitely, and any local reader of the scratch directory sees tenant data at rest. A submit-loop fills the disk (compounded by the unbounded `MaxRows` above).
- **Remediation:** Register a hosted service/timer that calls `PurgeExpiredJobsAsync(TimeSpan.FromMinutes(configured))` (default <= 1 h), also deleting files of Failed/Cancelled jobs and orphan files at startup; create the scratch directory with 0700 (`UnixFileMode`), cap per-tenant scratch bytes, and re-check authorization (`GetJobAsync` + current policy) when serving the result. Make `UpdateJob` a compare-and-swap so a late `Completed` cannot overwrite `Cancelled` (see `AsyncQueryJobBackgroundWorker.cs:112`, `AsyncQueryJobManager.cs:45`).

### Medium — SQL endpoint hot-reload: unhandled exceptions in `FileSystemWatcher` handlers can terminate the host; deletions of renamed endpoints leave them registered
- **File:** `src/Autheris.Application/SqlEndpoints/Services/SqlEndpointLoader.cs:521-535` (handlers), `:92-114` (`LoadFile`/`ParseSqlContent`), `:65` (recursive scan)
- **CWE:** CWE-755 / CWE-459 / CWE-61
- **Confidence:** Confirmed for the missing try/catch and stale registration; Likely for the symlink point
- **Issue:** `_watcher.Created`/`Changed` call `LoadFile(e.FullPath)` with no try/catch. `LoadFile` throws on a locked file (`IOException`, the normal state while an editor saves), an empty file (`ArgumentException.ThrowIfNullOrWhiteSpace`), or any parse error. Exceptions in these thread-pool callbacks are unhandled and crash the process (the procedure loader explicitly guards this, review P-3). `Deleted` unregisters by file name, but endpoints are registered under the `-- @name:` header, so deleting/disabling a file whose header name differs from its file name leaves the old endpoint live (fail-open removal); a `Changed` event with a new `@name` also leaves the old name active. `LoadFromDirectory` uses `SearchOption.AllDirectories` and `File.ReadAllText` without any symlink/reparse-point check (the procedure loader rejects them), so a symlinked directory inside the queries folder pulls in `.sql` files from outside the root.
- **Exploit scenario:** Whoever can write the `queries/` directory (CI sync, shared volume) saves an empty/half-written `.sql` file, which kills the gateway (availability). An operator "revokes" a sensitive endpoint by deleting `reports.sql` (header `@name: salary_report`), but `/api/v1/queries/salary_report` keeps executing until restart.
- **Remediation:** Wrap each handler body in try/catch (log, keep the previous definition), retry with backoff on `IOException`, track `fullPath -> endpointName` (as `ProcedureDefinitionLoader._fileToName` does) and unregister that name on delete/rename/invalid change, and reuse the `HasLinkedDirectory`/`ReparsePoint`/containment checks from the procedure loader.

### Low — Structured virtual-filter predicates on the SQL channel have no tenant restriction on their source tables (federation key query does)
- **File:** `src/Autheris.Application/VirtualFilters/StructuredFilterSqlBuilder.cs:49-114`, `:150-210` vs `src/Autheris.Application/VirtualFilters/Federation/StructuredFilterKeyQueryBuilder.cs:70-80`; related `src/Autheris.Application/VirtualFilters/SqlFilterCompiler.cs:124-139`
- **CWE:** CWE-285 / CWE-639
- **Confidence:** Likely (code divergence confirmed; exploitability depends on key-source table design)
- **Issue:** The key-source query adds `alias.tenant_col = @vf_tenant` for every tenanted table (WI-19 / SEC-6), but `Build`/`BuildTyped` (the predicate actually injected into WebSQL/REST/OData) emit `EXISTS (SELECT 1 FROM source ... WHERE <conditions> AND key = target.key)` with no tenant condition. For SQL-defined filters, SR15-11 only checks that the column named `tenant_id`/`tenantid` is *referenced* in some filter position (`FilterColumnReferences`), not that it is compared with the caller's tenant (`a.tenant_id IS NOT NULL` passes); other tenant column spellings accepted elsewhere (`RequireTenantColumnOrThrow`) are not recognised.
- **Exploit scenario:** The assignment table `sec.user_customers` is shared across tenants; tenant B has a row (user S-1-5-.., customer 42). A filter whose conditions do not pin the subject tightly (e.g. group/role based) authorizes customer 42 rows of tenant A for the same principal on the SQL channel while the federation channel correctly intersects with the tenant.
- **Remediation:** Apply the same per-alias tenant condition (bound parameter) in `Build`/`BuildTyped`, and make `SqlFilterCompiler.Validate` require an equality comparison of the catalog's actual tenant column (via `RequireTenantColumnOrThrow`) with a gateway-bound tenant parameter, not mere presence.

### Low — Federated subgraph result masking is a field-name denylist
- **File:** `src/Autheris.Application/Federation/Services/SubgraphResultMasker.cs:168-211`
- **CWE:** CWE-1188 / CWE-200
- **Confidence:** Likely
- **Issue:** Subgraph responses are masked only when the response key/real field matches a hard-coded substring list (email, iban, phone, ssn, salary, birth, ...). Everything else passes unmasked, independent of catalog classification/consents.
- **Exploit scenario:** A subgraph returns `taxNumber`, `passportNo`, `homeAddress`, `nationalId`, `licensePlate`; none match, so non-admin callers receive them in clear text.
- **Remediation:** Drive masking from the catalog/consent decision for the subgraph's entity (default-mask unknown scalar fields of sensitive types) and keep the heuristic only as an additional layer; document that name heuristics are not a policy.

## Verified strengths
- WebSQL pipeline: single statement, DDL/DML gates, function allowlist per dialect, reserved `__gql_` prefix rejected in client SQL and parameter names, case-differing table spellings rejected, catalog-only tables, tenant column predicate with plain-identifier regex and quoted tenant literal, bound client parameters with collision checks (`GovernedSqlExecutor.cs`, `GovernedSqlRewriter.cs`).
- Plan cache key = tenant + dialect + datasource + 64-bit query hash + policy hash over RLS text, masks, column list, row limit, functions, plus raw SQL and fingerprint equality check; the cached plan carries no values (policy values are re-bound per request) (`CompiledSqlQueryPlanCache.cs`).
- Masked/denied columns are rejected in WHERE/JOIN/HAVING/ORDER BY (`EnforceMaskedColumnGuardrails`, `SqlDataSourceExecutor`, `DataApiFilterTranslator`, `TreeSqlCompiler`); REST data API filter text must resolve every word to a catalog column, so function/subquery smuggling fails.
- Federated staging authorises all tables before any read, per-source-qualified decisions (SEC-1), governed reader masks once and strips denied columns, audit is fail-closed, HTTP auth modes and ForwardBearerToken restricted, budgets for rows/bytes/tables.
- Async job manager: zero-IDOR check on tenant AND owner for status/result/cancel, GUID ids, path-containment with trailing separator, tenant-validated directory names, fail-closed audit for ALLOW.
- Procedures: typed parameters, `CommandType.StoredProcedure`, identifier validation, reparse-point/symlink rejection and file size limits in the loader, row scope via unique-key match, bounded readers, SESSION_CONTEXT read-only (`MssqlProcedureInvoker`, `ProcedureDefinitionLoader`).
- HTTP declarative executor: redirect handling is same-origin only with re-validation, reserved tenant parameter names, traversal checks, header deny list, egress validation.
- DuckDB engine: `enable_external_access=false` + `lock_configuration`, per-session temp dir, memory/threads/temp-size caps, concurrency semaphore, row/byte caps, rows inserted via bound parameters, `$` marker validation, recursive CTE blocked.
- Streaming enforcer: tenant check, no anonymous fallback, virtual filters fail closed, unknown catalog columns dropped.
- CSV export neutralises leading `= + - @ \t \r` (SEC-MED-16), regexes carry timeouts, tenant ids use `\z`-anchored regex.

## Areas not covered
- `TrinoSqlEngine` (parser/AST rewriter, `RewriteRls`, function allowlists, column reference extraction): whether HMAC-masked columns (exempted from the filter/join guardrail) are replaced by the mask expression at *every* reference (WHERE/JOIN/GROUP BY/CASE/subquery) was not verified; predicate-oracle, CTE/set-operation and subquery masking leakage depend on that engine.
- `Autheris.Api` endpoints (authorization attributes, `EndpointSecurity.GetRequestTenant`, rate limiting), `Autheris.Infrastructure` connectors/repositories, `EgressUrlPolicy` (DNS pinning/rebinding), `Policy/*` (`TableAccessPolicy`, consent/profile caches, ReBAC), `Security/*`.
- `OData` (only `OpenApiCacheManager` and endpoints that call it were read; the generated spec is global, not per-user), `Performance/IncrementalDelivery`, `ArrowExportService`/`ParquetExportService` internals beyond limits (Parquet export has no caller in `src/`), `ProcedureDefinitionParser` YAML details, `StoredProcedureCatalogValidator`, `BatchRelationLoader`, `ChunkedQueryExecutor`, `VirtualFilterAdministrationService`, `PathLookupConnector`/`HttpKeyPushdownCapability`.
- DuckDB `getenv`/settings behaviour in DuckDB.NET 1.5.6 was not executed (reasoned from code only); `DataTable.Select` expression semantics for the in-memory row filter (backslash/bracket escaping) were not tested.

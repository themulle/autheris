## 3. Contract changes against `PLAN-FED-01` section 3

### 3.1 Transports and default list
- `SqlTransports` stays the only registry; add `GraphQl`. No `FederationTransports` type. `CrossSourceOptions` gets `DefaultAllowedTransports(bool protectedStaging)`; the literal at `RestApiOptions.cs:77` is replaced.
- Widening of the default list is staged so that no transport is ever allowed before its conditions hold (SEC-FED-18, SEC-FED-09): the seven SQL-text transports (`Rest`, `Mcp`, `ArrowExport`, `FlightSql`, `SqlEndpoints` added to `WebSql`, `Trino`) after I-10; `Olap` after I-11 (the facade); `AsyncJob` after I-12 (`ProtectedStagingEnabled`); `GraphQl` after I-19. Each addition needs the SEC-FED-18 default-list decision test. An explicit `AllowedTransports` list always replaces the default. Q-1: `Enabled` stays `false`, so no default install changes behavior.

### 3.2 Gate and exception
- `IFederationGate` keeps `EnsureAllowed(string?)` and `IsEnabledFor(string?)` (signatures already match `PLAN-FED-01` section 3).
- One code for both gate denials: **`FEDERATION_DISABLED`** with the existing fixed text. `FEDERATION_TRANSPORT_NOT_ALLOWED` is dropped: the merged gate and its Phase 3 review chose identical text so a caller cannot probe which transports are configured. Default taken; the owner may veto.
- `IFederatedQueryExecutionService.ValidateAsync` gets a `transport` argument (callers: `GovernedSqlExecutionService.cs:113`, `ArrowFlightSqlServer.cs:95`, async submit). Gate runs after `AuthorizeAllTablesAsync` in execute and validate.

### 3.3 Parameters (#131)
`WP-FED-03` no longer carries parameters. The only carrier is `FederatedParameterContract` (I-26). Until then a client parameter in a federated statement behaves as today (analysis error) and list values stay refused with `SQL_LIST_PARAM_UNSUPPORTED` (#128, I-5). `FEDERATION_PARAMETER_INVALID` is not introduced; federated parameter errors use `SQL_LIST_PARAM_*` and the existing single-source parameter codes (`PLAN-FED-131` A-7). `SEC-FED-35..37` are reviewed in S-2.

### 3.4 Key columns and Clear
Parent and child key columns are Clear by `GetEffectiveColumnAccess(...) == Clear` on decisions produced by the data-path resolver (`IConsentResolutionService.ResolveAccess` with `GetScopeSet(principal.Claims)`, as fixed by #127). No scope-blind copy of consent rules is allowed in `Data/Relations`, the splitter or MCP relation lists.

### P3.3 Findings

**SEC-FED-DELTA-01 - High - LIVE BUG (when `CrossSource:Enabled=true`): the federated failure audit stores `ex.Message` for every non-`GatewaySecurityException`.**
Evidence: `FederatedDuckDbExecutionService.cs:347-350` (`catch (Exception ex)` -> `RecordFailureAuditAsync`), `:630`: `error = ex is GatewaySecurityException denial ? $"Access denied ({denial.ErrorCode})" : ex.Message`. The SEC-11 comment directly above (`:629`) states that messages "may carry names or data values of the failing source", and the code then does the opposite for every other exception (`WebSqlPolicyException`, `SecurityException`, `InvalidOperationException`, DuckDB conversion errors that quote the offending staged value, provider text from source reads). The record lands in the HMAC-chained audit store, which is append-only and read by a wider population than the caller; a leaked value cannot be erased. `PLAN-FED-131` `SEC-131-04` is therefore correct, and the exposure does not depend on parameters. Contrast: PR #140's OLAP audit stores stable codes only (`OlapStagingService.cs:562` `FailureDetails(code)`, `:530`), so routing OLAP through this method (WP-FED-05) would **regress** OLAP audit hygiene. The async-job path is already clean (`AsyncQueryJobBackgroundWorker.cs:305-311` uses `FixedMessageOrDefault`), and the HTTP body is generic outside Development, so the leak is the audit record (and any log line that repeats the message).
Required change: `error` is a fixed text derived from `reasonCode` (stable code, or the exception type name) for every exception, never `ex.Message`; `reasonCode` for a `FederationException` is its code (DELTA-11); the audit record of this method is the only place; log lines of this path log type and code only. Test: for DuckDB conversion error, provider error with a value in the text, `WebSqlPolicyException` carrying a column name and a plain `InvalidOperationException("secret-value")`, the persisted `DetailsJson` contains none of the marker strings; cancellation and `GatewaySecurityException` unchanged.
Recommendation: **split out as a standalone bugfix, delivered before I-9** (see P3.7).

**SEC-FED-DELTA-02 - High - The staged widening order of 3.1 is unsafe: the seven SQL-text transports are added after I-10, but their conditions are not met by I-10.**
Evidence and required prerequisites, each one binding for the widening step (the default-list decision test of SEC-FED-18 must assert them):
1. *Spill at rest (SEC-FED-07/09).* The delta says `AsyncJob` absent from the default "keeps SEC-FED-09 safe". That covers only the async result file. DuckDB spill is enabled by default: `DuckDbOlapOptions.MaxTempDirectorySize = "256MB"` (`DistributedCacheOptions.cs:80`), applied by `DuckDbOlapEngine.BuildSetupSql` (`:285-287`, `max_temp_directory_size`), with no encryption. Every federated query (already `WebSql`/`Trino`, soon `Rest`, `Mcp`, `ArrowExport`, `FlightSql`, `SqlEndpoints`) can write governed rows to disk in clear. Encryption lands in WP-04 (I-12), after the widening (I-10). Required: either I-10 sets the default `MaxTempDirectorySize` to `0B` (no spill; DuckDB fails with an out-of-memory error that maps to `FEDERATION_LIMIT_EXCEEDED`) and WP-04 later re-enables spill together with `temp_file_encryption` and per-request owner-only directories, or the widening moves behind I-12. Take the first option (about 10 LOC, reversible).
2. *Concurrency (SEC-FED-08).* The federated executor has no lease at all (no limiter reference in `FederatedDuckDbExecutionService.cs` or `FederatedStagingService.cs`); only OLAP has `OlapRequestLimiter`. Widening to five more transports multiplies an unbounded number of parallel stagings per tenant. Required: the per-tenant plus global lease moves from the OLAP service to the federation path (taken after authorization and gate, before the first read, released in `finally`) in WP-FED-03, as a precondition of the widening; WP-FED-05 then reuses it.
3. *Error and audit hygiene (SEC-FED-13).* `SEC-FED-DELTA-01` fixed and `FEDERATION_SOURCE_ERROR` mapped with no driver text (WP-FED-03) before the widening.
4. *`Rest` is not one consumer.* `SqlTransports.Rest` is stamped by `AnalyticsEndpoints.cs:108`, `DatasetDataEndpoints.cs:184`, `GovernedAggregationService.ValidationAndExecution.cs:369/376` and planned reads (`GovernedDataQueryService.cs:178/193`, with a `CrossSourceRoutingException` fallback at `:214`). Allowing `Rest` also opens federation for aggregation and dataset reads, which `PLAN-FED-01` never reviewed per consumer. Required: `Rest` is added only after a consumer inventory test (every call site that sets `Rest` is listed with its federation behaviour: allowed, or refused with `FEDERATION_UNSUPPORTED_SOURCE`); aggregation over a federated statement stays refused until reviewed. `Mcp`, `ArrowExport` and `FlightSql` need the SEC-FED-13 Arrow/Development test first.
5. *Explicit lists bypass every staging condition.* `CrossSourceOptionsValidator.cs:36-47` accepts any known transport name, including `AsyncJob`, with no protection check (the option `ProtectedStagingEnabled` does not exist yet). That is a configuration hole today (inert under Q-1) and stays one after I-12 unless the validator fails startup when `AllowedTransports` contains `AsyncJob` and `ProtectedStagingEnabled` is false or its prerequisite is not effective; likewise `GraphQl` before WP-08 is complete (the name does not exist yet) and `Olap` is unaffected. Required in WP-FED-01.
6. *Unknown transports are denied correctly:* `SemanticMetricQueryService.cs:233` stamps `"SemanticMetrics"`, which is not in `SqlTransports.All`; the gate denies it (blank or unlisted = deny). It must stay denied; add it to the decision test as "explicitly not allowed".
Corrected order: I-9 (gate wiring, `FederationException`, option validation) -> **S-0 bugfix** -> I-10 including lease, spill default `0B`, `FEDERATION_SOURCE_ERROR`; widening step A adds `WebSql`+`Trino` (unchanged) plus `Mcp`, `SqlEndpoints`, `FlightSql`, `ArrowExport` at the end of I-10; `Rest` only after the inventory test; `Olap` with I-11; `AsyncJob` with I-12; `GraphQl` with I-19.

**SEC-FED-DELTA-03 - High (Medium while Q-1 holds) - LIVE: the oracle order violation is not limited to the gate; at least six denials precede table authorization.**
Evidence: in `ExecuteFederatedInternalAsync` before `AuthorizeAllTablesAsync` (`:308`) the code throws for: disabled switch (`:247`), transport (`:252`, `:262`), DML (`:258`), function denylist with the function name (`:267`), "not a cross-source query" (`:282`) and table count (`:289`, with the count). `ValidateAsync` has the same shape (`:210`, `:217`, `:222-225`, authorization only at `:228`). The router, called before authorization, throws type-specific text for an existing table of an unsupported type (`CrossSourceQueryRouter.cs:114`, `HttpPlugin`/lakehouse) while a missing or inactive table gets the generic `WebSqlTableDeniedException` (`:108`): a caller who cannot see the table learns that it exists and its type (`BC-OLAP-06` required this check after authorization; PR #140 does so, the SQL path does not). Before the executor, `GovernedSqlRewriter` throws `CrossSourceRoutingException` at `:297`, `:401`, `:445`, `:458` after only checking that the table exists, is active and is registered on another source (no consent evaluation yet): with `Enabled=true` and a transport that is not allowed, `SELECT ... FROM visible JOIN probe` returns the transport text for an existing foreign-source table and `SQL_POLICY_DENIED` for a missing one (the combined result is an existence oracle for tables of other sources; with the transport allowed the later `WebSqlTableDeniedException` hides it). The delta moves only the gate (3.2) and so closes one of these.
Required change (WP-FED-01/03): (a) router and executor produce only *facts* before authorization; every `FEDERATION_*`/`SQL_*` rejection that depends on tables (unsupported type, table count, "not cross-source", function denylist when it names a table-bound element) is raised after `AuthorizeAllTablesAsync`. Statement-level denials that depend only on the caller's own text (DML, a denied function name in the statement) may stay first because they reveal nothing about the catalog. (b) `GovernedSqlRewriter` stops branching on `CrossSourceOptions.Enabled` at the four sites and `:296-302`: it always raises `CrossSourceRoutingException` for a multi-source statement, so the federated service (authorize, then gate, which includes `Enabled`) is the single decision point; `ResolveFederatedService` already fails closed (`GovernedSqlExecutionService.cs:96-98`). This also unifies the disabled and not-allowed texts (DELTA-04). (c) The router's `Enabled` check (`:141-143`) is removed for the same reason (the gate owns it). Test: spy on connector, planner and audit: with two sources and one unauthorized table, every refusal body and status is identical for (missing, inactive, unauthorized, unsupported type, over table count, transport denied, switch off), and the first connector call happens after authorization and gate.
Recommendation: part (a)/(b) for the gate and the router's unsupported-type check are a candidate for the same standalone bugfix as DELTA-01 only if the owner enables `CrossSource` before wave 2 ships; under Q-1 they ride with I-9 (they must not wait for I-10).

**SEC-FED-DELTA-11 - Medium - `FederationException : WebSqlPolicyException` keeps old catches working, but also inherits behaviour that is wrong for several codes.**
Evidence: `WebSqlPolicyException` is a `SecurityException` and "curated, safe to return" (`WebSqlPolicyException.cs:6-11`); it is echoed outside production in `SqlEndpointRoutes.cs:375`, stored as the audit reason in `GovernedSqlExecutor.cs:639` (`WebSqlPolicyException => error.Message`), classified as a denial with `reasonCode = "POLICY_VIOLATION"` in `FederatedDuckDbExecutionService.cs:621-630`, mapped to a uniform 404 in the Trino poll (`WebSqlEndpoints.Execution.cs:427`) and to 403 in `SqlEndpointRoutes.cs:370/449`, `WebSqlEndpoints.Execution.cs:474`, `ProcedureEndpointRoutes.cs:353`. Consequences: (a) `FEDERATION_SOURCE_ERROR` (upstream failure, availability) as a `WebSqlPolicyException` would be audited as `DENY`/`POLICY_VIOLATION`, returned as 403 and echoed in Development: wrong class, wrong status, and the message becomes "safe to return" by type. (b) A `switch` on `WebSqlPolicyException` placed before a `FederationException` arm swallows the code. (c) The message of any subclass is trusted by name; an inner exception message must never be copied into it.
Required change: split the hierarchy: `FederationDeniedException : WebSqlPolicyException` (codes `FEDERATION_DISABLED`, `FEDERATION_UNSUPPORTED_SOURCE`, `FEDERATION_KEY_NOT_CLEAR`, `FEDERATION_SORT_NOT_SUPPORTED`, limit codes) and a separate `FederationSourceException : Exception` for `FEDERATION_SOURCE_ERROR` (not a `SecurityException`; 502/503 per transport; audited as `QueryExecutionError`). Both expose `ErrorCode` and a fixed message from a constant table; constructors accept no free text and never an inner message (the inner exception is only logged by type). `SqlCompilerErrorMapper` and `ErrorSanitizingFilter` (`:61-` handles `GatewaySecurityException` only today) get explicit arms **before** the generic ones; the audit methods use `ErrorCode` as `reasonCode`. Test: each code through REST, Trino poll, Flight, MCP, GraphQL and async-job persistence yields the stable code and fixed text, no inner message, correct status and audit class; a driver exception with a marker string never reaches any body, log field or audit field.

**SEC-FED-DELTA-12 - High - Q-6 "both owners" cannot be implemented on the current model; the fail-closed default makes the feature unusable until WP-07 defines an owner.**
Evidence: `TableMetadata` has `OwnerTenantId` only (`TableModels.cs:144`, a tenant, not a principal); `DataOwner` is a global role (`EndpointSecurity.cs:72`, `DevConfiguration.cs:117`) with no per-table assignment; `AllowCrossDataSource` is init-only and never persisted (`TableModels.cs:293`). So today *every* table is "without a defined owner" and, by the delta's own rule, cannot be enabled. That is safe (fail closed) but it is a design gap, not a flag check.
Required change (WP-FED-07, binding): (1) a per-table owner designation (principal SID or group, tenant-scoped) must exist and be set through an audited path before the flag can be enabled; absent, empty, unresolvable, deactivated or a different tenant -> not enableable and evaluated as `false` at runtime. (2) Both tables must have an owner; the approval is recorded per (relation id, parent epoch, child epoch); any owner change or epoch bump of either table invalidates the approval and the flag evaluates `false` until re-approved. (3) Four-eyes means distinct principals: the requester cannot be one of the two approvals; if one principal owns both tables, a second distinct approver (`GovernanceAdmin`) is required; the same SID twice is refused; service identities cannot approve. (4) `GovernanceAdmin` plus both owner approvals, not either/or; the MCP admin four-eyes flow stays additional. (5) Disabling requires one owner or admin (asymmetric on purpose). (6) The flag is read as `false` if the store cannot be read. (7) Audit before/after, actors, both approver SIDs; epoch bump of both tables; schema cache invalidation (SEC-FED-11/15). Tests: table without owner, one owner missing, same principal as both owners, requester as approver, owner change after approval, cross-tenant relation id, store failure.

**SEC-FED-DELTA-13 - Low - Q-8 key-set import per source: default off must hold in all three DDLs and in the in-memory/shape layers.**
Required (WP-12/14): column default `false` (not nullable), DDL x3 and shapes in one serial change (G-SHARED); missing column on an older database evaluates `false`; four-eyes and audit as for other source settings; `allow_key_set_import` is never inferred from `AllowCrossDataSource`; HTTP, lakehouse and plugin sources never receive keys regardless of the flag (SEC-FED-26); parameters pushed under #131 are separately governed (no import).

Clarification to record in `PLAN-FED-01` 12.2: the HMAC exemption applies to DuckDB-internal joins and filters only; relation keys, key sets and pushed predicates require `Clear` (SEC-FED-19/20). (c) `SemanticMetrics` transport stays denied. (d) The delta's Totals and the "0 / about 3,400" test estimate must grow by the tests of P3.6 (about 700 lines).
